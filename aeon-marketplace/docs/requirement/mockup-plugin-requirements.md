# Mockup Plugin — Requirement Specification

> **สถานะ:** Draft v0.1 (สำหรับใช้เป็นโจทย์ในการสร้าง plugin)
> **ผู้เขียนความต้องการ:** User
> **เอกสารที่ต้องอ่านคู่กัน:** Design Plugin Spec (§12 ขอบเขต, §6 trace, §19 continuity)
> **ที่มา:** เนื้อหาส่วนนี้เคยอยู่ใน design plugin §12 และ V16–V22, D18–D22 — แยกออกมาเป็น plugin ของตัวเอง หมายเลขเดิมในฝั่ง design ถูกสงวนไว้แล้ว

---

## 0. สรุปย่อสำหรับผู้เรียน

Mockup Plugin คือ **ตัวแปลงผังหน้าจอให้เป็นภาพที่คนดูรู้เรื่อง โดยที่ภาพนั้นยังผูกกับ spec อยู่ตลอด**

**Analogy:** เหมือนบ้านหนึ่งหลัง

- **Wireframe** คือแปลนบ้าน — ห้องอยู่ตรงไหน ประตูเปิดไปทางไหน มีหน้าต่างกี่บาน แปลนไม่บอกว่าผนังสีอะไร
- **Theme** คือแบบตกแต่ง — สี วัสดุ ฟอนต์ ระยะห่าง
- **Mockup** คือภาพเสมือนจริง = แปลน + แบบตกแต่ง

เหตุผลที่ต้องแยกสองชั้นนี้เด็ดขาด: **แปลนต้องตรงกับ spec ส่วนแบบตกแต่งเปลี่ยนได้ตลอด** ถ้าปนกันตั้งแต่แรก พอลูกค้าเปลี่ยนสีแบรนด์ จะต้องมานั่งตรวจใหม่หมดว่าฟิลด์ยังครบไหม

**หัวใจไม่ใช่ "ทำหน้าเว็บให้สวย" แต่คือ ภาพทุกภาพต้องตอบได้ว่ามาจาก requirement ข้อไหน และตอนนี้พัฒนากับทดสอบไปถึงไหนแล้ว**

## 1. เป้าหมาย และ Non-Goals

### 1.1 เป้าหมาย

| ID | เป้าหมาย | วัดผลอย่างไร |
|---|---|---|
| G1 | รับ handoff จากเครื่องมือออกแบบมาใช้ได้ | นำเข้าแล้วได้ token และ component inventory ที่ใช้ต่อได้ |
| G2 | ถ้าไม่มี handoff ต้องถามก่อน พร้อมเสนอ prompt ที่ใช้ได้จริง | prompt ที่เสนอมีรายละเอียดของโปรเจกต์นี้ ไม่ใช่ prompt ทั่วไป |
| G3 | สร้าง wireframe ตาม sitemap โดยไม่แตะเรื่องสไตล์ | wireframe ไม่มีค่าสี ฟอนต์ หรือขนาดฝังอยู่ |
| G4 | สร้าง HTML ตาม sitemap โดยใช้สไตล์จาก handoff หรือ theme | mockup อ้าง token เท่านั้น |
| G5 | ตรวจ sitemap แล้วเลือกสร้างเฉพาะหน้าที่ต้องการได้ | รายงานความครอบคลุมถูกต้อง |
| G6 | ตอบได้ว่าหน้าเว็บนี้มาจาก req อะไร design อะไร โค้ดไฟล์ไหน เทสตัวไหน | ตอบครบสี่ทางในคำตอบเดียว |
| G7 | ส่งต่อให้ dev โดยแยกชัดว่าอะไรบังคับ อะไรอ้างอิง | ชุดส่งมอบติดป้ายครบ |
| G8 | มีคำสั่งช่วยเหลือที่บอกลำดับการใช้งาน | ผู้ใช้ใหม่เริ่มได้โดยไม่ต้องอ่านสเปก |

### 1.2 Non-Goals

- ไม่กำหนดว่าหน้าจอต้องมีฟิลด์อะไร หรือใครเข้าถึงได้ — มาจาก design
- ไม่สร้าง design system หรือแบรนด์เอง — มาจาก handoff หรือ theme template
- ไม่เขียนโค้ดระบบจริง — mockup เป็นภาพอ้างอิง ไม่ใช่ของที่เอาไป production
- ไม่ทำ responsive ทุกขนาดหน้าจอโดยอัตโนมัติ (ดู MD4)
- ไม่ตัดสินว่าดีไซน์สวยหรือไม่สวย

## 2. ผู้เกี่ยวข้อง

| Actor | ต้องการอะไร |
|---|---|
| System Analyst / Designer (มนุษย์) | สั่งสร้าง เลือกหน้า ตรวจกับลูกค้า |
| ลูกค้า | เห็นภาพก่อนสร้างจริง เพื่อยืนยันว่าตรงกับที่ต้องการ |
| AI Agent (mockup) | รู้ว่าสร้างหน้าไหน ด้วย theme อะไร และผูก trace อย่างไร |
| AI Agent (dev) | รู้ว่าอะไรต้องทำตามเป๊ะ อะไรดูเป็นแนวทางได้ |
| AI Agent (qa) | รู้ว่าหน้านั้นต้องรองรับสถานะอะไรบ้าง เพื่อเอาไปทำเทส |

## 3. ตำแหน่งใน Marketplace

```
req ──▶ design ──▶ mockup ──▶ dev ──▶ qa ──▶ deliver
         ▲           │
         └── back-channel ──┘
```

### 3.1 Inbound Contract (mockup ← design)

| ต้องอ่านได้ | ใช้ทำอะไร | จำเป็น |
|---|---|---|
| ผังหน้าจอ (sitemap) | รู้ว่ามีหน้าอะไรบ้าง และโครงลำดับชั้น | บังคับ |
| รายละเอียดหน้าจอ — ฟิลด์ กฎตรวจสอบ action ปลายทาง | เนื้อในของ wireframe | บังคับ |
| ตารางสิทธิ์ | รู้ว่าหน้าไหนต้องมีสถานะ "ไม่มีสิทธิ์" และฟิลด์ไหนซ่อนจากบางบทบาท | บังคับ |
| รายการสถานะที่หน้านั้นต้องรองรับ | สร้างภาพของแต่ละสถานะ | บังคับ |
| ผังสถานะ | เข้าใจลำดับหน้าจอในกระบวนการ | ควรมี |
| trace ของ design | ต่อ edge ของตัวเอง | บังคับ |

**กติกาเหล็ก:** ถ้าหน้าจอใดยังไม่ผ่าน V5 ของ design (ขาดฟิลด์ ขาด action ขาดสิทธิ์ ขาดรายการสถานะ) **ต้องไม่สร้างหน้านั้น** ให้ส่งคำถามกลับผ่าน back-channel
ภาพที่สวยแต่สร้างจาก spec ที่ยังไม่ครบ จะถูกลูกค้าเข้าใจว่าตกลงกันแล้ว แล้วกลายเป็นข้อผูกมัด

### 3.2 Outbound Contract

| ผู้รับ | ต้องได้อะไร |
|---|---|
| `dev` | theme token, component inventory, mockup, รายการสถานะ, และแผนที่ SCR ↔ MCK ↔ REQ พร้อมป้าย บังคับ/อ้างอิง |
| `qa` | รายการสถานะที่แต่ละหน้าต้องรองรับ เพื่อใช้เป็นชุดทดสอบ UI |
| `design` | จุดที่ spec หน้าจอไม่ครบจนสร้างภาพไม่ได้ (back-channel) |

### 3.3 กติกาความเข้ากันได้

เหมือน plugin อื่นทุกประการ — `schemaVersion` ทุกไฟล์, เพิ่ม field ได้/ลบต้องขึ้น major, มี `extensions`, ทนต่อ field ที่ไม่รู้จัก

## 5. Artifact ที่ Mockup เป็นเจ้าของ

| Artifact | รูปแบบ | หน้าที่ |
|---|---|---|
| Theme | JSON | design token, component inventory, กติกาเลย์เอาต์ |
| Theme Decision Log | JSON | ผู้ใช้เลือกทางไหน เมื่อไร เพราะอะไร |

## 6. Theme และ Handoff

### 6.1 ลำดับการตัดสิน

เมื่อสั่งงานที่ต้องใช้สไตล์ ให้ไล่ตามลำดับนี้ **ห้ามข้ามขั้นไปสร้างสไตล์เอง**

1. **มี handoff จากเครื่องมือออกแบบอยู่แล้ว** → นำเข้า แปลงเป็น token แล้วใช้ต่อ
2. **ไม่มี handoff** → **ต้องถามผู้ใช้ก่อนเสมอ** ว่าจะไปสร้างด้วยเครื่องมือออกแบบก่อนไหม พร้อม **เสนอ prompt ที่พร้อมใช้** (ดู §6.2)
3. **ผู้ใช้ตอบว่าไม่ใช้** → ให้เลือก theme template ที่มีอยู่ หรือระบุแนวทางเองแบบสั้น ๆ
4. **ผู้ใช้ยังไม่ตัดสิน** → ทำได้แค่ระดับ wireframe เท่านั้น **ห้ามเดาสีเดาฟอนต์แล้วสร้าง HTML ไปก่อน**

ผลการตัดสินต้องบันทึกทันทีก่อนตอบผู้ใช้ (persist-before-answer) และห้ามถามซ้ำในรอบถัดไป

### 6.2 Prompt สำหรับสร้าง Theme ต้องประกอบจาก spec

นี่คือจุดที่ทำให้ข้อนี้มีค่ามากกว่าการเขียน prompt สำเร็จรูปแปะไว้

Prompt ที่เสนอ ต้องประกอบจากข้อมูลที่มีอยู่แล้วใน design artifact อย่างน้อย:

- ประเภทธุรกิจและกลุ่มผู้ใช้
- ลักษณะการใช้งานจริง เช่น ใช้บนเดสก์ท็อปทั้งวัน หรือใช้บนมือถือระหว่างเดินทาง
- **รายการส่วนประกอบที่ระบบนี้ต้องใช้จริง** ดึงจากหน้าจอทั้งหมด เช่น ตารางที่มีการกรองและแบ่งหน้า ฟอร์มหลายขั้นตอน ป้ายสถานะกี่สถานะ กล่องยืนยันการทำรายการ
- ข้อจำกัดที่รู้แล้ว เช่น ต้องรองรับภาษาไทย ต้องอ่านง่ายในที่แสงจ้า ต้องมีโหมดความคมชัดสูง
- สิ่งที่ต้องไม่ทำ

**ประโยชน์:** theme ที่กลับมาจะมีส่วนประกอบครบตามที่ระบบต้องใช้จริง ไม่ใช่ได้มาสวยแต่ไม่มีตารางแบบที่ต้องใช้ แล้วต้องมาเดาต่อเอง

### 6.3 การนำเข้า Handoff

สิ่งที่ต้องดึงออกมาและเก็บให้อ้างอิงได้:

- **Design token** — สี ตัวอักษร ระยะห่าง มุมโค้ง เงา และทุกสถานะการโต้ตอบ
- **Component inventory** — ส่วนประกอบที่ใช้ซ้ำได้ พร้อมสถานะของแต่ละตัว
- **กติกาเลย์เอาต์** — ระบบกริด ความกว้างสูงสุด จุดตัดขนาดหน้าจอ

**ต้องตรวจตอนนำเข้า**

| ตรวจอะไร | ทำไม |
|---|---|
| handoff ครอบคลุมส่วนประกอบที่ระบบต้องใช้ครบไหม | ถ้าขาด ต้องรู้ตอนนี้ ไม่ใช่ตอนสร้างหน้าที่ 20 |
| มีหน้าจอไหนใน sitemap ที่ handoff ไม่ครอบคลุม | ต้องรายงาน ไม่ใช่เงียบแล้วเดาเอง |
| มี component ใน handoff ที่ไม่มีหน้าจอไหนใช้เลย | อาจแปลว่า sitemap ขาดหน้าจอ หรือ handoff ทำเกิน |
| token ครบทุกสถานะไหม (ปกติ ชี้ค้าง กด ปิดใช้งาน ผิดพลาด) | ขาดสถานะไหน dev จะไปเดาเอง แล้วได้ไม่เหมือนกันทุกหน้า |

**เมื่อ handoff เปลี่ยน** ต้องทำเครื่องหมายว่า mockup ที่ใช้ theme เดิมล้าสมัย ด้วยกลไกเดียวกับที่ใช้เมื่อ requirement เปลี่ยน

## 7. Wireframe

### 7.1 ข้อบังคับ

- สร้างตาม sitemap เท่านั้น ไม่คิดหน้าใหม่เอง
- ทุกฟิลด์ ทุก action ที่ระบุในหน้าจอ ต้องปรากฏครบ
- **ห้ามมีค่าสไตล์ใด ๆ อยู่ในตัว** ไม่มีสี ไม่มีฟอนต์ ไม่มีขนาด ไม่มี CSS
- ต้องแสดงลำดับและการจัดกลุ่มของข้อมูลตามที่ spec ระบุ
- ต้องระบุได้ว่าส่วนไหนเห็นได้เฉพาะบทบาทใด

### 7.2 ทำไมต้องเข้มเรื่องนี้

wireframe คือของที่เอาไปตรวจกับลูกค้าว่า **ข้อมูลครบและลำดับถูก** ถ้ามีสไตล์ปนเข้ามา บทสนทนาจะเปลี่ยนจาก "ฟิลด์ครบไหม" เป็น "สีนี้ไม่สวย" ทันที แล้วเรื่องที่สำคัญกว่าจะไม่ถูกตรวจ

## 8. Mockup HTML

### 8.1 ข้อบังคับ

- สร้างจาก wireframe บวก theme เท่านั้น
- **ต้องอ้างค่าจาก token เท่านั้น ห้ามมีค่าสไตล์ที่ตั้งขึ้นเอง**
- ทุก component ที่ใช้ ต้องมีอยู่ใน component inventory
- ข้อมูลที่แสดงเป็นข้อมูลสมมติ และต้องระบุชัดว่าเป็นของสมมติ

### 8.2 สถานะที่ต้องทำ

design เป็นผู้ประกาศว่าหน้านั้นต้องรองรับสถานะอะไรบ้าง mockup มีหน้าที่ทำภาพของสถานะเหล่านั้น

รายการที่พบบ่อย:

- ยังไม่มีข้อมูล (ครั้งแรกที่เข้าใช้)
- กำลังโหลด
- โหลดไม่สำเร็จ
- ข้อมูลเยอะจนต้องแบ่งหน้า
- ข้อความยาวเกินที่ออกแบบไว้ — ทั้งชื่อคนไทยที่ยาวมากและชื่อบริษัทที่ยาวกว่า
- ผู้ใช้ที่ไม่มีสิทธิ์เห็นบางส่วนของหน้า
- ฟอร์มที่กรอกผิดหลายช่องพร้อมกัน
- สถานะระหว่างส่งข้อมูล (กันการกดซ้ำ)

**ข้อควรระวัง:** ถ้าทำแต่กรณีที่ทุกอย่างเรียบร้อย dev จะไม่รู้ว่าต้องทำสถานะพวกนี้ และ qa จะไม่มีอะไรเอาไปทดสอบ

## 9. ความครอบคลุมและการเลือกสร้างเป็นหน้า ๆ

### 9.1 ระดับความละเอียด

| ระดับ | ได้อะไร | ใช้ทำอะไร |
|---|---|---|
| L0 | มีชื่ออยู่ใน sitemap แต่ยังไม่ทำอะไร | ตรวจว่าหน้าครบไหม |
| L1 — Wireframe | โครงหน้า ฟิลด์ ปุ่ม ลำดับ ไม่มีสไตล์ | ตรวจกับลูกค้าว่าข้อมูลครบและลำดับถูก |
| L2 — Mockup | L1 + theme | ให้ลูกค้าเห็นภาพจริง และให้ dev อ้างอิง |

**ไม่ใช่ทุกหน้าต้องขึ้นถึง L2** หน้า CRUD ที่ซ้ำแบบเดียวกันสิบหน้า ทำ L2 หน้าเดียวเป็นตัวแทนก็พอ ที่เหลืออยู่ L1

### 9.2 สิ่งที่ระบบต้องทำได้

- ตรวจ sitemap แล้วรายงานว่าแต่ละหน้าอยู่ระดับไหน รวมถึงหน้าที่ยังไม่ได้ทำอะไรเลย
- เลือกสร้างเฉพาะหน้าที่ต้องการ — ระบุรายหน้า ทั้งโมดูล หรือตามความสำคัญ
- รายงานความครอบคลุม: จาก sitemap ทั้งหมดกี่หน้า ทำแล้วกี่หน้า ระดับไหนบ้าง
- ตรวจได้ว่ามีหน้าใน sitemap ที่เพิ่มเข้ามาใหม่แล้วยังไม่มีภาพ

## 10. Traceability — รู้ว่าหน้าเว็บนี้มาจากอะไร

### 10.1 Edge ที่ mockup เป็นเจ้าของ

```
SCR ──mockedBy──▶ MCK
MCK ──usesComponent──▶ COMPONENT (จาก theme)
MCK ──rendersState──▶ STATE
```

mockup **append edge ของตัวเองเท่านั้น** ห้ามแตะ edge ของ design, dev หรือ qa

### 10.2 คำถามสี่ทางที่ต้องตอบได้

นี่คือความสามารถที่โจทย์ระบุไว้โดยตรง — สำหรับหน้าเว็บหนึ่งหน้า ต้องตอบได้ว่า:

| ทาง | คำถาม | อ่านจาก |
|---|---|---|
| **req** | หน้านี้มาจากความต้องการข้อไหนของลูกค้า | trace ของ design ต่อขึ้นไปถึง REQ |
| **design** | หน้านี้มีฟิลด์อะไร กฎอะไร ใครเข้าถึงได้ อยู่ในกระบวนการไหน | screens, rbac, statemachines |
| **code** | หน้านี้พัฒนาแล้วหรือยัง อยู่ไฟล์ไหน | trace ของ dev (SRC) |
| **qa** | หน้านี้ทดสอบด้วยเทสตัวไหน ผลล่าสุดเป็นอย่างไร | trace ของ qa (TC + RUN) |

**ข้อสำคัญ:** mockup plugin **อ่าน** ข้อมูลของ dev และ qa เพื่อตอบคำถาม แต่ **ห้ามเขียน** ลงไฟล์ของสองตัวนั้น การรวมกราฟเกิดขึ้นตอนอ่าน (merged view) ไม่มีไฟล์กราฟรวมที่เขียนได้

ถ้ายังไม่มี dev หรือ qa ในโปรเจกต์ ต้องตอบว่า "ยังไม่มีข้อมูล" ไม่ใช่เดาหรือเงียบ

## 11. การส่งต่อให้ dev

**หลักการเดียวที่ต้องจำ: mockup เป็นภาพอ้างอิง ไม่ใช่ต้นฉบับของพฤติกรรม**

ถ้าไม่ประกาศให้ชัด สิ่งที่จะเกิดคือ dev ก๊อป HTML ไปแปะใน framework แล้วได้หน้าจอที่หน้าตาถูกแต่ไม่ผูกกับข้อมูลจริง ไม่มี validation ไม่มีการคุมสิทธิ์ และแก้ต่อไม่ได้

| สิ่งที่ส่งให้ | สถานะ | ความหมายสำหรับ dev |
|---|---|---|
| Design token | **บังคับ** | ห้ามตั้งค่าสีหรือระยะห่างเอง ต้องอ้าง token |
| Component inventory | **บังคับ** | ส่วนประกอบเดียวกันต้องใช้ตัวเดียวกันทุกหน้า |
| รายการสถานะที่หน้านั้นต้องรองรับ | **บังคับ** | เป็นรายการงาน ไม่ใช่ของเสริม |
| แผนที่ SCR ↔ MCK ↔ REQ | **บังคับ** | ใช้ผูก trace ต่อ ไม่ต้องมาไล่จับคู่เอง |
| โครงสร้าง HTML ของ mockup | **อ้างอิง** | ใช้ดูลำดับและการจัดวาง ไม่ต้องก๊อปมาตรง ๆ |
| ข้อความตัวอย่างและข้อมูลตัวอย่าง | **อ้างอิง** | เป็นของสมมติ ห้ามนำไปใช้เป็นค่าเริ่มต้นจริง |

> หมายเหตุ: รายการฟิลด์ กฎตรวจสอบ และสิทธิ์ เป็นของ **design** ไม่ใช่ของ mockup — dev ต้องอ่านจาก design โดยตรง mockup ไม่ทำซ้ำ (กฎ W3 อ้างอิง ไม่คัดลอก)

**สิ่งที่ต้องตัดสินตั้งแต่ต้น:** เมื่อ dev สร้างหน้าจอจริงแล้ว หน้าจอจริงกลายเป็นของจริง ส่วน mockup เริ่มล้าสมัย จะรักษาให้ทันตลอด หรือประกาศเลิกใช้เมื่อพัฒนาเสร็จ (ดู MD5)

### 12.1 ข้อกำหนดของ `/mock:help`

โจทย์ระบุให้มีคำสั่งช่วยเหลือโดยเฉพาะ จึงต้องระบุให้ชัดว่าต้องมีอะไร:

- ลำดับที่แนะนำ: `init` → `theme` → `wireframe` → `html` → `handoff`
- prerequisite ของแต่ละคำสั่ง และจะเกิดอะไรถ้าข้าม
- **สิ่งที่ plugin นี้ไม่ทำ และต้องไปใช้ตัวไหนแทน** — ข้อนี้สำคัญที่สุด เพราะผู้ใช้มักขอสิ่งที่เป็นของ design (เช่น "เพิ่มฟิลด์ในหน้านี้") แล้วถ้า plugin ทำให้ จะเกิดของจริงสองแหล่งทันที
- ตัวอย่างคำสั่งที่ใช้บ่อย
- สถานะปัจจุบันของโปรเจกต์แบบย่อ

## 17. ลำดับการสร้าง

**Milestone 1 — รู้ว่าต้องทำหน้าอะไร**
`init` → `coverage` → `wireframe`
*เป้าหมาย: พิสูจน์ว่าสร้างจาก sitemap เท่านั้น และ wireframe ไม่มีสไตล์ปน*

**Milestone 2 — เรื่อง theme**
`theme` → `html`
*เป้าหมาย: พิสูจน์ว่าไม่มี theme แล้วไม่เดา และ prompt ที่เสนอมาจาก spec จริง*

**Milestone 3 — เชื่อมกับคนอื่น**
`trace` → `sync` → `handoff`
*เป้าหมาย: พิสูจน์ว่าตอบคำถามสี่ทางได้ และส่งต่อโดยแยกบังคับ/อ้างอิง*

## 18. Acceptance Checklist

- [ ] สั่งสร้าง mockup โดยยังไม่มี handoff — ต้องถามก่อน และเสนอ prompt ที่มีรายละเอียดของโปรเจกต์นี้จริง ไม่ใช่ prompt ทั่วไป
- [ ] ยังไม่ตอบเรื่อง theme แล้วสั่งสร้างต่อ — ทำได้แค่ wireframe ไม่เดาสีเดาฟอนต์
- [ ] ดู wireframe ที่ได้ — ต้องไม่มีค่าสีหรือฟอนต์ฝังอยู่
- [ ] นำเข้า handoff ที่ขาด component ที่ระบบต้องใช้ — ต้องรายงานว่าขาดอะไร ไม่ใช่เดาเติม
- [ ] เลือกสร้างเฉพาะสามหน้าจากยี่สิบหน้า — ทำได้ และรายงานความครอบคลุมถูกต้อง
- [ ] เปลี่ยน handoff แล้วสั่งตรวจ — mockup เดิมถูกทำเครื่องหมายล้าสมัย
- [ ] ขอให้สร้างหน้าที่ไม่มีใน sitemap — ต้องปฏิเสธ
- [ ] ขอให้เพิ่มฟิลด์ในหน้าจอ — ต้องชี้ไปที่ design plugin ไม่ใช่ทำเอง
- [ ] หน้าจอที่ spec ยังไม่ครบ — ต้องไม่สร้าง และต้องส่งคำถามกลับ
- [ ] ถามว่าหน้านี้มาจาก req อะไร design อะไร โค้ดไฟล์ไหน เทสตัวไหน — ตอบครบสี่ทาง (หรือบอกว่ายังไม่มีข้อมูล)
- [ ] แก้ไฟล์ HTML ด้วยมือ แล้วสั่งสร้างใหม่ — ต้องไม่ทับงานที่แก้ไว้
- [ ] ดูชุดส่งมอบ — แยกชัดว่าอะไรบังคับ อะไรอ้างอิง
- [ ] สั่ง `help` — บอกลำดับการใช้งาน และบอกว่าอะไรไม่ใช่หน้าที่ของ plugin นี้

### 18.1 Cold Start Test

ปิดทุกอย่าง เปิดใหม่โดยมีแค่ไฟล์ในดิสก์ แล้วถาม

1. โปรเจกต์นี้ใช้ theme จากไหน ใครตัดสิน เมื่อไร
2. ทำภาพไปแล้วกี่หน้า ระดับไหนบ้าง เหลืออะไร
3. หน้านี้มาจาก requirement ข้อไหน และตอนนี้พัฒนากับทดสอบไปถึงไหน
4. มีภาพไหนที่ล้าสมัยเพราะ spec เปลี่ยน
5. มีคำถามอะไรค้างที่ต้องส่งกลับ design

## ภาคผนวก: อภิธานศัพท์

| คำ | ความหมาย |
|---|---|
| Handoff | ผลลัพธ์จากเครื่องมือออกแบบที่ส่งเข้ามาเป็นต้นทางของสไตล์ |
| Design token | ค่าพื้นฐานของสไตล์ที่อ้างอิงด้วยชื่อ ไม่ใช่ค่าดิบ |
| Component inventory | รายการส่วนประกอบที่ใช้ซ้ำได้ พร้อมสถานะของแต่ละตัว |
| Wireframe | โครงหน้าจอที่ไม่มีสไตล์ — ตรวจว่าข้อมูลครบและลำดับถูก |
| Mockup | wireframe ที่ใส่ theme แล้ว |
| Fidelity level | ระดับความละเอียดของหน้านั้น — L0 / L1 / L2 |
| บังคับ / อ้างอิง | ป้ายในชุดส่งมอบ ว่าสิ่งใดต้องทำตามเป๊ะ สิ่งใดดูเป็นแนวทางได้ |
| Merged view | กราฟที่รวมจากหลาย plugin ตอนอ่าน ไม่มีอยู่จริงบนดิสก์ |
