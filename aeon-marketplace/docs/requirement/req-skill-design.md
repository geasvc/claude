### 2.1 `/req:calc <BR-id>` — Calculation Contract (ขั้น 6)

**ทำไมต้องแยกเป็นคำสั่ง ไม่ยัดเข้า `/req:ask`:** question bank ตอนนี้มีหมวด `calculation` อยู่ **คำถามเดียว**
ขณะที่ขั้น 6 ต้องการคำตอบอย่างน้อย 6 อย่างที่**ไม่ใช่ multiple choice ทั้งหมด** และผูกกับกฎแบบ 1:1
ยิงทีละ 3 ข้อแบบ `/req:ask` ตอบไม่ครบสัญญา

โหนดใหม่ `CALC-xxx` ผูกกับ `BR-xxx@vN` (`constrains`) เก็บ:

| field | ตัวอย่างจาก MiniLoan (BR-06) | กับดักถ้าไม่มี |
|---|---|---|
| `formula` | `EMI = P × r × (1+r)^n / ((1+r)^n − 1)` verbatim | ต่างคนต่างจำสูตร |
| `inputs[]` | `P: money(2)`, `r: rate(10)`, `n: int` | ปนชนิดข้อมูล |
| `numeric_type` | `decimal` — **ห้าม float** | เงินเพี้ยนสตางค์ |
| `rounding_mode` | `HALF_UP` | ต่างภาษาต่าง default |
| `rounding_points` | ปัดที่**ผลลัพธ์แต่ละงวด** ไม่ใช่ปัดตอนท้าย | ผลต่างกันหลักบาท |
| `residual_policy` | งวดสุดท้ายรับเศษ ให้ยอดคงเหลือ = 0 | ยอดค้าง 0.03 บาทตลอดกาล |
| `boundary_behavior` | `n = 0`, `r = 0`, `P` ต่ำสุด | หารด้วยศูนย์ |

ทุก field ที่ตอบว่า "ยังไม่แน่ใจ" → `Q-xxx` **การ์ดแดง** ตามกลไกเดิม
สิ่งที่ต้องเห็น entity ก่อน (เช่น `decimal(p,s)` เท่าไหร่) → `DQ-xxx` **คิวส่งต่อ** ไม่บล็อก CP1 — กติกาเดิมไม่เปลี่ยน

### 2.2 `/req:golden <BR-id|CALC-id>` — Golden Test Data (ขั้น 9)

**นี่คือคำสั่งที่มีมูลค่าสูงสุดที่เพิ่มเข้ามา** และเป็นคำสั่งเดียวในชุดที่เป็นชนิด **Verify**

หลักที่ห้ามละเมิด — สไลด์ยกตัวอย่าง EMI งวดสุดท้าย 9,504.**43** ที่ "เพิ่งรู้ตอนกดเลข":

1. **โมเดลห้ามคิดเลขในหัว** ต้อง**รันโค้ด**คำนวณ แล้วแสดงทั้งสคริปต์และผล
   (เก็บสคริปต์ไว้ที่ `<state-dir>/golden/<CALC-id>.mjs` — รันซ้ำได้ ไม่ใช่ผลลอย ๆ · `<state-dir>` มาจาก `state-dir.mjs` **ห้ามพิมพ์ `.aeon` ตรง ๆ**)
2. **คนยืนยันตัวเลข** ผลจากสคริปต์ยังเป็นแค่ข้อเสนอ จนกว่าเจ้าของจะเซ็น → `verified_by` + `verified_at`
3. **ถ้าเลขไม่ลงตัว → ย้อนกลับขั้น 6** (Loop L2 ในสไลด์ 3) ไม่ใช่แก้ตัวเลขให้สวย
4. ถ้ามี **ข้อมูลตัวอย่างจากลูกค้า** (`SRC` kind `sample_data`) ให้ใช้เป็น input ตั้งต้น
   แล้ว **diff ผลของเรากับผลของลูกค้า** — ตรงนี้คือจุดที่กฎที่หายไปโผล่บ่อยที่สุด

โหนดใหม่ `GD-xxx` (golden dataset): `proves` → BR/CALC · `rows[]` (input → expected) · `computed_by` (path สคริปต์) · `verified_by` · `source` (ถ้ามาจาก sample data)

## 3. การเก็บข้อมูลจากลูกค้า — 5 ชนิด input

ทุกชนิดเข้าประตูเดียว `/req:capture` · **1 input = 1 `SRC-xxx`** · ทุกไฟล์ต้องลงดินใต้ `docs/` (check #8)

> input ทุกชนิดในตารางนี้เป็น "ของที่เปลี่ยนกฎเดิม" ได้ทั้งหมด ไม่ใช่แค่ "ของใหม่" —
> capture จึงต้องตัดสินให้ได้ก่อนเขียนว่าอันไหนใหม่ อันไหนเปลี่ยน **ดู §7.7**

| ชนิด input | SRC kind | ไปที่ field ไหน | ต้องระวัง |
|---|---|---|---|
| **สัมภาษณ์ / ข้อความพิมพ์** | `chat` | `extracted.text` | ใส่ `spoken_by` + `spoken_at` — คำพูดคนละคนคนละวันขัดกันได้ ต้อง trace ว่าใครพูด |
| **PDF (text layer)** | `file` | `extracted.text` + `pages` | locator ต้องเป็นหน้า/มาตรา ไม่ใช่ชื่อไฟล์ |
| **PDF (สแกน) / รูปภาพ / สกรีนช็อตแชท** | `image` | `interpretation.transcript` | ⚠️ **ห้ามลง `extracted` เด็ดขาด** — โมเดลอ่าน = เดา จนกว่าจะยืนยัน |
| **Word `.docx`** | `file` | `extracted.text` + `pages` | หัวข้อมีเลขมาตรา → เอาไปเป็น locator ได้ดี |
| **Excel `.xlsx`** | `file` | `extracted.sheets[].cells[]` **`formula` + `value`** | 🔥 **หลอกที่สุด** — เซลล์โชว์ `930` แต่สูตรคือ `=IF(B2>1000,B2*0.93,B2)` = กฎ *"เกิน 1,000 ลด 7%"* |
| **ข้อมูลตัวอย่างจากลูกค้า** | `sample_data` 🆕 | `extracted.rows[]` + `schema[]` | 🆕 **ไม่ใช่แหล่งของกฎ แต่เป็นหลักฐานของขั้น 9** |

> `source.kind` ปัจจุบัน enum เป็น `chat | file | image | url` (มี `url` ที่ตารางข้างบนไม่ได้พูดถึง — ใช้กับลิงก์ที่ไม่ได้โหลดมาเป็นไฟล์)
> **การเพิ่ม `sample_data` = แก้ enum ใน schema** ไม่ใช่แค่ใส่ค่าใหม่ลงไฟล์ — `additionalProperties: false` และ enum จะทำให้ ajv ตีกลับทันที

### 3.1 ทำไม `sample_data` ต้องเป็น kind แยก

เพราะมันตอบคนละคำถาม และ**ถ้าปนกันจะพังเงียบ**:

| | เอกสาร/รูป/แชท | ข้อมูลตัวอย่าง |
|---|---|---|
| ตอบคำถาม | "กฎคืออะไร" | "**ค่าที่ถูกต้องคือเท่าไหร่**" |
| ป้อนให้ | `BR-xxx` (ขั้น 5) | `GD-xxx` (ขั้น 9) |
| ถ้าอ่านผิดชนิด | — | เอาข้อมูลจริง 500 แถวไป**เดากฎ** → ได้กฎที่อธิบายข้อมูลชุดนั้นชุดเดียว |

ห้ามสรุปกฎจาก sample data โดยตรง — ทำได้แค่ **ตั้งข้อสงสัย** แล้วส่งเข้ารอบยืนยัน
เช่น *"ในไฟล์นี้ 47 แถวจาก 500 มียอดเกิน 1,000 แล้วลด 7% ทั้งหมด — ยืนยันว่าเป็นกฎไหม หรือบังเอิญ"*
(ตัวเลือกที่ 3 ยังคงเป็น "ยังไม่แน่ใจ ต้องถามลูกค้า" → การ์ดแดง)

**PII:** sample data จากลูกค้ามักมีข้อมูลจริง — ก่อน commit ต้องเสนอ mask และบันทึก `masked: true/false`
กติกาเดิมที่ว่า `docs/` อยู่ใต้ git ทำให้ข้อมูลจริงตกลง history ถาวร นี่คือจุดที่ต้องถามก่อน ไม่ใช่หลัง

## 4. Question bank — ปรับเป็น 2 ชั้น

## 5. รูปแบบเอกสาร — LLMWIKI + OKF

### 5.1 การตัดสินใจหลัก: `spec.json` ยังเป็นความจริง

**wiki เป็น render ตัวที่สาม ไม่ใช่ที่เก็บความจริงตัวที่สอง**

เหตุผลไม่ได้มาจากรสนิยม แต่มาจาก doctrine ที่เขียนไว้แล้วใน `SKILL.md` v0.2.0:
> *"`deliver`'s Word SRS is **another render of the same data**, not a second document.
> **Never build a second extraction path.**"*

```
                       ┌──→ docs/requirements/REQ-xxx.md   (ไทย · ให้คนอ่าน)      ← มีแล้ว
<state-dir>/           │
  spec.json  ──────────┼──→ docs/wiki/**                   (OKF · ให้ agent อ่าน)  ← ใหม่
  (ความจริง)             │
                       └──→ SRS .docx                      (ส่งลูกค้า)             ← phase deliver
```

และตรงนี้เข้าทาง OKF พอดี — สเปกโฆษณาตัวเองว่า **producer/consumer independence**: bundle ที่ generate ทั้งก้อนคือของที่ conformant โดยธรรมชาติ ไม่ใช่ของแปลก

**ผลที่ตามมาที่ต้องยอมรับ:** ห้ามแก้ไฟล์ใน `docs/wiki/` ด้วยมือ เหมือนที่ห้ามแก้ `REQ-xxx.md`
อยากแก้ข้อความ → แก้ `narrative` ใน `spec.json` แล้ว regenerate
และ**ห้ามใช้ marker block แบบ "แก้ในนี้ได้"** — v0.2.0 ห้ามไว้เพราะเคยมีคนแก้นอก marker แล้ว regenerate กินทิ้งเงียบ ๆ

### 6.1 ทำไมเป็น check #12 ใหม่ ไม่ใช่ขยาย #10

อ่านโค้ดจริงแล้วชัด — `doc-hash.mjs` คำนวณ **hash ต่อ REQ** ครอบ `{requirement, glossary, rules, examples}`
คือ granularity ของ `REQ-xxx.md` หนึ่งไฟล์ต่อหนึ่ง requirement

แต่ wiki bundle เป็น **หนึ่งไฟล์ต่อหนึ่งโหนด** — hash ระดับ REQ ตอบไม่ได้ว่าไฟล์ `BR-loan-006@v2.md` ไฟล์เดียว stale ไหม
จึงต้องเพิ่ม export ตัวใหม่ในไฟล์เดิม (**ห้ามเขียน hash ขึ้นเองที่อื่น** — กติกาข้อนี้เข้มที่สุดในระบบ):

```js
// scripts/doc-hash.mjs — เพิ่ม ห้ามแก้ reqDocHash ของเดิม
export function nodeDocHash(spec, node) { … }   // hash ต่อโหนด สำหรับหน้าใน wiki
```

#### ขอบเขตของ hash ต้องเท่ากับ "ทุกอย่างที่หน้านั้น render"

นี่คือจุดที่พลาดง่ายที่สุดและพลาดแล้วเงียบสนิท `reqDocHash` เดิม**ไม่ได้** hash แค่โหนด REQ
มันครอบ closure ทั้งก้อน (`requirement` → `glossary` → `rules` → `examples`) ตามคอมเมนต์ในไฟล์เองว่า
*"everything the generated document renders"* — `nodeDocHash` ต้องใช้หลักเดียวกัน ไม่ใช่ hash โหนดเปล่า

**ถ้า hash แค่โหนดเปล่าจะเกิดอะไร:** หน้า `BR-loan-006@v2.md` ใน §5.4 render คำพูดจากแหล่ง
(*"ดอกเบี้ยลดต้นลดดอก 25% ต่อปี"*) ด้วย วันหนึ่งแหล่งนั้นถูกแก้เป็น `corrected` พร้อม `corrected_to`
→ ข้อความบนหน้าผิดทันที แต่โหนดกฎไม่ขยับ → **check #12 ยังเขียว** = ความผิดพลาดชนิดเดียวกับที่ #10 มีไว้กัน

| `type` | closure ที่ต้องเข้า hash |
|---|---|
| `Business Rule` | โหนดกฎ + CALC ที่ผูก + EX ที่พิสูจน์ + GD ที่ผูก + `quote`/`validation` ของทุก provenance source + สตับเวอร์ชันที่ถูกแทน |
| `Calculation Contract` | โหนด + กฎที่ `constrains` + provenance |
| `Example` | โหนด + id/ข้อความกฎที่ `proves` |
| `Golden Dataset` | โหนด + rows + `verified_by/at` + BR/CALC ที่พิสูจน์ + SRC ต้นทาง |
| `Requirement` | เหมือน `reqDocHash` เดิม (เรียกซ้ำได้เลย) |
| `Glossary Term` · `Question` · `NFR` · `Source` | โหนดตัวเอง + id ของโหนดที่อ้างถึงบนหน้า |

> **ทางลัดที่ห้ามใช้:** hash เนื้อไฟล์ `.md` ที่ render ออกมาแทน — แบบนั้นพิสูจน์ได้แค่ว่าไฟล์ไม่ถูกแก้มือ
> แต่พิสูจน์ไม่ได้เลยว่ามันยัง**ตรงกับ `spec.json`** ซึ่งคือเหตุผลทั้งหมดที่กลไก #10 มีอยู่

#### check #12 ตรวจ 7 ข้อ — 5 ข้อร่วมกับด่าน authoring + 2 ข้อเฉพาะตัว

(ง)(ฉ) เป็น error ระดับเดียวกับ #10 เพราะเป็นความผิดพลาดชนิดเดียวกันเป๊ะ — เอกสาร generate แล้วค้าง
(ช) จำเป็นเพราะ (ฉ) ตรวจทางเดียว: ลบกฎทิ้งหรือเปลี่ยนชื่อ id แล้วหน้าเก่าจะค้างอยู่แบบเขียวตลอดไป
— LLMWIKI เรียก operation นี้ว่า **lint** และระบุ orphaned page เป็นเป้าหมายไว้เองอยู่แล้ว

> **ถ้าไม่มี (ก)(ข)(ค) จะเกิดอะไร:** หน้าที่เขียน `type: Bogus` หรือ id ผิดรูปแบบ **ผ่านฉลุย**
> เพราะ (ง) ตรวจแค่ว่า hash ตรง และ hash คำนวณจาก `spec.json` ไม่ได้คำนวณจาก frontmatter
> bundle ที่เครื่องมือ OKF ตัวอื่นอ่านไม่ออก จะยังเขียวในด่านของตัวเอง

> **ทางเลือก trigger ของ #13 ที่ต้องใช้ให้ถูก:** `test_design` เป็น **array** และ enum ของมันคือ
> `EP | BVA | decision_table | state_transition | pairwise` — **ไม่มีค่า `calculation`**
> ตัวที่ใช่คือ `kind` ซึ่ง enum เป็น `invariant | policy | calculation | constraint` อยู่แล้ว
> แปลว่า #13 **ใช้ของที่มีใน schema ปัจจุบันได้เลย ไม่ต้องเพิ่ม enum**

> **กันงูกินหาง:** closure คำนวณจาก **data ของโหนดอื่น** ไม่ใช่จาก **hash ของโหนดอื่น**
> หน้ากฎรวม data ของ `CHG` ที่อ้างถึงมัน และหน้า `CHG` ก็รวม data ของกฎ — ถ้าเผลอเขียนเป็น
> `hash(BR) = f(…, hash(CHG))` จะ recurse ไม่รู้จบ · ตัด dependency ที่ระดับ data เท่านั้น

### 6.2 ทำไม #13 เป็น warn ก่อน

ใช้บรรทัดฐานเดียวกัน: ตั้งเป็น warn รอบแรก ถ้าใช้จริงแล้วเจอว่าเลขหลุดจริง ค่อยเลื่อนเป็น error

## 7. Requirement เปลี่ยน — เก็บเวอร์ชันยังไง

### 7.1 ของที่มีอยู่แล้ว (อ่านจากโค้ดจริง ไม่ใช่จากเอกสาร)

**ชั้นข้อมูลรองรับดีมาก แต่เฉพาะ `BR` เท่านั้น** — และตัวตรวจบังคับจริง ไม่ได้เป็นแค่ convention:

```jsonc
{ "id": "BR-job-011@v2",  "base_id": "BR-job-011",  "version": 2,
  "is_current": true,     "status": "draft",
  "supersedes": "BR-job-011@v1",  "superseded_by": null,  "superseded_at": null,
  "change_reason": "TOR §3.5 ระบุชัดว่าต้องอนุมัติ — คำบอกเล่าตอนแรกหลวมกว่าเอกสาร",
  "traces_down": { "features": [], "test_cases": [] } }
```

| กติกา | บังคับโดย | ทำอะไร |
|---|---|---|
| ทุกเวอร์ชันเป็น**โหนดแยก** ไม่ใช่ array ซ้อน | schema | ของเก่าไม่ถูกทับ ยังชี้ถึงได้ตลอดไป |
| `version > 1` ต้องมี `supersedes` **และ `change_reason`** | check #6 | ข้อความ error เขียนตรง ๆ ว่า *"cannot answer why the rule changed"* — เปลี่ยนกฎโดยไม่บอกเหตุผล = ตัวตรวจแดง |
| `supersedes` / `superseded_by` ต้องชี้กลับหากัน | check #6 | สายโซ่ขาดไม่ได้ |
| `status: superseded` ↔ มี `superseded_by` | check #6 | สถานะโกหกไม่ได้ |
| id ต้องมี `@v` เสมอ · อ้างอิงแบบ id เปล่า = **error** | check #7 | *"a bare rule id silently re-points when current moves"* |
| **หนึ่ง base_id มี `is_current` ได้ตัวเดียว** | check #7 | ไม่มีวันมี "กฎปัจจุบัน" สองตัว |
| `rule_coverage` นับเฉพาะ `is_current` | `rollup.mjs` | เวอร์ชันเก่าไม่ถ่วงตัวหาร |

`traces_down: {features, test_cases}` มีช่องรอไว้แล้ว = โครงของ impact analysis ที่ยังไม่มีใครเติม

> **schema จองที่ให้ `/req:change` ไว้แล้ว** — คำอธิบายของ `status` เขียนตรงตัวว่า
> *"`locked` is only escapable via `/req:change`; `superseded` is terminal."*
> แปลว่าตอนนี้ `spec.json` มีสถานะที่**ออกไม่ได้ด้วยเครื่องมือที่มีอยู่จริง** — คำสั่งที่หายไปไม่ใช่ของเสริม แต่เป็นทางออกเดียวที่ออกแบบไว้

### 7.2 ช่องว่างจริง 6 ข้อ

| # | ขาดอะไร | ผลตอนใช้จริง |
|---|---|---|
| 1 | **ไม่มีคำสั่ง `/req:change`** | v0.2.0 บอกให้ *"report and stop"* เมื่อ input ใหม่ขัดกับโหนด `locked`/`superseded` — คือหยุดเฉย ๆ ต้องไปแก้ `spec.json` มือ ซึ่งเป็นทางที่ผิด @v กันได้ง่ายที่สุด |
| 2 | **มีเวอร์ชันเฉพาะ `BR`** | `REQ` / `EX` / `UL` / `CALC` มีแค่ `status` enum (`draft`/`validated`/`locked`/`superseded`) ไม่มี `base_id`/`version`/`supersedes` |
| 3 | **ไม่มีไทม์ไลน์การเปลี่ยนแปลง** | ตอบได้ว่ากฎข้อนี้เปลี่ยนเพราะอะไร · ตอบ**ไม่ได้**ว่า *"รอบวันที่ 13 ส.ค. แก้อะไรไปบ้าง ใครสั่ง มาจากเอกสารไหน"* ซึ่งเป็นคำถามที่ลูกค้าถามจริง |
| 4 | **ไม่มี `effective_from`** | มีแต่ `superseded_at` · ตอบ *"ตอนใบสมัครใบนี้ถูกสร้าง กฎคือเวอร์ชันไหน"* ได้ทางเดียวคือดูว่า feature ชี้ `@v` ไหนไว้ ตอบด้วยวันที่ไม่ได้ · **ปิดช่องนี้ต้องใส่ `effective_from` ลงบนตัวโหนดเวอร์ชันเอง** ไม่ใช่พึ่ง `CHG` — เพราะ check #14 เป็น warn การเดินย้อน CHG→โหนดจึงไม่การันตี |
| 5 | **`/req:impact` / `/req:lock` ยังไม่มี** | `impact` ต้องรอ `traces_down` จาก phase ที่ยังไม่มี — เป็นข้อจำกัดที่รู้ตัวอยู่แล้ว |
| 6 | **ตัวอย่างข้ามเวอร์ชันไม่มีกติกา** | ในฟิกซ์เจอร์ `EX-job-021` `proves: ["BR-job-011@v1","BR-job-011@v2"]` — ตัวอย่างเดียวพิสูจน์กฎสองเวอร์ชันที่**เนื้อหาขัดกัน** ("แก้ได้เลย" vs "ต้องอนุมัติก่อน") ไม่มีที่ไหนเขียนว่าเมื่อไหร่ทำแบบนี้ได้ |

> ข้อ 6 อันตรายที่สุดเพราะมันยัง**เขียว** — ไม่มี check ไหนถามว่าตัวอย่างที่ยกมายังพิสูจน์ข้อความใหม่ได้จริงไหม
> กฎขึ้นเวอร์ชันใหม่แล้วยืมตัวอย่างเก่ามาใช้ = coverage สวยแต่ไม่มีอะไรถูกพิสูจน์

### 7.3 ข้อเสนอ — คำสั่งที่ 8 + concept ใหม่ 1 ตัว

**`/req:change <BR-id|CALC-id>`** — ขยับกฎขึ้นเวอร์ชันอย่างถูกกติกา

1. อ่านโหนดปัจจุบัน แสดงข้อความเดิม vs ที่จะเป็น
2. **บังคับกรอก `change_reason`** — ไม่กรอกไม่ให้ไปต่อ (check #6 จะแดงอยู่ดี ดักตั้งแต่ตอนถามดีกว่า)
3. สร้าง `@v(n+1)` · เซ็ต `is_current` ย้ายข้าง · ปิดสายโซ่ทั้งสองทาง · ลง `superseded_at` **และ `effective_from` บนโหนดใหม่** (ปิดช่องว่าง 7.2 ข้อ 4 ตรง ๆ ไม่ผ่าน `CHG`)
4. **ถามเรื่องตัวอย่างทีละตัว** (ปิดช่องว่าง 7.2 ข้อ 6):
   > `EX-job-021` พิสูจน์ `@v1` ว่า "แก้ได้เลย" · ข้อความใหม่คือ "ต้องอนุมัติก่อน"
   > 1) ยังพิสูจน์ได้ → ยก `proves` มาที่ `@v2` ด้วย   2) พิสูจน์ไม่ได้แล้ว → คงไว้ที่ `@v1` เท่านั้น (กฎใหม่กลับไปมีตัวอย่าง 0 → **coverage ตก ซึ่งถูกต้อง**)   3) ยังไม่แน่ใจ → 🛑 การ์ดแดง
5. เตือนสิ่งที่กระทบ: `CALC` ที่ผูก · `GD` ที่คำนวณจากกฎเดิม (**ต้องรัน `/req:golden` ใหม่**) · `traces_down` ถ้ามี
6. สร้างโหนด `CHG-xxx` (ข้างล่าง) → regenerate → 🛑 หยุด

**`CHG-xxx` — change set เป็น concept ชั้นหนึ่ง** ปิดช่องว่าง 7.2 ข้อ 3

```jsonc
{ "id": "CHG-loan-004",
  "at": "2026-08-13T14:05+07:00",
  "requested_by": "ลูกค้า (คุณเอ) ทางไลน์",
  "approved_by": "user",
  "triggered_by": ["SRC-009"],                      // ประชุม/เอกสารที่ทำให้เปลี่ยน
  "reason": "ธปท. ปรับเพดานดอกเบี้ย ต้องลด 25% → 23%",
  "affects": ["BR-loan-004@v2", "CALC-loan-002@v2"],
  "invalidates": ["GD-loan-003"],                   // เลขเฉลยที่ต้องคำนวณใหม่
  "effective_from": "2026-09-01" }
```

ทำไมต้องเป็นโหนดแยก ไม่ใช่แค่บรรทัดใน log: เพราะ **การเปลี่ยนหนึ่งครั้งกระทบหลายโหนด** เปลี่ยนดอกเบี้ยทีเดียวขยับทั้ง BR + CALC + ทำให้ GD ตาย — ถ้าเก็บเหตุผลไว้ในแต่ละโหนด (`change_reason`) มันจะถูกก๊อปซ้ำ 3 ที่และไม่มีใครรู้ว่าเป็นเรื่องเดียวกัน

### 7.4 กติกาหนึ่งบรรทัด: version เฉพาะโหนดที่มีคนชี้แบบล็อกเวอร์ชัน

ไม่ต้องขยาย versioning ไปทุกโหนด — ตัดสินด้วยเกณฑ์เดียว **"มีของข้างล่างชี้มาแบบ `@v` ไหม"**

| โหนด | version? | เหตุผล |
|---|---|---|
| `BR` | ✅ (มีแล้ว) | feature / test ชี้ `@v` — นี่คือเหตุผลที่ทั้งระบบมี versioning |
| `CALC` 🆕 | ✅ **ต้องเพิ่ม** | เปลี่ยนวิธีปัดเศษ = เปลี่ยนสัญญา ตัวเลขที่คำนวณไว้แล้วผิดหมด · **ตัวเลขที่ผลิตออกไปแล้วยังต้องอธิบายได้ว่าใช้สัญญาเวอร์ชันไหน** |
| `GD` | ❌ | ผูกกับ CALC@v อยู่แล้ว · CALC ขยับ → GD เก่า `invalidated` ไม่ใช่ขึ้นเวอร์ชัน |
| `EX` | ❌ | ตัวอย่างเกิดมาเพื่อพิสูจน์กฎเวอร์ชันหนึ่ง · กฎเปลี่ยน = เขียนตัวอย่างใหม่ ไม่ใช่แก้ของเดิม |
| `REQ` · `UL` | ❌ | ไม่มีใครชี้ `REQ@v` เพื่อ build · ประวัติเก็บที่ `CHG` timeline พอ |
| `SRC` | ❌ | ต้นฉบับแก้ไม่ได้อยู่แล้ว — เอกสารใหม่ = `SRC` ใหม่ (check #8 จับ hash เปลี่ยนอยู่แล้ว) |

### 7.5 หน้าตาใน OKF

versioning เข้ากับ OKF ได้ตรง ๆ เพราะ **path = identity** และไฟล์เก่าไม่เคยถูกทับ:

> ⚠️ **แผนผังข้างล่างแสดงเฉพาะส่วนที่เกี่ยวกับเวอร์ชัน ไม่ใช่โครงเต็ม** — โครงเต็มดู **§5.3**
> (ที่นี่ไม่ได้แสดง `examples/` `glossary/` `questions/` `nfr/` `sources/` ซึ่งต้องมีเหมือนกัน)

```
docs/wiki/
├── log.md                        # ไทม์ไลน์แบน ๆ ทุกครั้งที่เขียน
├── changes/                      # 🆕 concept ใหม่
│   ├── index.md                  #   ตารางรวม: เมื่อไหร่ · ใคร · กระทบอะไร
│   └── CHG-loan-004.md
├── rules/
│   ├── index.md                  #   base → current (ตัวเดียวที่บอกว่าอันไหน current)
│   ├── BR-loan-004@v1.md         #   ❄️ แช่แข็ง ห้ามลบ
│   └── BR-loan-004@v2.md
└── calculations/
    ├── CALC-loan-002@v1.md
    └── CALC-loan-002@v2.md
```

หน้า `CHG-loan-004.md`:

```markdown

title: ปรับเพดานดอกเบี้ย 25% → 23%

requested_by: ลูกค้า (คุณเอ) ทางไลน์
approved_by: user
effective_from: 2026-09-01
affects: [BR-loan-004@v2, CALC-loan-002@v2]
invalidates: [GD-loan-003]
triggered_by: [SRC-009]
spec_hash: sha256:…
---

## เปลี่ยนอะไร
| โหนด | จาก | เป็น |
|---|---|---|

## ต้องทำต่อ

> เปิดบน GitHub / Obsidian / editor อะไรก็เดินสายโซ่ย้อนหลังได้ทันที และ agent ตัวไหนก็อ่านออก

### 7.6 ตัวตรวจเพิ่ม

| # | check | gate | ระดับ |
|---|---|---|---|
| 6 | *(ขยายของเดิม)* กติกา `supersedes`/`change_reason` ครอบ `CALC` ด้วย | ALL | ❌ error |
| **14** | **change-set integrity** — ทุกโหนดที่ `superseded` ต้องมี `CHG` อ้างถึง · ทุก `CHG` ชี้โหนดที่มีจริง · มี `approved_by` · `invalidates` ที่ยังไม่ถูกสร้างใหม่ถูกรายงาน | CP1 | ⚠️ **warn ก่อน** |

`nodeDocHash` closure ต้องรวม field เวอร์ชัน (`supersedes`/`superseded_by`/`change_reason`) และ `CHG` ที่อ้างถึงโหนดนั้นด้วย — ไม่งั้นแก้เหตุผลการเปลี่ยนแล้วหน้ายัง stale แบบเขียว (เหตุผลเดียวกับ §6.1)

### 7.7 `/req:capture` ต้องตรวจเองว่า "นี่คือของใหม่ หรือของที่เปลี่ยน"

#### รูโหว่วันนี้

`commands/capture.md` เขียนไว้ข้อเดียวว่า:

> *"**Never modify a `locked` or `superseded` node** — if the input contradicts one, that is a
> `/req:change` situation: report it and stop."*

**ครอบแค่ `locked` กับ `superseded`** — แต่กฎส่วนใหญ่ในชีวิตจริงเป็น `draft` หรือ `validated`
ถ้า input ใหม่ขัดกับกฎที่เป็น `draft` **ไม่มีบรรทัดไหนบอกให้ทำอะไรเลย** และพฤติกรรมโดยปริยายของ capture คือ *"ร่างกฎใหม่จาก input"*

**ผลที่ได้คือความพังแบบเงียบที่สุดในระบบ:**

```
BR-loan-004@v1  "ดอกเบี้ย 25% ต่อปี"          is_current ✅ มีตัวอย่าง 2 ตัว
BR-loan-009@v1  "ดอกเบี้ย 23% ต่อปี"          is_current ✅ มีตัวอย่าง 2 ตัว   ← capture ร่างใหม่จากไลน์ที่ลูกค้าส่งมา
```

ตัวตรวจ **เขียวหมดทุกข้อ** — คนละ `base_id` กัน check #7 จึงไม่มีอะไรให้ค้าน · coverage 100% · ไม่มีการ์ดแดง
แต่ระบบมีกฎสองข้อที่ขัดกันเอง และไม่มีใครรู้ว่าข้อไหนคือของจริง จนกว่าจะเขียนโค้ดไปแล้ว
**เวอร์ชันที่ควรจะเป็น `@v2` กลายเป็นกฎคนละข้อ** — และ versioning ทั้งระบบใน §7.1 ถูกข้ามหัวไปเฉย ๆ

#### ตัดสิน 4 ทางต่อกฎที่ร่างได้หนึ่งข้อ

ก่อนจะเขียนอะไรลง `spec.json` ทุกกฎที่ร่างได้จาก input ต้องถูกตัดสินว่าเป็นอะไรใน 4 อย่างนี้

| ผล | แปลว่า | capture ทำอะไร |
|---|---|---|
| 🆕 **NEW** | ไม่ชนกับกฎไหนที่มีอยู่ | ร่างเป็น `BR-xxx@v1` ตามปกติ |
| ♻️ **SAME** | พูดเรื่องเดิม ความหมายเดิม | **ไม่สร้างกฎใหม่** — เพิ่มแค่ `provenance` ให้กฎเดิม (แหล่งที่สองยืนยันกฎเดียวกัน = ของดี ไม่ใช่ของซ้ำ) · ⚠️ **แต่ถ้า REQ นั้นมีรายการ CHANGED อยู่ด้วย ให้ค้างไว้** — ดูกติกาแช่แข็ง |
| ⚠️ **CHANGED** | ขัดกับกฎที่ `is_current` อยู่ | 🛑 **หยุด แจ้ง ถาม — ห้ามเขียน ห้าม regenerate** |
| ❓ **UNSURE** | บอกไม่ได้ว่า refine หรือ contradict | 🛑 หยุดเหมือนกัน · ตอบ "ยังไม่แน่ใจ" → การ์ดแดง `Q-xxx` |

> **UNSURE ต้องมีเป็นทางเลือกที่ 4 จริง ๆ** เพราะเคสที่เจอบ่อยที่สุดไม่ใช่ขัดกันชัด ๆ แต่เป็น
> *"อายุ 20–60"* → *"อายุ 20–60 และต้องไม่เป็นพนักงานสัญญาจ้าง"* — เพิ่มเงื่อนไข หรือกฎใหม่คนละข้อ
> ถ้าบังคับให้เลือกแค่ NEW/CHANGED โมเดลจะเดา และเดาผิดครึ่งหนึ่ง

#### สัญญาณตรวจจับ — แยกของที่วัดได้ ออกจากของที่โมเดลอ่าน

หลักเดียวกับ `extracted` vs `interpretation` เป๊ะ: **สัญญาณวัดได้เอาไว้ตั้งข้อสงสัย ไม่ใช่เอาไว้ตัดสิน**

| ชั้น | สัญญาณ | น้ำหนัก |
|---|---|---|
| **วัดได้** | **hash ของ SRC เดิมเปลี่ยน** — check #8 warn ว่า *"file changed since import"* อยู่แล้ว · TOR ฉบับแก้ทับของเดิม ≈ เป็นการเปลี่ยนเกือบ 100% | สูงสุด · มีอยู่ในระบบแล้ว แค่ยังไม่มีใครอ่านมันเป็นสัญญาณ change |
| **วัดได้** | ผู้ใช้พิมพ์ `BR-xxx` มาตรง ๆ ใน input | สูงสุด |
| **วัดได้** | **`CALC` field diff** — กฎใหม่ให้ค่าที่ชนช่องเดิมของสัญญาการคำนวณ (`formula`, `rounding_mode`, อัตรา, ช่วงค่า) | สูง · เทียบทีละ field ไม่ใช่เทียบข้อความ จึงแม่นกว่า |
| **วัดได้** | `belongs_to` เดียวกัน + **โทเคนตัวเลขใน `statement` ไม่เท่ากัน** | กลาง |
| **โมเดลอ่าน** | ข้อความขัดกันเชิงความหมาย | ต่ำ — **ต้องยืนยันเสมอ** ไม่ว่ามั่นใจแค่ไหน |

> **สองข้อที่ต้องระวังเรื่องนี้ ไม่งั้นเขียนโค้ดแล้วจับไม่ได้:**
> 1. `domain_concepts` อยู่บน **`requirement` ไม่ใช่ `ruleVersion`** — เทียบ "UL ชุดเดียวกัน" ระหว่างกฎสองข้อจึงไม่ได้ความอะไรเลย
>    มันคงที่ทั้ง REQ · ตัวที่ใช้จริงได้คือ `belongs_to` เท่านั้น
> 2. **ตัวอย่าง "25% → 23%" จับด้วยสัญญาณ `CALC` ไม่ใช่สัญญาณ `statement`** — เพราะอัตราดอกเบี้ยเป็น *input ของสัญญาการคำนวณ*
>    ถ้า `statement` เขียนแค่ "คิดดอกเบี้ยแบบลดต้นลดดอกตาม CALC-loan-002" การ diff ตัวเลขในข้อความจะไม่เจออะไรเลย
>    → **กฎที่ตัวเลขไปอยู่ใน `CALC` ต้องพึ่งสัญญาณ `CALC` เท่านั้น** อย่าคาดหวังจากการ diff ข้อความ

**ต้องถามทุกกรณี ไม่มีข้อยกเว้น** ต่อให้สัญญาณเป็นชั้น "วัดได้" ทั้งหมด เพราะสิ่งที่วัดได้คือ *"ข้อความต่างกัน"*
ส่วนสิ่งที่ต้องรู้จริงคือ *"ลูกค้าตั้งใจเปลี่ยนกฎ หรือกำลังพูดถึงคนละเรื่อง"* — อันหลังเป็น **business decision**
เหมือนเรื่องแบ่ง REQ ที่ skill เดิมกันไว้แล้วว่า *"splitting is a business decision, not text extraction"*

#### แทรกตรงไหนในรอบยืนยัน

รอบยืนยันของ capture ปัจจุบันคือ 1) แบ่ง REQ → 2) แหล่งขัดกัน → 3) การตีความที่คลอดกฎ → 4) ที่เหลือ
**change detection แทรกเป็นรอบที่ 2** ดันของเดิมลงไปหนึ่งขั้น:

| รอบ | ถามอะไร | ทำไมอยู่ตรงนี้ |
|---|---|---|
| 1 | input นี้เข้า REQ ไหน / แบ่งยังไง | ยังไม่รู้ REQ ก็ยังเทียบกับกฎเดิมไม่ได้ — ต้องมาก่อนเสมอ |
| **2** 🆕 | **อันไหนเป็นการเปลี่ยนกฎเดิม** | ถ้าเป็น change คำถามที่เหลือของกฎข้อนั้น**ไม่ต้องถามแล้ว** — มันจะไปถามใน `/req:change` แทน |
| 3 | แหล่งขัดกันเอง | เดิมรอบ 2 |
| 4 | การตีความที่คลอดกฎ | เดิมรอบ 3 |
| 5+ | ที่เหลือ (บอกจำนวนที่ค้างเสมอ) | เดิมรอบ 4 |

การอยู่รอบ 2 ประหยัดคำถามด้วย — ยืนยันการตีความรูปภาพของกฎที่กำลังจะถูกแทนทั้งข้อ คือถามฟรี

#### กติกาแช่แข็ง — capture เขียนอะไรได้ เขียนอะไรไม่ได้

โจทย์คือ **"แจ้งก่อน ถามก่อน แล้วค่อยอัปเดตเอกสาร"** แปลเป็นกติกาที่ไม่กำกวม:

| ของ | เขียนไหมตอนเจอ change | เหตุผล |
|---|---|---|
| `sources[]` + ไฟล์ใต้ `docs/` + hash | ✅ **เขียน** | หลักฐานเป็นกลาง ไม่ขึ้นกับว่าตกลงยังไง · และรูป paste ในแชท**ตายพร้อมหน้าต่าง** ถ้าไม่เขียนตอนนี้ก็ไม่มีอีกแล้ว |
| `extracted` / `interpretation` ของ SRC นั้น | ✅ เขียน | เหตุผลเดียวกัน |
| **โหนด `BR` ที่เป็น CHANGED** | ❌ **ห้ามเขียน** | ทางเดียวที่จะขึ้นเวอร์ชันคือ `/req:change` — ถ้า capture ทำเองได้ จะมี**สองเส้นทางที่สร้าง `@v(n+1)`** ซึ่งขัดกฎ *"never build a second extraction path"* ตรง ๆ |
| **โหนดอื่น ๆ ของ REQ ที่ถูกแช่แข็ง — รวม `provenance` ของรายการ SAME** | ❌ **ห้ามเขียน ค้างไว้ก่อน** | ดูกล่องข้างล่าง |
| **`docs/requirements/*.md` + `docs/wiki/**` ของ REQ ที่ถูกแช่แข็ง** | ❌ **ห้าม regenerate** | นี่คือข้อที่โจทย์สั่งตรง ๆ |
| REQ อื่นใน batch เดียวกันที่ไม่มีรายการ CHANGED | ✅ ทำต่อจนจบตามปกติ | แช่แข็ง**ราย REQ ไม่ใช่ทั้ง batch** — ยกเลิกงานทั้งก้อนเพราะกฎข้อเดียวคือการลงโทษคนใช้ |

> **หน่วยของการแช่แข็งคือ REQ และต้องเป็น REQ เท่านั้น**
> `provenance` อยู่**บนโหนดกฎ** (`ruleVersion.provenance`) ไม่ใช่บน source — เพิ่ม provenance ให้รายการ SAME
> จึงเป็นการ**แก้โหนดกฎ** ซึ่งขยับ `reqDocHash` ทันที
>
> batch จริงมักคละกัน: `SRC-009` เปลี่ยน `BR-loan-004` ขณะที่ `SRC-010` ยืนยัน `BR-loan-006` ใน REQ เดียวกัน
> ถ้าเขียน provenance ของ SAME ลงไปแต่ห้าม regenerate → **เอกสารค้างจริง check #10 แดง**
> จึงต้องค้างทุกอย่างของ REQ นั้น แล้วรายงานว่าค้างอะไรไว้บ้าง:
>
> ```
> ค้างไว้เพราะ REQ-loan-002 มีรายการที่ต้องตัดสินก่อน:
>   · SRC-010 ยืนยัน BR-loan-006@v1 (ไม่ได้ขัดกัน) — จะเพิ่ม provenance ให้หลังเคลียร์
> ```
>
> รายการที่ค้างจะถูกเขียนตอนสั่ง `/req:change` เสร็จ หรือตอบว่า "ไม่ใช่การเปลี่ยน" แล้วสั่ง capture ซ้ำ
> **แช่แข็ง = ไม่เขียนอะไรเลยใน REQ นั้น** ไม่ใช่ *เขียนแล้วไม่ render* — `spec-hash` จึงไม่ขยับ
> check #10/#12 ยังเขียว และไม่มีสถานะ "รอ regenerate" ให้ลืม

#### หน้าตาการแจ้ง

แจ้งก่อนถาม และ**เอาข้อความเดิมกับใหม่มาวางคู่กัน** — คนตัดสินจากการเห็นสองบรรทัดนี้ ไม่ใช่จากคำอธิบาย

```
⚠️ เจอ 1 รายการที่น่าจะเป็นการ "เปลี่ยนกฎเดิม" ไม่ใช่กฎใหม่ — ยังไม่เขียนอะไรลงไฟล์

  BR-loan-004@v1  (is_current · มีตัวอย่าง 2 ตัว · ใช้โดย CALC-loan-002)
    เดิม : ดอกเบี้ยลดต้นลดดอก 25% ต่อปี          ← SRC-002 TOR หน้า 3 §5.6
    ใหม่ : ดอกเบี้ยลดต้นลดดอก 23% ต่อปี          ← SRC-009 ไลน์ 13 ส.ค. (คุณเอ)
    สัญญาณ: UL ชุดเดียวกัน · REQ เดียวกัน · ตัวเลขต่าง (วัดได้ ไม่ใช่การตีความ)

  ถ้าเป็นการเปลี่ยนจริง จะกระทบต่อ:
    · CALC-loan-002  สัญญาการคำนวณต้องขึ้นเวอร์ชันตาม
    · GD-loan-003    เลขเฉลย 12 แถวใช้ไม่ได้ ต้องคำนวณใหม่
    · EX-loan-021/022 ต้องตรวจว่ายังพิสูจน์ข้อความใหม่ได้ไหม

  1) ใช่ เป็นการเปลี่ยน → สั่ง /req:change BR-loan-004@v1
  2) ไม่ใช่ เป็นกฎคนละข้อ → ร่างเป็น BR ใหม่ (บอกด้วยว่าต่างกันตรงไหน)
  3) ยังไม่แน่ใจ / ต้องถามลูกค้า → 🛑 การ์ดแดง

  ส่วนที่เหลือของ batch (SRC-010, SRC-011 → REQ-loan-003) ไม่ชนกับกฎไหน ทำต่อให้แล้ว
```

**capture ไม่รัน `/req:change` ให้เอง** ต่อให้ตอบข้อ 1 — กติกา *"ทุกคำสั่งจบด้วยการหยุดรออนุมัติ ไม่ไหลไปขั้นต่อไป"* ไม่มีข้อยกเว้น
สิ่งที่ capture ทำคือ**บอกคำสั่งถัดไปให้พิมพ์** และจดการแจ้งนี้ลง `log.md` ไว้ ไม่ว่าจะตอบข้อไหน — คำถามที่ถูกเลื่อนแล้วหายคือคำถามที่จะกลับมาตอนเขียนโค้ด

#### ขีดจำกัดที่ต้องพูดตรง ๆ

**การตรวจจับ change เป็น deterministic gate ไม่ได้** — "สองข้อความนี้ขัดกันไหม" ไม่มีสคริปต์ไหนตอบได้
มันจึงเป็น**รอบยืนยัน ไม่ใช่ check** และไม่มีเลข check ใหม่ในตาราง §6 สำหรับเรื่องนี้
คงหลักของระบบไว้: *"ไม่มีการให้ AI ตัดสินเลยสักข้อ"* ในตัวตรวจ — AI ตั้งข้อสงสัยได้ แต่คนเป็นคนตัดสิน และการตัดสินนั้นถูกบันทึกเป็นข้อมูล (`CHG` / `Q-xxx` / กฎใหม่) ที่ตัวตรวจจับต่อได้

สิ่งที่**ทำให้เป็น deterministic ได้จริง** มีอยู่อย่างเดียวคือ hash ของไฟล์ต้นทาง — แต่ต้องทำให้ครบวง ไม่งั้นพัง:

check #8 ตอนนี้ warn ว่า *"file changed since import"* แล้ว **แต่ไม่มีทางปิด warn นั้นเลย**
`CHG.triggered_by` ชี้ SRC ที่**ทำให้เกิด**การเปลี่ยน ส่วนเคสนี้คือ SRC **เดิม**ที่ถูกแก้ทับ — และตาม §7.4 เราไม่ทำ version ให้ SRC
ผลคือ warn จะแดงค้างตลอดกาลหลังใครแก้ไฟล์แม้แต่แก้คำผิด · **warn ที่ปิดไม่ได้ทำให้คนเลิกอ่าน warn ทั้งหมด** ซึ่งจะพา #13 กับ #14 ตายไปด้วย

ต้องมีทางรับทราบ และมันมีอยู่แล้วสองทางพอดี:

| ตอบว่า | ปิด warn ยังไง |
|---|---|
| เป็นการเปลี่ยนกฎ | `/req:change` บันทึก `hash_at_import` ใหม่ให้ SRC นั้น พร้อมผูก `CHG` |
| ไม่ใช่ (แก้คำผิด / จัดหน้าใหม่) | `/req:capture` บันทึก hash ใหม่ + `hash_reconfirmed_at` — **หลังถามแล้วเท่านั้น ห้ามอัปเดตเงียบ ๆ** |

ถ้าไม่ยอมเพิ่ม `hash_reconfirmed_at` เข้า schema — **ให้ตัดข้อเสนอนี้ทิ้งทั้งข้อ** เหลือ warn เดิมของ #8 ไว้เฉย ๆ
warn ที่ปิดไม่ได้แย่กว่าไม่มี warn

## 8. Loop ย้อนกลับ — ต้องออกแบบให้เกิด ไม่ใช่ให้หลีกเลี่ยง

สไลด์ 3 บอกว่า *"ถ้าเก็บ requirement แล้วไม่เคยต้องย้อนกลับ แปลว่าคุณยังไม่ได้ตรวจ"* — แปลเป็นพฤติกรรมของ skill:

| loop | เกิดตอน | skill ต้องทำอะไร |
|---|---|---|
| **L1** AC → BR | `/req:example` เขียนไม่ออก | บอกว่า **กฎขัดกัน** และเสนอ `/req:change` — ห้ามยัดตัวอย่างที่พิสูจน์ไม่ได้ |
| **L2** Golden → Calc | `/req:golden` เลขไม่ลงตัว | ย้อน `/req:calc` **ห้ามแก้ตัวเลขเฉลยให้เข้ากับสูตร** |
| **L4** Scope → Goal | `/req:capture` ตัด scope เยอะ | ถามซ้ำว่ายังบรรลุ end goal ไหม |
| **L5** API → Actors | Phase 2 | ไม่ใช่ของ skill นี้ |

## 10. ความสอดคล้องกับ DOC-STANDARD v1.1

เอกสารนี้เขียนก่อนมาตรฐาน · ตรวจย้อนแล้ว **ตรงเกือบทั้งหมดโดยบังเอิญ เพราะทั้งคู่งอกจากกติกาชุดเดียวกัน**
รายการที่ต้องรู้:

| ข้อของมาตรฐาน | สถานะของแบบออกแบบนี้ |
|---|---|
| **§1 สถานะใน JSON · ความรู้ใน Markdown · generate จาก JSON** | ✅ นี่คือ §5.1 ของเอกสารนี้ทั้งดุ้น (`spec.json` เป็นความจริง wiki เป็น render ตัวที่สาม) |
| **§2 เอกสาร 4 ชั้น ห้ามปนในไฟล์เดียว** | ✅ หน้า wiki = ชั้น A (ห้ามแก้มือ มี `spec_hash`) · `log.md` = ชั้น C · ห้าม marker block |
| **§4 frontmatter บังคับบนหน้า concept** | ✅ §5.4 ใช้ 6 field มาตรฐาน + ส่วนขยาย |
| **§4 คีย์ `status` สงวนให้ schema** | ✅ §5.4 ใช้ `status: draft` ตาม enum ของ `spec.schema.json` ไม่ใช่ค่าของ `lifecycle` |
| **§5.2 รายการ type ของ project bundle** | ✅ ตรงกัน — และ **`Calculation Contract` / `Golden Dataset` / `Change Set` ถูกบรรจุเข้ารายการปิดของมาตรฐานแล้ว** ในฐานะ type ที่ `req` v0.3 เสนอ |
| **§5 id `SRC-<nnn>` ไม่มีส่วน module** | ✅ ใช้ `SRC-002` `SRC-009` ตลอด — ตรงกับ `^SRC-[0-9]{3}$` ใน schema (มาตรฐานจดเป็นข้อยกเว้นไว้แล้ว) |
| **§6 `index.md` ต้องมีคอลัมน์ที่ตอบคำถามหลักของไดเรกทอรี** | ✅ §5.5 `rules/index.md` มีคอลัมน์ *"มีตัวอย่างกี่ตัว"* — กติกาข้อนี้ในมาตรฐาน**ถอดมาจากตรงนี้** |
| **§6 `log.md` ต้องจดสิ่งที่ยังไม่เสร็จด้วย** | ✅ §7.7 สั่งให้จดการแจ้ง change ลง log ไม่ว่าผู้ใช้จะตอบข้อไหน |
| **§9 ไม่สร้างสคริปต์ตัวใหม่ · ตรรกะเขียนที่เดียว** | ✅ check #12 อยู่ใน `verify-rules.mjs` เดิม · `nodeDocHash` เพิ่มใน `doc-hash.mjs` เดิม · **ข้อ (ก)–(จ) ของ #12 import จาก `doc-frontmatter.mjs` ร่วมกับด่าน authoring ระดับ severity ตรงกันทั้งคู่** |
| **§8 ข้อ 8 รูปแบบวันเวลา** | ✅ ทุกตัวอย่างใช้ `+07:00` มีวินาที · และจดไว้ว่า schema ไม่บังคับให้ ตัว render ต้อง normalize เอง |
| **§9 ของใหม่เข้าเป็น warn ก่อน · ห้ามมี warn ที่ปิดไม่ได้** | ✅ #13/#14 เป็น warn · และ §7.7 ตัดข้อเสนอ warn ที่ปิดไม่ได้ทิ้งเองพร้อมเขียนเหตุผล |
| **§10 ห้ามนับเลขด้วยมือ** | ✅ `rollup.mjs --write` ทุกครั้ง ห้ามนับเอง |
| **§7 ข้อ 4 หนึ่งไฟล์ = หนึ่งหน่วยงาน** | 🟡 **ยกเว้นโดยประกาศ** — ข้อเสนอออกแบบยกเว้นทั้งชนิด (ประกาศไว้ที่หัวเอกสารและใน DOC-STANDARD §11) |
| **§8 ข้อ 1 หนึ่งข้อเท็จจริงมีที่อยู่ที่เดียว** | ✅ แก้แล้ว — §7.5 ประกาศบนหัวแผนผังว่าแสดงเฉพาะส่วนเวอร์ชัน โครงเต็มอยู่ที่ §5.3 ที่เดียว (ก่อนแก้ ผังนั้นอ่านเหมือนโครงเต็มที่ไม่มี `examples/` `glossary/` `questions/`) |

### สิ่งที่การเทียบครั้งนี้ทำให้ต้องแก้ที่ *มาตรฐาน* ไม่ใช่ที่นี่

มาตรฐาน v1.0 ปิดรายการ `type` ไว้รายการเดียว (Marketplace / Plugin / Skill / …) ซึ่งเป็น type ของ **authoring bundle**
ถ้าปล่อยไว้ ตัวตรวจ D2 จะ**ตีกลับทุกหน้าของ project bundle** — `Business Rule`, `Requirement`, `Example` ไม่มีอยู่ในรายการ
แก้แล้วโดยแยกเป็น **§5.1 authoring** กับ **§5.2 project** และให้ D2 ตรวจตาม scope ของ bundle ไม่ใช่ตรวจรวมกอง

## 11. คำถามที่ยังไม่ได้เคาะ

1. **`docs/wiki/` เข้า git ไหม** — เข้า = diff อ่านง่ายมากตอน review requirement, ไม่เข้า = ไม่มี noise ตอน regenerate
   (เอกสารนี้เดาไว้ว่า **เข้า** ตามแนวเดียวกับ `docs/requirements/`)
2. **สอนในคลาสด้วยไหม** — ถ้าใช่ ขั้น 6/9 ต้องมี worked example ของ MiniLoan (EMI 9,504.43) เป็น fixture ตั้งแต่รอบ 3
3. **ขั้น 7 State Machine — ควรมีโหนด `SM-xxx` ไหม** (ช่องว่างที่เหลืออยู่ข้อสุดท้าย)

   **เนื้อหามีที่อยู่แล้ว:** transition ต้องห้ามเขียนเป็น BR + EX ได้ตรง ๆ — MiniLoan US-06 ทำแบบนั้นอยู่
   (*Given `Rejected` · When พยายามอนุมัติ · Then invalid transition*) ไม่ใช่เนื้อหาที่ตกหล่น

   **ที่ขาดคือความครบ ไม่ใช่ที่เก็บ:** ระบบนี้ทั้งระบบวัดด้วยการ**นับ** — "กฎข้อไหนยังไม่มีตัวอย่าง" นับได้เพราะรู้ตัวหาร
   แต่ *"ลูกศรที่ไม่ได้วาด"* ตามสไลด์ **นับไม่ได้** เพราะไม่มีใครรู้ว่าตัวหารคือเท่าไหร่
   `SM-xxx` จะเปลี่ยนเรื่องนี้ได้จริง — ตาราง n สถานะ × m เหตุการณ์ ทำให้ช่องว่างกลายเป็น**เซลล์ที่นับได้**

   **ทำไมยังไม่เอาเข้ารอบนี้:** ตัวโหนดเปล่า ๆ ไม่ให้อะไรเลย มันมีค่าก็ต่อเมื่อมี check ความครบของเมทริกซ์คู่มาด้วย
   ซึ่งเป็นงานใหญ่กว่ารอบ 1–7 รวมกัน และต่างจาก `CALC`/`GD` ตรงที่สองตัวนั้น**ไม่มีที่อยู่เลย**ในสไปน์ปัจจุบัน
   ส่วนนี่มีที่อยู่แล้วแค่ตรวจไม่ได้ — ลำดับความสำคัญจึงต่างกัน ไม่ใช่หลักฐานต่างกัน
