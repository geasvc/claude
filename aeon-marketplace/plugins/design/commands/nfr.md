# /design:nfr — ความต้องการที่ไม่ใช่หน้าที่

**ต้องรัน `/design:function` ให้เสร็จก่อน** ไม่งั้นหยุดด้วย exit 2 — NFR คือเป้าหมายที่วางทับหน้าที่ ถ้ายังไม่มีหน้าที่ก็ยังไม่มีอะไรให้วางทับ

ผลิตหัวข้อ 4 ของเอกสารลูกค้า: สมรรถนะ · ความปลอดภัย · ความพร้อมใช้ · ความง่ายในการใช้ · การปฏิบัติตามข้อกำหนด (PDPA)

## id ของ NFR — **อ้าง ไม่ใช่สร้างใหม่**

`req` มี NFR อยู่แล้วใน `requirements[].nfr[]` และ **schema ที่ประกาศไว้ของ req เป็นเจ้าของรูปแบบ id** (`^NFR-<module>-###$`) พร้อม `kind` ที่เป็น enum ปิด

> §6.1 เดิมให้ `NFR-###` เป็นของ design — บนโปรเจกต์จริงมันถูกจองไปแล้ว
> นี่คือรอยต่อเดียวกับ `RULE-###` / `BR-xxx` ที่เคาะไปเมื่อ 2026-08-20 · มินต์คู่ขนานเมื่อไหร่ = แหล่งความจริงสองที่ ซึ่ง §5.4 W3 ห้ามตรงตัว
> **`nfr.json` อ้าง id ของ `req` เท่านั้น** · ด่าน NF2 ตีตกทันทีที่เจอ id ที่ `req` ไม่มี

**ถ้าเจอข้อกำหนดเชิงคุณภาพที่ `req` ไม่ได้เก็บ — ห้ามเขียนเองที่นี่** ส่งกลับผ่าน back-channel (§19.3) เพราะ §1.2 ห้าม `design` เก็บ requirement เอง

## ตัวเลข — **design เป็นคนร่างกับเจ้าของ**

`req` ให้ข้อความมา ไม่ให้ตัวเลข · DoD ของคำสั่งนี้บังคับว่า **ทุก NFR ต้องมีตัวเลขที่วัดได้** (V9)

> **เจ้าของเคาะ 2026-08-20: design ร่างตัวเลขกับเจ้าของ** เหมือนที่ `/design:function` ร่าง FN/UC
> §1.2 ห้าม design **เก็บ requirement ใหม่** — การใส่ตัวเลขให้ข้อความที่ req เก็บมาแล้วไม่ใช่ requirement ใหม่
> จึง **ไม่มีช่องให้ผ่านแบบ "ยังไม่รู้ตัวเลข"** · ไม่มีตัวเลข = NF3 แดง ไม่ใช่คำเตือนที่พาต่อไปได้

**"ระบบต้องเร็ว" ที่หลุดไปถึงเอกสารลูกค้า คือสิ่งที่ V9 มีไว้กัน** — ข้อกำหนดที่ไม่มีใครสอบตกได้ ไม่ใช่ข้อกำหนด

## ของที่ derive มา ห้ามเขียนซ้ำใน `nfr.json`

| ของ | มาจากไหน | ทำไมไม่ให้เขียนเอง |
|---|---|---|
| REQ ที่เป็นเจ้าของ NFR | ที่ `req` วางมันซ้อนอยู่ | เขียนซ้ำ = มีสองที่ให้ผิด และมีที่เดียวที่ถูกตรวจ |
| `kind` | `req` | design ไม่จัดประเภทใหม่ให้ของที่ req จัดไปแล้ว (NF6) |
| `verification.method` | ตั้งต้นจาก `verified_by` ของ `req` | เขียนต่างได้ แต่ต้องตั้งใจ — ต่างเมื่อไหร่ NF5 แดง ไม่ใช่ทับเงียบ ๆ |

## ขั้นตอน

1. **อ่านก่อน** — `spec.json` (`requirements[].nfr[]`) และ `design.state.json`

2. **ร่าง `nfr.json` กับเจ้าของ** ที่ `<state-dir>/design/`

   ยังไม่มีไฟล์ก็รันดูก่อน มันพิมพ์รูปร่างตั้งต้น **พร้อมรายการ NFR ที่ `req` เก็บไว้แล้ว** ให้:
   ```
   node "${CLAUDE_PLUGIN_ROOT}/scripts/nfr.mjs" --root .
   ```

   แต่ละข้อใน `nfrs[]`:
   ```json
   {
     "id": "NFR-loan-004",
     "metric": { "name": "สิ่งที่วัด", "operator": "<=", "value": 3, "unit": "วินาที",
                 "condition": "วัดตอนไหน ภายใต้ภาระเท่าไร" },
     "verification": { "method": "fault_injection_test", "evidence": "หลักฐานเก็บที่ไหน" }
   }
   ```
   - `operator` เลือกจาก `<=` `<` `>=` `>` `==` `between` (ใช้ `between` ต้องมี `max` ที่มากกว่า `value`)
   - `unit` ว่างไม่ได้ — **3 อะไร** วินาที เปอร์เซ็นต์ หรือครั้ง
   - `value` เป็น **0 ได้** และมักเป็นเป้าหมายจริง เช่น "ใบสมัครที่ยื่นแล้วสูญหาย 0 ใบ"

3. **NFR ที่จงใจไม่กำหนดเป้าหมาย ต้องประกาศ ไม่ใช่เงียบ**
   ใส่ใน `notApplicable[]` พร้อม `reason` ที่เขียนจริง — NF1 แดงทั้งกรณีลืม และกรณีใส่เหตุผลว่าง

4. **ตรวจ** (ยังไม่เขียนอะไร):
   ```
   node "${CLAUDE_PLUGIN_ROOT}/scripts/nfr.mjs" --root .
   ```
   - **exit 2** — `function` ยังไม่เสร็จ หรือยังไม่มี `nfr.json` · ยกพาธที่มันบอกมาพูดตรง ๆ
   - **exit 1** — ไม่ผ่าน · รายงานทีละข้อพร้อม id **แล้วแก้ JSON ไม่ใช่แก้เอกสาร**
   - **exit 0** — ผ่าน

   | ด่าน | ตรวจอะไร |
   |---|---|
   | NF0 ⚠️ | `req` มี NFR อย่างน้อยหนึ่งข้อ — **เตือน ไม่ใช่แดง** เพราะโปรเจกต์ที่ไม่มีข้อกำหนดแบบนี้จริง ๆ ก็มีได้ |
   | NF1 | ทุก NFR ที่ `req` เก็บไว้ ถูกกำหนดเป้าหมาย หรือประกาศ `notApplicable` พร้อมเหตุผล |
   | NF2 | ทุก id มีอยู่จริงใน `req` — **design ไม่มินต์ id เอง** |
   | NF3 | **ทุกข้อมีตัวเลขที่วัดได้** (V9) |
   | NF4 | ตัวเลขนั้นอ่านออก — operator รู้จัก · `unit` และ `name` ไม่ว่าง · `between` มีขอบบนจริง |
   | NF5 | มีวิธีพิสูจน์ และไม่ขัดกับ `verified_by` ของ `req` |
   | NF6 | `kind` ไม่ขัดกับที่ `req` จัดไว้ |

5. **หยุดขออนุมัติ 🛑**

6. เขียนจริง:
   ```
   node "${CLAUDE_PLUGIN_ROOT}/scripts/nfr.mjs" --root . --write
   ```
   ได้ `trace.design.json` + `docs/design/04-non-functional-requirements.md`

7. บอกคำสั่งถัดไป **ห้ามรันเอง** แล้วหยุด 🛑

## กราฟสาวกลับ — คำนวณจากไฟล์ทุกใบที่มี ไม่ใช่แค่ของคำสั่งนี้

`trace.design.json` มีเจ้าของคนเดียวคือ `design` (§6.2 แยกกราฟตามคนเขียน) แต่ **design มีหลายคำสั่งที่ผลิตของ**

> ถ้าแต่ละคำสั่งเขียนไฟล์นี้จากสิ่งที่ตัวเองรู้ คำสั่งที่รันทีหลังจะลบ edge ของอีกคำสั่งทิ้งเงียบ ๆ — รอยรั่วเดิม (§19.2 L1) ที่ย้ายเข้ามาอยู่ในปลั๊กอินที่การแยกตามคนเขียนมองไม่เห็น
> `scripts/trace-design.mjs` จึงสร้างกราฟจาก **ไฟล์ทุกใบที่มีอยู่จริงบนดิสก์** และทุกคำสั่งที่เขียนไฟล์นี้เรียกตัวเดียวกัน
> **รันคำสั่งสลับลำดับกันแล้วได้กราฟเดียวกันไบต์ต่อไบต์** เพราะกราฟเป็นผลของ artifact ไม่ใช่ผลของลำดับที่ใครรันอะไรก่อน

## เอกสารที่ออกมา ห้ามแก้ด้วยมือ

แก้ที่ `nfr.json` แล้ว render ใหม่ · ไฟล์มีหัวเตือนติดอยู่ในตัว

**เลขหัวข้อย่อยผูกกับหมวด ไม่ได้ไล่ตามลำดับ** — โปรเจกต์ที่มีแค่ security กับ compliance จะได้ `4.2` แล้วข้ามไป `4.5` ซึ่ง**ตั้งใจ**
หมวดเดิมได้เลขเดิมทุกโปรเจกต์และทุกครั้งที่ render ใหม่ · การอ้างอิงข้ามเอกสารที่เขียนวันนี้จึงยังชี้ถูกหลังมีหมวดเพิ่มหรือหายไป

**หัวข้อ 4 ที่ว่าง จะบอกออกมาตรง ๆ ว่าว่างเพราะอะไร** ไม่ปล่อยหน้าเปล่าที่ดูเหมือนมีคนลืม — §11 บังคับให้หัวข้อนี้ต้องมีอยู่ หน้าเปล่าจึงหลุดถึงลูกค้าได้จริง

## ตรวจตัวสคริปต์เอง

```
node "${CLAUDE_PLUGIN_ROOT}/scripts/nfr.mjs" --root "${CLAUDE_PLUGIN_ROOT}/scripts/fixtures/nfr-ok"        # ต้อง exit 0 · 0 error · 6 trace edges
node "${CLAUDE_PLUGIN_ROOT}/scripts/nfr.mjs" --root "${CLAUDE_PLUGIN_ROOT}/scripts/fixtures/nfr-bad"       # ต้อง exit 1 · 6 error (NF1-NF6 ข้อละครั้ง)
node "${CLAUDE_PLUGIN_ROOT}/scripts/nfr.mjs" --root "${CLAUDE_PLUGIN_ROOT}/scripts/fixtures/nfr-empty"     # ต้อง exit 0 · 1 warn (NF0) · req ไม่มี NFR เลยสักข้อ
node "${CLAUDE_PLUGIN_ROOT}/scripts/nfr.mjs" --root "${CLAUDE_PLUGIN_ROOT}/scripts/fixtures/function-ok"   # ต้อง exit 2 (function ยังไม่เสร็จ)
```

สัญญาของแต่ละ fixture อยู่ที่ `scripts/fixtures/EXPECTED.md`
