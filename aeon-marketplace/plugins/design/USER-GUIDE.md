# คู่มือใช้งาน `design` — Phase 2 (Design)

**เจ้าของเอกสาร:** Mounchon — **ยังไม่ได้ทบทวน**
**ร่างเมื่อ:** 2026-08-20 โดยขั้น S0 · รอเจ้าของอ่านแล้วยืนยัน จึงจะเติมวันทบทวนได้
**สถานะ:** v0.6.0 — **Milestone 1 เสร็จ** (init → overview → function → status) + `nfr` · อีก 9 คำสั่งยังไม่ได้สร้าง

## 1. ตอนนี้ใช้อะไรได้บ้าง

**ใช้ได้ 6 ตัว:** `/design:help` · `/design:init` · `/design:overview` · `/design:function` · `/design:nfr` · `/design:status`

เปิด session ใหม่ให้สั่ง **`/design:status`** ก่อนเสมอ — มันบอกว่าค้างตรงไหนและคำสั่งถัดไปคืออะไร โดยคำตอบมาจาก exit code ของสคริปต์ ไม่ใช่จากที่โมเดลคิดเอง

อีก **9 คำสั่ง** ออกแบบไว้ครบแล้วใน `docs/requirement/design-plugin-requirements.en.md` แต่ **ยังไม่ได้สร้าง** — `help` ลงชื่อไว้ทุกตัวว่าตัวไหนยังไม่มี

ทำไมถึงลงทะเบียนตั้งแต่ยังสร้างไม่ครบ แทนที่จะรอให้ครบก่อน — เพราะกติกา `docs/progress.json` → `rules[3]` บอกว่า *หนึ่ง task ต่อหนึ่ง session* การมีโครงกับ `help` ที่บอกตรง ๆ ว่าอะไรยังไม่มี ปลอดภัยกว่าการมี plugin ที่ดูเหมือนใช้ได้แต่ครึ่งเดียว

**ถ้าสั่งคำสั่งที่ยังไม่มี** — จะไม่มีอะไรเกิดขึ้น และ **ห้ามให้ Claude เดาทำแทน** นี่คือเหตุผลที่ `help` ต้องลงชื่อคำสั่งที่ยังไม่มีไว้ทุกตัว (DOC-STANDARD §3.5)

## 2. design มีไว้ทำอะไร

ปัญหาที่มันแก้: เวลาทำงานให้ลูกค้า ต้องเขียนของเดียวกันสองรอบ

1. เอกสารที่ลูกค้าอ่านแล้วเซ็นรับได้ — ภาษาคน มีบทนำ มีไดอะแกรม
2. เอกสารที่ AI เอาไปเขียนโค้ดต่อได้ — เนื้อหาเดียวกันแท้ ๆ แต่ต้องจัดรูปใหม่หมด

พอลูกค้าขอแก้ มักลืมแก้อีกฝั่ง **ภายในเดือนเดียวเอกสารกับความจริงก็ไม่ตรงกัน**

`design` รับความต้องการมาครั้งเดียว แล้วผลิตออกทั้งสองทางจากความจริงชุดเดียว โดยที่สองทางนั้นหลุดจากกันไม่ได้

**หัวใจไม่ใช่เอกสารที่เขียนสวย แต่คือความสาวกลับได้ทั้งเส้น**

## 3. มันต่อกับ plugin อื่นยังไง

```
req ──▶ design ──┬──▶ mockup
                 ├──▶ dev
                 ├──▶ qa
                 └──▶ deliver
```

**ของที่รับเข้ามาจาก `req`** — `requirements.json` กับ `glossary.json` เป็นของบังคับ ถ้าขาดหรือไฟล์เสีย **`design` ต้องหยุดแล้วบอกว่าขาดอะไร ห้ามเดาเนื้อหาแล้วทำต่อ**

**ของที่ส่งออกไป** — `mockup` รับ `sitemap.json` · `screens.json` · `rbac.json` / `dev` รับ `functions.json` · `datamodel.json` · `interfaces.json` / `qa` รับ `scenarios.json` + trace

## 4. เส้นแบ่งกับ `mockup` — เรื่องที่เข้าใจผิดบ่อยที่สุด

| `design` เป็นเจ้าของ | `mockup` เป็นเจ้าของ |
|---|---|
| ผังเว็บ (sitemap) | wireframe รายหน้า |
| รายละเอียดหน้าจอ — ฟิลด์ · กฎตรวจค่า · ปุ่ม · ไปไหนต่อ | ไฟล์ mockup HTML |
| สิทธิ์ระดับหน้าจอและระดับปุ่ม | สี ฟอนต์ ชุด component |
| **รายการสถานะที่หน้าจอต้องรองรับ** (ว่าง · โหลด · ผิดพลาด · ไม่มีสิทธิ์ · ล้น) | การรับ handoff จากดีไซเนอร์ |

**ทำไมรายการสถานะถึงอยู่ฝั่ง design** — เพราะมันเป็นข้อกำหนดเชิงพฤติกรรม ไม่ใช่เรื่องหน้าตา `dev` ต้องเขียนมันและ `qa` ต้องทดสอบมัน ไม่ว่าโปรเจกต์นั้นจะทำ mockup หรือไม่

**`design` ห้ามทำเด็ดขาด** — กำหนดสี/ฟอนต์ · สร้าง HTML หรือ wireframe · รับ handoff · เขียนลงพื้นที่ของ `mockup`

ถ้าสั่ง `design` ให้ทำ mockup ให้ **มันต้องบอกให้ไปใช้ `mockup` แทน ไม่ใช่ทำให้**

## 5. กติกาที่ทุกคำสั่งต้องทำตาม

1. อ่าน `design.state.json` ก่อนทำอะไรเสมอ
2. คำสั่งก่อนหน้ายังไม่ได้รัน → **หยุดและรายงาน**
3. **รันซ้ำได้ผลเท่าเดิม** — แก้ของเดิม ไม่สร้าง ID ซ้ำ
4. เขียน JSON ก่อน แล้วค่อยเรนเดอร์ Markdown
5. สร้างของใหม่เมื่อไหร่ ต้องอัปเดต trace ทุกครั้ง
6. เสร็จแล้วอัปเดต `design.state.json` พร้อมเวลา
7. **ห้ามแก้ของที่ `status: approved`** เว้นแต่มี change-set อนุญาต

**กฎที่สำคัญที่สุดและโมเดลชอบละเมิดเองโดยธรรมชาติ:**

> ห้ามตอบว่า "รับทราบ" / "เข้าใจแล้ว" / "เดี๋ยวจัดให้" **ก่อน** เขียนบันทึกลงดิสก์จริง

เพราะสิ่งที่หายไปทุกครั้งที่ปิด session ไม่ใช่ไฟล์ แต่คือ **สิ่งที่คุยกันแล้วไม่มีใครจดไว้**

## 6. หนึ่งไฟล์ หนึ่งเจ้าของ — เหตุผลที่ต้องเข้มขนาดนี้

**ห้ามให้ plugin สองตัวเขียนไฟล์เดียวกัน แม้จะเขียนคนละฟิลด์ก็ตาม**

เพราะการ regenerate เขียนทับทั้งไฟล์เสมอ — `qa` บันทึกผลเทสลงไฟล์ที่ `design` เป็นเจ้าของ พอ `design` เรนเดอร์ใหม่ **ผลเทสทั้งชุดหายเงียบ ๆ** ไม่มีใครรู้จนกว่าจะต้องใช้

ทางแก้คือแยกไฟล์ตามคนเขียน แล้วเชื่อมกันด้วย ID:

```
design/trace.design.json      เจ้าของ: design
qa/scenario-results.json      เจ้าของ: qa
dev/implementation-map.json   เจ้าของ: dev
```

กราฟรวมถูกประกอบตอนอ่าน **ไม่มีไฟล์กราฟรวมอยู่บนดิสก์** ของที่ไม่มีตัวตนบนดิสก์ ถูกเขียนทับไม่ได้

## 7. ทำไมของบางอย่างเป็น JSON บางอย่างเป็น Markdown

| อยู่ในรูป | ใช้กับ |
|---|---|
| **JSON** | สถานะ · รายการ · การจับคู่ · ผ่าน/ไม่ผ่าน — ของที่เครื่องต้องตัดสิน |
| **Markdown** | เหตุผล · บริบท · บันทึกการตัดสินใจ — ของที่คนกับ AI ต้องอ่าน |

เหตุผลจริงที่เป็นแบบนี้: **โมเดลลังเลที่จะแก้ JSON แต่แก้ Markdown ได้อย่างสบายใจ** ของที่ห้ามเพี้ยนจึงต้องอยู่ในรูปที่โมเดลไม่กล้าแตะ

และ Markdown ยังต้องแยกอีกชั้น ถามว่า **"เนื้อหานี้ยังจริงอยู่ไหมหลังเฟสนี้จบ"**

- จริงต่อ → `wiki/` จัดตาม**หัวข้อ** (โมเดลของโดเมน · ADR · ธรรมเนียมการเขียน)
- ไม่จริงต่อ → `docs/<plugin>/` จัดตาม**plugin** (บทนำ · บันทึกสัมภาษณ์ · รายงานผลกระทบ)

เปรียบเทียบ: `docs/` คือ**สำนวนคดี** ปิดคดีก็จบ · `wiki/` คือ**ห้องสมุดกฎหมาย** ไม่มีใครเป็นเจ้าของชั้นหนังสือ ทุกคดีหยิบไปใช้ และมันอยู่นานกว่าทุกคดี

## 8. ตารางสิทธิ์ — ทำไมแค่ role × screen ถึงไม่พอ

ตารางสองมิติแบบที่เห็นกันทั่วไปพังทันทีที่เจอองค์กรจริง เพราะมันตกไปสี่มิติที่สำคัญกว่า

| มิติที่ขาด | คำถามที่ต้องตอบให้ได้ | ไม่มีแล้วเป็นยังไง |
|---|---|---|
| **ขอบเขตข้อมูล** | อนุมัติของ*ใคร* — ทั้งหมด / สาขาตัวเอง / ทีมตัวเอง / ที่ตัวเองสร้าง | `dev` เดาไม่ได้ ต้องถามกลับ หรือเดาผิดแล้วรื้อชั้น query ใหม่ |
| **เงื่อนไขตามสถานะ** | แก้ได้ตอนอยู่สถานะไหน · ยกเลิกได้ก่อนขั้นตอนไหน | `dev` ทำ CRUD ธรรมดาไปก่อน แล้วมาไล่แก้ทุกหน้าทีหลัง |
| **ระดับฟิลด์** | ฟิลด์ไหนที่บาง role ต้องมองไม่เห็น (เงินเดือน · เลขบัตรประชาชน) | ข้อมูลส่วนบุคคลรั่วผ่านหน้าที่ role นั้นเปิดได้อยู่แล้ว |
| **การมอบอำนาจ** | ใครทำแทนใครได้ ช่วงไหน | มีเกือบทุกงานองค์กรไทย แต่ไม่เคยอยู่ใน requirement ตั้งต้น |

**ค่าเริ่มต้นต้องเป็น "ปฏิเสธ"** — อะไรที่ไม่ได้ประกาศไว้ คือห้าม เริ่มจาก "อนุญาต" จะเกิดรูที่ไม่มีใครเห็นจนกว่าจะโดนเจาะ

**ประกาศแค่ชั้น `ui` ไม่นับเป็นการคุมสิทธิ์** — ซ่อนปุ่มคือซ่อนปุ่ม ต้องบังคับที่ `api` หรือ `domain` อย่างน้อยหนึ่งชั้น (V26)

**ตารางสิทธิ์เป็นเอกสารที่ลูกค้าต้องเซ็น** ไม่ใช่ของภายในทีม เพราะมันเข้ารหัสอำนาจในองค์กร ไม่ใช่รายละเอียดทางเทคนิค ตัดออกจากเอกสารลูกค้าเมื่อไหร่ **รับประกันว่าจะมีเรื่องเถียงกันตอน UAT ว่าใครควรอนุมัติได้**

## 9. อยากได้คำสั่งที่ยังไม่มี ทำยังไง

สร้างทีละ step ตามลำดับใน `help` — หนึ่ง step ต่อหนึ่ง session

สถานะจริงของแต่ละ step อ่านจาก **`docs/progress.json` ที่เดียว** ห้ามเชื่อเอกสารหน้าไหนรวมทั้งหน้านี้

ก่อนเริ่ม step ใหม่ ให้รันด่านเพื่อดูว่าตอนนี้เขียวอยู่ไหม:

```
node scripts/verify-design.mjs --root .
```

## 10. ของที่ยังไม่เคาะ

สเปก §16 มี 17 ข้อ **เคาะแล้ว 2 ข้อ** (D1 ตารางสิทธิ์ · D17 ผัง wiki) ที่เหลือยังเป็นข้อเสนอ

คำสั่งที่ต้องใช้ข้อมูลจากข้อที่ยังไม่เคาะ **จะหยุดถามเจ้าของ ไม่ใช่เลือกเอง** — ตามกฎยืน CLAUDE.md §6 *"ห้ามเดา — ข้อมูลที่ขาดคือช่องว่าง ให้บันทึกแล้วส่งกลับขึ้นไป ไม่ใช่เติมให้ดูครบ"*
