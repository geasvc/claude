## ⚠️ อ่านก่อน — ตอนนี้ยังสร้างไม่เสร็จ

`design` v0.5.0 ยังสร้างไม่ครบ คำสั่งที่ใช้ได้จริงมี **5 ตัว** คือ `/design:help` (หน้านี้) · `/design:init` · `/design:overview` · `/design:function` · `/design:status`
อีก 10 ตัวข้างล่าง **ออกแบบไว้แล้วแต่ยังไม่ได้สร้าง** — สั่งไปก็ไม่มีอะไรทำงาน

**`/design:status` คือตัวที่ควรสั่งเป็นอันแรกเมื่อเปิด session ใหม่** — มันบอกว่าค้างอยู่ตรงไหนและต้องทำอะไรต่อ

**ห้ามให้ Claude เดาทำแทน** ถ้าอยากได้ตัวไหน สั่งให้สร้าง step นั้นก่อน (ดูตาราง step ท้ายหน้า)

## design ทำอะไร

รับกระดูกสันหลังของกฎที่ `req` เก็บมา แล้วผลิตออกสองทางจากความจริงชุดเดียว

| ปลายทาง | รูปแบบ | ใครใช้ |
|---|---|---|
| คน | เอกสารร้อยแก้วภาษาไทย (Markdown → Word/PDF) | ลูกค้า · PM เอาไว้อ่านแล้วเซ็นรับ |
| AI | JSON + Wiki Markdown | plugin ปลายน้ำ (`mockup` · `dev` · `qa`) เอาไปทำงานต่อ |

**ของที่ต้องได้จริง ๆ ไม่ใช่เอกสารที่เขียนสวย แต่คือความสาวกลับได้ทั้งเส้น** — ทุกชิ้นงานมี ID ที่ไล่ขึ้นไปถึง `REQ-xxx` ได้เสมอ

**สิ่งที่ design ไม่ทำ** — ไม่เก็บ requirement เอง (เป็นงานของ `req`) · ไม่เขียนโค้ดจริง (`dev`) · ไม่รันเทส (`qa`) · **ไม่ทำ wireframe / mockup / สี / ฟอนต์** (`mockup`) ถ้าอยากได้ mockup ให้ไปใช้ plugin นั้น อย่าให้ design ทำให้

## ลำดับที่ต้องรัน

```
/design:init  →  overview  →  function  →  datamodel  →  rbac  →  sitemap
                                  ↓                                   ↓
                                 nfr  →  interface  →  scenario  →  export
```

**กติกาลำดับที่ห้ามข้าม**

- `rbac` ต้องรัน **หลัง** `function` + `datamodel` (ต้องมี action กับ entity อยู่ก่อน) และ **ก่อน** `sitemap`
- ถ้าไม่มี `rbac.json` แล้วสั่ง `sitemap` → **ต้องหยุดและรายงาน** ห้ามสร้างหน้าจอที่ไม่มีสิทธิ์ผูกอยู่
- ทุกคำสั่งอ่าน `design.state.json` ก่อนทำอะไรเสมอ · ถ้าคำสั่งก่อนหน้ายังไม่ได้รัน → หยุดและบอก
- ทุกคำสั่ง **รันซ้ำได้ผลเท่าเดิม** ไม่สร้าง ID ซ้ำ

### ✅ `/design:help` 👁 — มีจริง ใช้ได้

- **ทำอะไร:** อธิบายคำสั่งทั้งหมด ลำดับที่ต้องรัน และบอกว่าตัวไหนยังไม่ได้สร้าง

- **เขียนไฟล์:** 👁 ไม่เขียนอะไรเลย

### ✅ `/design:init` — มีจริง ใช้ได้

- **ทำอะไร:** ตรวจว่าของจาก `req` ครบไหม ถ้าขาด **หยุดพร้อมบอกพาธที่มันหา ห้ามเดาเนื้อหาแล้วเดินต่อ** แล้วสร้างไฟล์สถานะ
- **ตัวอย่าง:** `/design:init`
- **เขียนไฟล์:** `<state-dir>/design/design.state.json` + โฟลเดอร์ `modules/` · **ค่าเริ่มต้นไม่เขียน** ต้องอนุมัติก่อนถึงจะเขียนจริง
- **รหัสจบ:** `0` = ของครบ · `2` = ของจาก `req` ขาดหรือผิดรูป ไม่เขียนอะไรเลย
- **อ่านอะไร:** `spec.json` ของ `req` ไฟล์เดียว (ไม่ใช่ `requirements.json` ตาม §3.1 เดิม — ดูเหตุผลใน `init.md`)
- **ของที่ `req` ไม่มีให้:** `stakeholders` กับ `okr` — จะรายงานทุกครั้ง และบันทึก `Q-STAKEHOLDERS` ที่บล็อก `rbac` ไว้ให้

---

### ✅ `/design:overview` — มีจริง ใช้ได้

- **ทำอะไร:** บทนำ + ภาพรวมระบบ (เอกสารหัวข้อ 1–2) — ขอบเขต ข้อจำกัด ข้อสมมติ และแผนภาพบริบท DFD 0
- **ตัวอย่าง:** `/design:overview`
- **เขียนไฟล์:** `docs/design/01-introduction.md` · `docs/design/02-system-overview.md` · **ค่าเริ่มต้นไม่เขียน** ต้องอนุมัติก่อน
- **รหัสจบ:** `0` = ผ่าน DoD · `1` = มี `context.json` แต่ไม่ผ่าน (บอกทีละข้อพร้อม id ที่ผิด) · `2` = ยังไม่ได้รัน `init` หรือยังไม่มี `context.json`
- **ใครเขียน `context.json`:** เจ้าของกับโมเดลร่วมกัน **สคริปต์ไม่แต่งเนื้อหาให้** มันตรวจกับเรนเดอร์เท่านั้น
- **ด่านที่ตรวจ:** OV1 วัตถุประสงค์ · OV2 ขอบเขต · OV3 ข้อจำกัด · OV4 ข้อสมมติ · OV5 แผนภาพสร้างได้ · OV6 ปลายทาง flow มีตัวตน · OV7 ทุกข้อสาวถึง REQ ที่มีจริง · OV8 ผู้ใช้ (เตือนอย่างเดียว)
- **⚠️ OV8 เตือนเสมอ:** `users` ว่างเพราะ `req` ไม่มี stakeholder → ผังผู้เกี่ยวข้องที่ §11 ต้องมียังทำไม่ได้ **และจะเป็น error ตอน `/design:rbac`**
- **เอกสารที่ออกมาห้ามแก้มือ** แก้ที่ `context.json` แล้ว render ใหม่

### ✅ `/design:function` — มีจริง ใช้ได้

- **ทำอะไร:** ความต้องการเชิงหน้าที่ (หัวข้อ 3) — FN · UC · เครื่องสถานะ · แผนภาพ use case + แผนภาพสถานะ
- **ตัวอย่าง:** `/design:function`
- **เขียนไฟล์:** `trace.design.json` · `docs/design/03-functional-requirements.md` · **ค่าเริ่มต้นไม่เขียน**
- **รหัสจบ:** `0` = ผ่าน · `1` = ไม่ผ่าน (บอกทีละข้อพร้อม id) · `2` = `overview` ยังไม่เสร็จ หรือยังไม่มีไฟล์ JSON
- **ใครเขียน JSON:** เจ้าของกับโมเดล · สคริปต์ตรวจกับเรนเดอร์เท่านั้น
- **ด่าน:** FU1 ครอบคลุมทุก REQ · FU2 ไม่มี scope creep · FU3 ทุก FN มี UC · FU4 UC ครบ 5 อย่าง · FU5 อ้าง BR ที่ `is_current` · FU6 STM ถูกรูป · FU7 ไม่มีสถานะตัน · FU8 id ไม่ซ้ำ
- **กฎธุรกิจ:** **อ้าง `BR-xxx@vN` ของ `req` ตรง ๆ ห้ามมินต์ `RULE-###` ขึ้นมาคู่ขนาน** (เจ้าของเคาะ 2026-08-20)
- **`trace.design.json` generate จาก JSON เสมอ** ห้ามเขียนมือ — กราฟจึงขัดกับของที่มันบรรยายไม่ได้

### ✅ `/design:status` 👁 — มีจริง ใช้ได้

- **ทำอะไร:** บอกว่าทำอะไรไปแล้ว ติดอะไร และ **คำสั่งถัดไปคืออะไร** — เป็น**เงื่อนไขจบของลูป** ผลมาจาก exit code ของสคริปต์ ไม่ใช่จากที่โมเดลคิดเอง
- **ตัวอย่าง:** `/design:status`
- **เขียนไฟล์:** 👁 ไม่เขียนอะไรเลย
- **รหัสจบ:** `0` = เสร็จครบ · `1` = ยังมีงานเหลือ **และมีอย่างน้อยหนึ่ง step ที่รันได้เลย** · `2` = **ไม่มีอะไรรันได้เลย** ต้องมีคนตัดสินก่อน
- **บอกคำสั่งถัดไปเสมอ** ไม่ว่ารหัสจะเป็นอะไร · ถ้าไม่มีคำสั่งไหนรันได้ มันบอกว่า**คนต้องทำอะไร**แทน
- **`0` ยากกว่าที่คิด:** ห้ามคืน `0` ขณะยังมีของ `stale` (§9.2 กติกา 6) และห้ามคืน `0` ขณะยังมีคำถามเปิดที่ `blocks` ไม่ว่าง (§19.3) — **ไฟเขียวที่ไม่จริงแย่กว่าไฟแดง**
- **ตัวกันลูปวน:** `attempts` เกิน 3 บน step เดียวกัน → นับเป็น blocked รอคน
- **⚠️ ยังไม่ปิด:** `wiki-index.json` ยังไม่มีคำสั่งไหนสร้าง · คำถามที่ค้างยังไม่มีทางกลับไปหา `req` (D16) ต้องให้คนถือกลับไป — สคริปต์เตือนทั้งสองข้อ ไม่เงียบ

### ⛔ ยังไม่ได้สร้าง — 10 ตัวข้างล่างนี้สั่งไปยังไม่มีอะไรเกิดขึ้น

#### ⛔ `/design:nfr` — ยังไม่มี

- **จะทำอะไร:** ความต้องการเชิงคุณภาพ (หัวข้อ 4) **ทุกข้อต้องมีตัวเลขวัดได้** เขียนว่า "ระบบต้องเร็ว" เฉย ๆ ตัวตรวจ V9 จะแดง
- **ตัวอย่าง:** `/design:nfr`
- **จะเขียน:** `nfr.json`

#### ⛔ `/design:datamodel` — ยังไม่มี

- **จะทำอะไร:** ความต้องการด้านข้อมูล (หัวข้อ 5) ทุก attribute ต้องมี type · บังคับกรอกไหม · กฎตรวจค่า แล้วออก ERD
- **ตัวอย่าง:** `/design:datamodel`
- **จะเขียน:** `datamodel.json`
- **⚠️ ติดข้อที่ยังไม่เคาะ:** D3 (ตารางรหัส/dropdown) · D9 (ย้ายข้อมูลจากระบบเดิม) · D11 (ชั้นความลับ + อายุการเก็บ ตาม PDPA) · D12 (invariant ของ aggregate อยู่ตรงไหน)

#### ⛔ `/design:interface` — ยังไม่มี

- **จะทำอะไร:** อินเทอร์เฟซภายนอกและ API (หัวข้อ 6) ทุกจุดเชื่อมต้องบอก protocol · การยืนยันตัวตน · พังแล้วทำยังไง
- **ตัวอย่าง:** `/design:interface`
- **จะเขียน:** `interfaces.json`
- **⚠️ ติดข้อที่ยังไม่เคาะ:** D2 (รายงาน/เอกสารพิมพ์ `RPT-xxx`) · D4 (ตารางรหัสข้อผิดพลาด) · D5 (แจ้งเตือน อีเมล/LINE/push)

#### ⛔ `/design:rbac` — ยังไม่มี

- **จะทำอะไร:** ตารางสิทธิ์ **4 มิติ** ไม่ใช่แค่ role × screen — ต้องมีขอบเขตข้อมูล (ของใคร) · เงื่อนไขตามสถานะ · ระดับฟิลด์ · การมอบอำนาจแทนกัน
- **ตัวอย่าง:** `/design:rbac`
- **จะเขียน:** `rbac.json`
- **กฎที่แดงบ่อย:** ไม่ประกาศ `scope` → V25 แดง · บังคับใช้แค่ชั้น `ui` → V26 แดง (ซ่อนปุ่มไม่ใช่การคุมสิทธิ์)

#### ⛔ `/design:sitemap` — ยังไม่มี

- **จะทำอะไร:** ทะเบียนหน้าจอ (หัวข้อ 8) ทุกหน้าต้องสาวถึง FN ได้และประกาศสิทธิ์เข้าถึง รวมทั้ง **รายการสถานะที่หน้าจอต้องรองรับ** (ว่าง · กำลังโหลด · ผิดพลาด · ไม่มีสิทธิ์ · ข้อมูลล้น)
- **ตัวอย่าง:** `/design:sitemap`
- **จะเขียน:** `sitemap.json` · `screens.json`
- **⚠️ ติดข้อที่ยังไม่เคาะ:** D7 (ช่องทาง web / mobile / api)

#### ⛔ `/design:scenario` — ยังไม่มี

- **จะทำอะไร:** ตารางสาวกลับ (RTM) + สถานการณ์ทดสอบ (หัวข้อ 7) ทุก FN และ NFR ต้องมีอย่างน้อย 1 สถานการณ์ที่ระบุผลลัพธ์ชัด
- **ตัวอย่าง:** `/design:scenario`
- **จะเขียน:** `scenarios.json` · `trace.design.json`
- **⚠️ ติดข้อที่ยังไม่เคาะ:** D15 (ใครเป็นคนออกข้อมูลทดสอบ design หรือ qa)

#### ⛔ `/design:change` — ยังไม่มี

- **จะทำอะไร:** รับ change-set จาก `req` แล้วไล่กราฟหา **ทุกชิ้นที่กระทบทุกระดับความลึก** ไม่ใช่แค่เพื่อนบ้านชั้นเดียว แล้วปั๊ม `stale`
- **ตัวอย่าง:** `/design:change`
- **จะเขียน:** รายการ stale · `CHANGELOG.md`
- **กติกา:** ของที่ถูกลบ **ห้ามลบจริง** ให้เปลี่ยนเป็น `deprecated` พร้อมเหตุผล เพื่อเก็บร่องรอยไว้

#### ⛔ `/design:trace` — ยังไม่มี

- **จะทำอะไร:** ถามกราฟความสัมพันธ์ เช่น "หน้าจอ SCR-007 มาจาก requirement ข้อไหน" หรือ "ถ้า REQ-012 เปลี่ยน กระทบอะไรบ้าง"
- **ตัวอย่าง:** `/design:trace SCR-007`
- **จะเขียน:** 👁 ไม่เขียนอะไร

#### ⛔ `/design:check` — ยังไม่มี

- **จะทำอะไร:** ด่านตรวจ V1–V27 บอกผลรายข้อพร้อมชื่อ ID ที่ผิด เพื่อให้ซ่อมได้ตรงจุดโดยไม่ต้องอ่านทั้งโปรเจกต์
- **ตัวอย่าง:** `/design:check`
- **จะเขียน:** `validation-report.json`

*(`/design:status` ย้ายขึ้นไปอยู่ในกลุ่มที่ใช้ได้แล้ว)*

#### ⛔ `/design:export` — ยังไม่มี

- **จะทำอะไร:** เรนเดอร์เอกสารฉบับลูกค้าออกมาครบทุกหัวข้อตาม §11 รวมตาราง RTM
- **ตัวอย่าง:** `/design:export`
- **จะเขียน:** `.md` / `.docx` ใน `export/`
- **⚠️ ติดข้อที่ยังไม่เคาะ:** D8 (บันทึกการอนุมัติของลูกค้าเก็บที่ไหน)
- **กติกา:** ไฟล์ที่ export ออกไป **ห้ามแก้มือ** แก้แล้วรอบหน้าโดนทับ — ความจริงอยู่ที่ JSON

## ของที่ยังไม่เคาะ แล้วจะทำให้คำสั่งหยุด

สเปกข้อ §16 มี 17 ข้อ แต่ **เคาะแล้วแค่ 2 ข้อ** (D1 ตารางสิทธิ์ · D17 ผัง wiki) ที่เหลือยังเป็นแค่ข้อเสนอ

ตามกติกา **ห้ามเดา** — คำสั่งที่ต้องใช้ข้อมูลจากข้อที่ยังไม่เคาะ จะหยุดถามเจ้าของ ไม่ใช่เลือกให้เอง

## แผนสร้างทีละ step

หนึ่ง step ต่อหนึ่ง session ตามกติกา `docs/progress.json` → `rules[3]`
สถานะจริงอ่านจาก `docs/progress.json` **ห้ามเชื่อตารางนี้**

| Step | ได้อะไร |
|---|---|
| S0 ✅ | โครง plugin + ลงทะเบียน marketplace + help นี้ |
| S1 ✅ | `init` — ตัวอ่านสัญญาจาก `req` + ไฟล์สถานะ + fixture 3 ชุด |
| S2 ✅ | `overview` — `context.json` + ด่าน OV1–OV8 + เรนเดอร์เอกสารหัวข้อ 1–2 พร้อม DFD 0 |
| S3 ✅ | `function` — FN/UC/STM + ด่าน FU1–FU8 + `trace.design.json` ที่ generate เอง |
| S4 ✅ | `status` — เงื่อนไขจบของลูป exit 0/1/2 · **ปิด Milestone 1 แล้ว** |
| S5–S7 | `datamodel` · `scenario` · `check` — พิสูจน์ว่าด่านจับของที่ขาดได้จริง |
| S8–S11 | `sitemap` · `interface` · `nfr` · `export` — พิสูจน์ว่าลูกค้าอ่านรู้เรื่อง |
| S12–S14 | `rbac` · `change` · `trace` — สิทธิ์และการเปลี่ยนแปลง |
