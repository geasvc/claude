# Dev Plugin — Requirement Specification

> **สถานะ:** Draft v0.1 (สำหรับใช้เป็นโจทย์ในการสร้าง plugin)
> **ผู้เขียนความต้องการ:** User
> **ขอบเขตเอกสารนี้:** ระบุ *ว่าต้องทำอะไร* ไม่ระบุ *ว่าเขียนโค้ดอย่างไร*
> **เอกสารที่ต้องอ่านคู่กัน:** Design Plugin Requirement Specification (§3, §6, §19)

---

## 0. สรุปย่อสำหรับผู้เรียน

Dev Plugin คือ **ตัวแปลงเอกสารออกแบบให้กลายเป็นโค้ดที่รันได้ โดยที่ยังสาวกลับถึงความต้องการเดิมได้ตลอด**

**Analogy:** คิดถึงหัวหน้าช่างที่รับแบบก่อสร้างมาจากสถาปนิก
- ต้องดูก่อนว่างานนี้ใช้ช่างสายไหน — ช่างไฟ ช่างประปา ช่างปูน (นี่คือการเลือก skill ให้ถูก)
- ต้องวางผังไซต์ก่อนลงมือ ว่าของอะไรกองตรงไหน (นี่คือ file structure)
- ต้องเดินน้ำเดินไฟก่อนสร้างจริง (นี่คือ database, redis, queue, docker)
- ต้องแบ่งเป็นใบสั่งงานที่ *ตรวจรับได้* ไม่ใช่ "ทำห้องน้ำให้หน่อย" แต่เป็น "ติดตั้งสุขภัณฑ์รุ่นนี้ ตรวจรับด้วยการทดสอบแรงดันน้ำ"
- และทุกใบสั่งงานต้องชี้กลับไปที่แบบแปลนได้ว่ามาจากหน้าไหน ไม่งั้นเวลาสถาปนิกแก้แบบ จะไม่มีใครรู้ว่าต้องรื้ออะไร

**หัวใจไม่ใช่ "ให้ AI เขียนโค้ดได้" — AI เขียนโค้ดได้อยู่แล้ว หัวใจคือทำให้โค้ดที่เขียนออกมา *ตรวจสอบย้อนกลับได้* และ *ทำต่อได้ในรอบหน้า***

## 1. เป้าหมาย และ Non-Goals

### 1.1 เป้าหมาย

| ID | เป้าหมาย | วัดผลอย่างไร |
|---|---|---|
| G1 | รับ spec จาก design plugin แล้วพัฒนาต่อได้โดยไม่ต้องถามซ้ำในเรื่องที่ design ตอบไว้แล้ว | ไม่มีคำถามที่คำตอบอยู่ใน design artifact แล้ว |
| G2 | รองรับหลาย framework ในโปรเจกต์เดียวกัน (.NET / Vue / Next.js / อื่น ๆ) | โปรเจกต์ที่มี API .NET + Web Next.js ทำงานได้ในโครงเดียว |
| G3 | เลือก skill ที่ถูกต้องตาม stack โดยไม่เดา | ทุกการเลือก skill มีที่มาบันทึกไว้ |
| G4 | กำหนดและบังคับใช้ file structure ได้ | ไฟล์จริงบนดิสก์ตรงกับผังที่ประกาศไว้ |
| G5 | ทุกไฟล์โค้ดสาวกลับถึง requirement ต้นทางได้ | ตอบได้ว่าคลาสนี้มาจาก REQ ข้อไหน |
| G6 | ทดสอบรันด้วย Docker ได้ครบทุก dependency | `compose up` แล้วระบบขึ้นครบ |
| G7 | ทำงานต่อเนื่องข้าม session ได้ | เปิดใหม่แล้วรู้ว่าทำถึง task ไหน |
| G8 | ส่งต่อให้ QA ได้โดยข้อมูลไม่หาย | qa รู้ว่าต้องเทสอะไร ที่ไฟล์ไหน ด้วยคำสั่งอะไร |

### 1.2 Non-Goals

- ไม่เก็บ requirement เอง (req plugin)
- ไม่ออกแบบระบบเอง — ถ้า spec ไม่ครบ ต้องถามกลับ ไม่ใช่ออกแบบเติมเอง
- ไม่รัน test suite เต็มรูปแบบและตัดสินคุณภาพ (qa plugin) — dev รันแค่ verify ระดับ task
- ไม่ทำ deployment จริงขึ้น production (นอกขอบเขต marketplace)
- ไม่ทำ UI/UX design — รับ mockup มาแปลงเป็นโค้ด
- ไม่จัดการ infrastructure จริง (VPS, DNS, TLS) — จบที่ Docker Compose สำหรับทดสอบ

## 2. ผู้เกี่ยวข้อง

| Actor | ต้องการอะไร |
|---|---|
| Developer (มนุษย์) | สั่งงาน ตรวจงาน แก้โค้ดเองได้โดยไม่ถูก agent ทับ |
| AI Agent (dev) | รู้ว่าทำ task ไหนอยู่ ใช้ skill ไหน เขียนไฟล์ที่ไหน |
| AI Agent (qa) | รู้ว่าโค้ดไหนตอบ scenario ไหน รันเทสยังไง |
| AI Agent (design) | รับ feedback กลับว่า spec ตรงไหนทำจริงไม่ได้ |
| ผู้ตรวจ/ลูกค้า | เห็นได้ว่าฟีเจอร์ที่ขอไป พัฒนาแล้วหรือยัง อยู่ตรงไหน |

## 3. ตำแหน่งใน Marketplace และสัญญากับ Plugin อื่น

```
req ──▶ design ──┬──▶ mockup ──┐
                 │             ▼
                 └───────────▶ dev ──▶ qa ──▶ deliver
                 ▲                      │
                 └──── back-channel ────┘
```

### 3.1 Inbound Contract (dev ← design, mockup)

| ต้องอ่านได้ | ใช้ทำอะไร | จำเป็น |
|---|---|---|
| รายการฟังก์ชันและ use case | แตกเป็น task | บังคับ |
| แบบจำลองข้อมูล + invariant ของ aggregate | สร้าง entity / migration | บังคับ |
| รายการหน้าจอ + ฟิลด์ + action | สร้าง UI | บังคับถ้ามี UI |
| สัญญา API และการเชื่อมต่อภายนอก | สร้าง endpoint / client | บังคับถ้ามี API |
| ผังสถานะ | บังคับใช้ state transition ใน domain | บังคับถ้ามี |
| ตารางสิทธิ์ | บังคับ authorization | บังคับ |
| Test scenario | ใช้เป็นแนวเขียน verify | บังคับ |
| Mockup | แปลงเป็น UI จริง | ถ้ามี |
| กราฟ trace ของ design | ใช้ต่อ edge ของตัวเอง | บังคับ |

**กติกาเหล็ก:** ถ้า input บังคับขาด → **หยุด แล้วเปิด question กลับไปที่ design ห้ามออกแบบเติมเอง**
โค้ดที่เขียนจาก spec ที่ agent เดาขึ้นมาเอง คือหนี้ที่ไม่มีใครรู้ว่ามีอยู่

### 3.2 Outbound Contract (dev → downstream)

| ผู้รับ | ต้องได้อะไร |
|---|---|
| `qa` | แผนที่ว่า scenario ไหน ↔ โค้ดไฟล์ไหน ↔ รันเทสด้วยคำสั่งอะไร, วิธียกระบบขึ้นด้วย Docker, ข้อมูลตั้งต้นสำหรับทดสอบ |
| `deliver` | สถานะความคืบหน้าเทียบกับ requirement, รายการที่ทำแล้ว/ยังไม่ทำ/ทำแบบต่างจาก spec |
| `design` | คำถามและการตัดสินใจที่เกิดตอนลงมือจริง (back-channel) |

### 3.3 กติกาความเข้ากันได้

เหมือน design plugin ทุกประการ — `schemaVersion` ทุกไฟล์, เพิ่ม field ได้/ลบต้องขึ้น major, มี `extensions` ให้ plugin อนาคต, ทนต่อ field ที่ไม่รู้จัก

## 4. หลักการออกแบบ

| # | หลักการ | เหตุผล |
|---|---|---|
| P1 | **JSON = สิ่งที่เครื่องต้องตัดสิน / Markdown = ความรู้ที่คนและ AI ต้องอ่าน** | สืบทอดจาก design plugin |
| P2 | **โค้ดคือ source of truth ของพฤติกรรม — spec คือ source of truth ของเจตนา** | ต่างจาก design ที่ JSON เป็นใหญ่ ตรงนี้ต้องยอมรับว่าโค้ดกับ spec หลุดกันได้ จึงต้องมีตัวจับ drift |
| P3 | **ห้ามเขียนทับโค้ดที่มนุษย์แก้เอง** | ข้อที่ยากที่สุดของ plugin นี้ (ดู §7.3) |
| P4 | **ไม่เดา stack ไม่เดา skill ไม่เดา spec** — ถามแล้วจำ | โปรเจกต์แต่ละตัวไม่เหมือนกัน การเดาผิดครั้งเดียวทำให้ต้องรื้อทั้งโครง |
| P5 | **ความเสร็จตัดสินจากคำสั่งที่รันจริง ไม่ใช่จากการที่ agent บอกว่าเสร็จ** | สืบทอดจาก design plugin |
| P6 | **ถามครั้งเดียว จำตลอดโปรเจกต์** | ถ้าถาม stack ซ้ำทุก session คือ plugin ที่ใช้งานจริงไม่ได้ |
| P7 | **1 ไฟล์ = 1 เจ้าของ ใช้กับ JSON ด้วย** | สืบทอด — dev ห้ามเขียนไฟล์ที่ design หรือ qa เป็นเจ้าของ |
| P8 | **หลีกเลี่ยง abstraction ก่อนเวลา** | ยังไม่ต้องทำ template engine ของตัวเอง ใช้ skill ที่มีอยู่ก่อน |
| P9 | **ทุกไฟล์โค้ดที่สร้างต้องผูก trace ทันทีที่สร้าง ไม่ใช่มาไล่ผูกทีหลัง** | ผูกทีหลัง = ไม่ได้ผูก |

## 5. Artifact ที่ Dev Plugin เป็นเจ้าของ

> ไม่ลงรายละเอียด path — ระบุแค่ว่าต้องมีของอะไรและใครเป็นเจ้าของ

| Artifact | รูปแบบ | หน้าที่ |
|---|---|---|
| Tech Profile | JSON | stack, framework, เวอร์ชัน, server, database, dependency เสริม |
| Skill Routing Map | JSON | เงื่อนไข → skill ที่ต้องเรียก |
| Layout Contract | JSON + Markdown | ผังโฟลเดอร์ที่ประกาศไว้ และเหตุผล |
| Task List | JSON | งานที่แตกจาก spec พร้อม trace / dod / verify / status |
| Implementation Map | JSON | design artifact → ไฟล์โค้ดจริง (node `SRC-###`) |
| Trace (dev) | JSON | edge ที่ dev เป็นคนเพิ่มเท่านั้น |
| Runtime Dependency Map | JSON | dependency → บริการใน Docker + env var |
| Dev Journal | JSONL (append-only) | การตัดสินใจและคำถามที่เกิดตอนลงมือจริง |
| Dev Notes / ADR | Markdown ใน wiki | เหตุผลเชิงสถาปัตยกรรมที่คนต้องอ่าน |

**สิ่งที่ dev ห้ามเขียนเด็ดขาด:** artifact ของ design (spec, scenario), artifact ของ qa (ผลเทส), global wiki

## 6. Tech Profile และ Skill Routing

> นี่คือหัวใจของ plugin นี้ และเป็นส่วนที่โจทย์ตั้งต้นระบุไว้ชัดที่สุด

### 6.1 Tech Profile ต้องเป็นรายชิ้นส่วน ไม่ใช่รายโปรเจกต์

**ข้อผิดพลาดที่ต้องกันตั้งแต่ต้น:** โปรเจกต์เดียวมีได้หลาย stack — API เป็น .NET, Web เป็น Next.js, Mobile เป็น MAUI
ถ้าออกแบบ tech profile เป็นค่าเดียวต่อโปรเจกต์ จะต้องรื้อทั้งชุดตอนเจอโปรเจกต์จริงตัวที่สอง

```json
{
  "schemaVersion": "1.0",
  "components": [
    {
      "id": "CMP-api",
      "kind": "api",
      "language": "csharp",
      "framework": "aspnetcore",
      "version": "8.0",
      "orm": "efcore",
      "skills": ["dotnet-dev"],
      "confirmedBy": "user",
      "confirmedAt": "2026-08-18T09:00:00Z"
    },
    {
      "id": "CMP-web",
      "kind": "web",
      "framework": "nextjs",
      "version": "15",
      "skills": ["vercel-best-practice", "frontend-design"],
      "confirmedBy": "user"
    }
  ],
  "runtime": {
    "database": { "engine": "postgresql", "version": "16" },
    "cache": { "engine": "redis" },
    "queue": { "engine": "rabbitmq" },
    "others": []
  }
}
```

### 6.2 กติกาการได้มาซึ่ง Tech Profile

1. `/dev:init` **ต้องถามผู้ใช้** ไม่ใช่ไปสแกนโค้ดแล้วเดา
2. ถ้าในโฟลเดอร์มีโค้ดอยู่แล้ว ให้ **ตรวจแล้วเสนอ** ว่าน่าจะเป็นอะไร แล้วรอผู้ใช้ยืนยัน
3. ทุก component ต้องมี `confirmedBy` — ถ้าไม่มี ถือว่ายังไม่ผ่านและใช้ทำงานต่อไม่ได้
4. เมื่อยืนยันแล้ว **บันทึกก่อนตอบผู้ใช้** (persist-before-answer) แล้วห้ามถามซ้ำอีก
5. เปลี่ยน stack กลางทางได้ แต่ต้องผ่านคำสั่งเฉพาะ และต้องบันทึกเหตุผลลง journal

### 6.3 Skill Routing

ตารางเงื่อนไข → skill ที่ต้องเรียก ต้องแก้ไขได้ และต้องมีลำดับความสำคัญชัดเจน

| เงื่อนไข | Skill ที่เรียก |
|---|---|
| component เป็น .NET / ASP.NET Core | `dotnet-dev` |
| component เป็น Next.js | skill best practice ของ Next.js/Vercel |
| งานที่แตะหน้าตา UI / HTML / component | `frontend-design` |
| งานสร้างเอกสารส่งลูกค้า | skill ฝั่งเอกสารที่มีอยู่ |
| ไม่มีเงื่อนไขไหนตรง | **ถามผู้ใช้ ห้ามเดา ห้ามทำเอง** |

**กติกาที่ต้องบังคับ**

- Skill routing ต้องประเมิน **ทั้งจาก component และจากประเภทของงาน** เพราะงานเดียวอาจต้องเรียกสอง skill (เช่น สร้างหน้า Razor ใน .NET ต้องใช้ทั้ง `dotnet-dev` และ `frontend-design`)
- ทุกครั้งที่เลือก skill ต้องบันทึกว่าเลือกเพราะเงื่อนไขข้อไหน — เพื่อให้ตรวจย้อนได้ว่าทำไมผลลัพธ์ตอนนั้นเป็นแบบนั้น
- ถ้า skill ที่ควรใช้ไม่ได้ติดตั้งอยู่ ต้องแจ้งผู้ใช้และหยุด **ห้ามทำงานต่อโดยไม่มี skill แล้วแกล้งว่าใช้แล้ว**
- ผู้ใช้ override ได้เสมอ และ override ต้องถูกจำ

## 7. File Structure และ Layout Contract

### 7.1 ผังต้องถูก "ประกาศ" ก่อน ไม่ใช่ "เกิดขึ้นเอง"

ก่อนสร้างไฟล์แรก ต้องมีผังที่ประกาศไว้ก่อน ระบุอย่างน้อย:

- แต่ละ component อยู่ที่ไหน
- ภายใน component แบ่งชั้นอย่างไร (เช่น domain / application / infrastructure / presentation)
- bounded context หรือ module จาก design ไป map กับโฟลเดอร์ไหน
- ของที่ใช้ร่วมกันระหว่าง component อยู่ที่ไหน
- ที่อยู่ของ test
- ที่อยู่ของไฟล์ Docker

**ผังต้อง derive จาก bounded context ของ design ไม่ใช่คิดใหม่** — ถ้าโครงโฟลเดอร์กับโครงโดเมนไม่ตรงกัน คนอ่านโค้ดจะหา entity ไม่เจอตลอดไป

### 7.2 Docker Layout (ตามที่โจทย์กำหนด)

- ไฟล์ compose รวมอยู่ในโฟลเดอร์ docker ที่ระดับ root ของ repo
- Dockerfile อยู่ใต้ project ของแต่ละ component (web / api) ไม่ใช่รวมไว้ที่ root

**ข้อควรระวังที่ต้องระบุไว้ในสเปกตั้งแต่ต้น:** Dockerfile อยู่ใต้ project แต่ build context มักต้องเป็น root เพราะมีโค้ดที่ใช้ร่วมกัน — ดังนั้น compose ต้องระบุ context กับ dockerfile แยกกันคนละค่า ไม่ใช่ชี้ที่เดียวกัน ถ้าไม่ระบุไว้ ผู้เรียนจะเจอปัญหา build ไม่ผ่านแล้วไปแก้ผังจนผิดจากที่ตกลง

### 7.3 Drift Detection และการอยู่ร่วมกับโค้ดที่มนุษย์เขียน

**นี่คือปัญหาที่ยากที่สุดของ plugin นี้ และเป็นจุดที่ทำพลาดแล้วผู้ใช้จะเลิกใช้ทันที**

| ปัญหา | สิ่งที่ต้องมี |
|---|---|
| agent สร้างไฟล์ซ้ำที่ผิดที่ | ตรวจผังจริงเทียบผังที่ประกาศ แล้วรายงานส่วนต่าง |
| agent เขียนทับโค้ดที่มนุษย์แก้เอง | ต้องแยกให้ออกระหว่างของที่ generate ได้กับของที่คนเขียน และของที่คนแก้แล้วต้องได้รับการปกป้อง |
| ไฟล์ถูกย้าย/ลบ แล้ว trace ชี้ไปที่ว่าง | ตรวจว่า path ที่บันทึกไว้ยังมีจริงไหม ถ้าไม่มีให้ทำเครื่องหมายว่าต้องทบทวน |

**ข้อเสนอขั้นต่ำสำหรับ v1:** ก่อนเขียนทับไฟล์ที่มีอยู่แล้วเสมอ ต้องเทียบก่อนว่าต่างจากรอบที่แล้วไหม ถ้าต่าง = มีคนแก้ → หยุดแล้วถาม ไม่ใช่ทับ

---

## 8. Runtime Dependency และ Docker

### 8.1 ต้องรู้ว่าระบบต้องพึ่งอะไรบ้าง

ต้องอ่านจาก design (การเชื่อมต่อภายนอก) บวกกับที่ผู้ใช้ระบุ แล้วสรุปให้ครบว่าต้องมี database อะไร cache อะไร message queue อะไร storage อะไร และบริการเสริมอื่นใด

**สิ่งที่โจทย์ตั้งต้นยังไม่ได้พูดถึงแต่ต้องมี:** ทุก dependency ต้องมาพร้อม **สัญญาการตั้งค่า** — ตัวแปรสภาพแวดล้อมชื่ออะไร ค่าเริ่มต้นคืออะไร อันไหนเป็นความลับ
ถ้าไม่มีข้อนี้ compose จะขึ้นได้บนเครื่องคนเขียนเท่านั้น แล้วพังบนเครื่องคนอื่นทุกครั้ง

### 8.2 ข้อกำหนดของ Compose ที่สร้างออกมา

- ต้องยกระบบขึ้นได้ครบด้วยคำสั่งเดียว
- ทุกบริการต้องมีการตรวจว่าพร้อมใช้งานจริง ไม่ใช่แค่ container ขึ้น (สั่ง API ก่อน database พร้อมคือปัญหาคลาสสิก)
- ต้องแยกค่าที่เป็นความลับออกจากไฟล์ที่ commit ได้ และต้องมีไฟล์ตัวอย่างให้คนอื่นทำตาม
- ต้องมีวิธีล้างข้อมูลกลับไปเป็นสถานะเริ่มต้น เพราะ QA จะต้องใช้
- Dependency ที่ประกาศไว้ใน tech profile กับที่มีจริงใน compose **ต้องตรงกันสองทาง** ขาดหรือเกินถือว่าไม่ผ่าน

## 9. การแตกงานและ Agent Loop

### 9.1 Task ต้องตรวจรับได้ ไม่ใช่แค่บรรยาย

ทุก task ต้องมีอย่างน้อย: สิ่งที่ต้องทำ, trace กลับไปที่ design artifact, เงื่อนไขว่าเสร็จคืออะไร (ระบุชื่อ test ที่ต้องผ่าน), **คำสั่งที่รันแล้วรู้ผลจริง**, สถานะ, จำนวนครั้งที่พยายาม, และสิ่งที่ติดขัดอยู่

```json
{
  "id": "TSK-014",
  "title": "บังคับกฎวงเงินสูงสุดตอนสร้างคำขอสินเชื่อ",
  "component": "CMP-api",
  "trace": ["REQ-012", "FN-004", "RULE-014"],
  "dod": ["LoanApplicationTests.RejectsWhenExceedsCreditLimit"],
  "verify": "dotnet test --filter FullyQualifiedName~LoanApplicationTests",
  "status": "in_progress",
  "attempts": 1,
  "blocked_by": []
}
```

**กติกา:** task ที่ไม่มี `verify` ที่รันได้จริง ห้ามเปลี่ยนสถานะเป็นเสร็จได้เลย ต่อให้โค้ดดูถูกแค่ไหน

### 9.2 เงื่อนไขออกจากลูป

- ความคืบหน้าตัดสินจาก script ที่ให้ผลเหมือนเดิมทุกครั้ง ไม่ใช่จากการที่ agent ประเมินตัวเอง
- ต้องบอกได้เสมอว่า task ถัดไปที่ควรทำคืออะไร
- พยายามซ้ำเกินจำนวนที่กำหนดในงานเดิม → เปลี่ยนเป็นติดขัด แล้วรอมนุษย์ ห้ามวนต่อ
- ห้ามข้าม task ที่ติดขัดไปทำตัวอื่นเงียบ ๆ โดยไม่รายงาน

## 10. Traceability ที่ Dev ต้องเพิ่ม

Dev เป็นเจ้าของ node ประเภท `SRC-###` (ไฟล์ / คลาส / module ที่พัฒนาจริง) และเพิ่ม edge ได้อย่างเดียว **ห้ามแตะ edge ของ design หรือ qa**

ความสัมพันธ์ที่ต้องบันทึก:

```
FN / SCR / API / RULE ──implementedBy──▶ SRC
SRC ──belongsTo──▶ CMP (component)
TSK ──produces──▶ SRC
```

**คำถามที่ต้องตอบได้หลังจากมี dev แล้ว**

1. คลาสนี้มาจากความต้องการข้อไหน
2. ความต้องการข้อนี้พัฒนาแล้วหรือยัง อยู่ไฟล์ไหน
3. ถ้าแก้ความต้องการข้อนี้ ต้องแก้โค้ดกี่ไฟล์
4. มีโค้ดไฟล์ไหนที่ไม่ได้มาจาก spec ใดเลย
5. มี spec ข้อไหนที่ยังไม่มีโค้ดรองรับ

ข้อ 4 คือตัวจับงานที่ทำเกินจาก spec ซึ่งเป็นสาเหตุที่โปรเจกต์บานโดยไม่มีใครรู้ตัว

---

## 11. รับการเปลี่ยนแปลงจาก Design

เมื่อ design แจ้งว่ามีอะไรเปลี่ยน dev ต้อง:

1. ไล่ตามกราฟหา task และไฟล์โค้ดที่ผูกอยู่กับ artifact ที่เปลี่ยน
2. ทำเครื่องหมายว่ารายการเหล่านั้นล้าสมัย พร้อมระบุว่าล้าสมัยเพราะอะไร
3. รายงานผลกระทบเป็นตัวเลขให้มนุษย์ตัดสินใจ ว่ากระทบกี่ task กี่ไฟล์
4. **ห้ามแก้โค้ดอัตโนมัติทันที** ต้องให้มนุษย์อนุมัติก่อนว่าจะแก้ตามหรือจะคุยกลับ
5. ตราบใดที่ยังมีของล้าสมัยค้าง ถือว่างานยังไม่เสร็จ

## 13. ความต่อเนื่องข้าม Session และข้าม Plugin

สืบทอดกลไกทั้งหมดจาก design plugin §19 และเพิ่มประเด็นเฉพาะของ dev

| รอยรั่ว | อาการเฉพาะของ dev | สิ่งที่ต้องมี |
|---|---|---|
| ถาม stack ซ้ำ | เปิด session ใหม่แล้วถามอีกว่าใช้ .NET เวอร์ชันอะไร | tech profile ต้องถูกอ่านก่อนเริ่มงานเสมอ |
| ลืมว่าทำไมทำแบบนั้น | รอบหน้ามาแก้กลับเป็นแบบเดิมที่เคยลองแล้วไม่เวิร์ก | ทุกการเบี่ยงจาก spec ต้องบันทึกเหตุผล |
| โค้ดที่มนุษย์แก้หาย | agent สร้างใหม่ทับ | ต้องตรวจก่อนเขียนทับเสมอ |
| ผลเทสของ QA หาย | dev regenerate ไฟล์ที่ qa เขียนผลไว้ | 1 ไฟล์ 1 เจ้าของ |
| ความรู้ตอนลงมือตายในรอบงาน | dev พบว่า spec ทำไม่ได้จริง แก้ไปแล้วไม่มีใครรู้ | back-channel ส่งกลับ design |

**กฎ persist-before-answer ใช้กับ dev ด้วย:** ห้ามตอบว่า "เข้าใจแล้ว จะใช้ PostgreSQL นะครับ" ถ้ายังไม่ได้บันทึกลงไฟล์

## 14. รองรับ Plugin และ Stack ที่ยังไม่มี

| กลไก | รายละเอียด |
|---|---|
| Framework ใหม่ | เพิ่มได้ด้วยการเพิ่มรายการใน skill routing ไม่ต้องแก้แกนกลาง |
| Skill ใหม่ | ประกาศเงื่อนไขแล้วใช้ได้ทันที |
| Plugin ใหม่ | ทุก artifact มีที่ว่างให้แนบข้อมูลเพิ่มโดยไม่กระทบ schema กลาง |
| การบังคับสิทธิ์เขียน | ใช้ hook ตรวจตอน commit ไม่ใช่หวังว่า prompt จะคุมอยู่ |

**ข้อทดสอบว่าออกแบบดีพอไหม:** เพิ่มการรองรับ Vue เข้าไปในระบบ ต้องแตะแค่ตาราง routing กับ tech profile ถ้าต้องไปแก้ตรรกะการแตก task หรือระบบ trace แปลว่ายังผูกกับ framework มากเกินไป

## 17. ลำดับการสร้าง

**Milestone 1 — รู้จักโปรเจกต์**
ตั้งต้น → ถามและจำ tech profile → เลือก skill ได้ถูก → บอกสถานะได้
*เป้าหมาย: พิสูจน์ว่าถามครั้งเดียวแล้วจำได้จริง และเลือก skill ถูกโดยไม่เดา*

**Milestone 2 — แตกงานและทำได้จริง**
ประกาศผัง → แตก task จาก spec → ทำ task พร้อม verify
*เป้าหมาย: พิสูจน์ว่าความเสร็จตัดสินจากคำสั่ง ไม่ใช่จากคำพูดของ agent*

**Milestone 3 — ยกระบบขึ้นได้**
สรุป dependency → สร้าง Docker → ยกระบบขึ้นครบ
*เป้าหมาย: พิสูจน์ว่ารันได้บนเครื่องคนอื่น ไม่ใช่แค่เครื่องตัวเอง*

## 18. Acceptance Checklist สำหรับตรวจงานผู้เรียน

- [ ] เริ่มโปรเจกต์ใหม่ — plugin ถามเรื่อง stack ก่อน ไม่เดาเอง
- [ ] ตอบเรื่อง stack ไปแล้ว ปิดแล้วเปิดใหม่ — ไม่ถามซ้ำ
- [ ] สั่งงานที่เกี่ยวกับหน้าเว็บ — เรียก skill ฝั่ง frontend ด้วย ไม่ใช่เรียกแค่ skill ของ backend
- [ ] สั่งงานบน stack ที่ไม่มีในตาราง routing — หยุดแล้วถาม ไม่มั่วทำต่อ
- [ ] แก้ไฟล์โค้ดด้วยมือ แล้วสั่ง agent ทำงานเดิมซ้ำ — ต้องไม่ทับงานที่แก้ไว้
- [ ] ย้ายไฟล์ไปผิดที่จากผังที่ประกาศ แล้วสั่งตรวจ — ต้องจับได้
- [ ] ถามว่าคลาสนี้มาจาก requirement ข้อไหน — ตอบได้จากข้อมูลที่บันทึก ไม่ใช่จากการอ่านโค้ดเดา
- [ ] เพิ่ม redis เข้า tech profile แล้วไม่ใส่ใน Docker — ต้องไม่ผ่านการตรวจ
- [ ] สั่งยกระบบขึ้นด้วยคำสั่งเดียว บนเครื่องที่ยังไม่เคยรัน — ต้องขึ้นครบ
- [ ] แก้ requirement ที่ต้นทางหนึ่งข้อ — ระบุได้ว่ากระทบ task และไฟล์ไหนบ้าง และไม่แก้โค้ดเองทันที
- [ ] มาร์ค task ว่าเสร็จทั้งที่คำสั่งตรวจสอบไม่ผ่าน — ระบบต้องปฏิเสธ
- [ ] เพิ่มการรองรับ framework ใหม่หนึ่งตัว — ต้องแตะแค่ตาราง routing ไม่ต้องรื้อแกน

### 18.1 Cold Start Test

ปิดทุกอย่าง เปิดใหม่โดยมีแค่ไฟล์ในดิสก์ แล้วถาม

1. โปรเจกต์นี้ใช้ stack อะไรบ้าง และใครเป็นคนยืนยัน
2. ตอนนี้ทำ task ไหนอยู่ ค้างอะไร
3. ฟีเจอร์นี้พัฒนาแล้วหรือยัง อยู่ไฟล์ไหน มาจากความต้องการข้อไหน
4. ทำไมตรงนี้ถึงทำต่างจาก spec
5. มีคำถามอะไรที่ต้องส่งกลับไปถามฝั่งออกแบบหรือลูกค้า

ตอบได้ครบห้าข้อโดยไม่ต้องเล่าอะไรเพิ่ม = ใช้ได้จริง

## ภาคผนวก: อภิธานศัพท์เฉพาะของ Dev Plugin

| คำ | ความหมาย |
|---|---|
| Component | ชิ้นส่วนที่มี stack ของตัวเอง เช่น API, Web, Mobile — โปรเจกต์เดียวมีได้หลายชิ้น |
| Tech Profile | บันทึกว่าแต่ละ component ใช้อะไร ผู้ใช้ยืนยันแล้วเมื่อไร |
| Skill Routing | กติกาว่าเงื่อนไขแบบไหนต้องเรียก skill ตัวไหน |
| Layout Contract | ผังโฟลเดอร์ที่ประกาศไว้ล่วงหน้าและใช้ตรวจของจริงได้ |
| Drift | สภาพที่ของจริงกับที่ประกาศไว้ไม่ตรงกัน |
| Verify | คำสั่งที่รันแล้วรู้ผลจริงว่างานนั้นเสร็จหรือไม่ |
| Back-channel | ช่องทางส่งการตัดสินใจและคำถามกลับไปยังต้นน้ำ |
