## ข้อมูลตัวอย่างจากลูกค้า — ระบบจัดคนละแบบกับเอกสาร

ไฟล์ข้อมูลจริง (export จากระบบเดิม, ตารางเคสจริง) **ไม่ถูกนับเป็นเอกสาร** เพราะมันตอบคนละคำถาม

| | เอกสาร / รูป / แชท | ข้อมูลตัวอย่าง |
|---|---|---|
| ตอบว่า | **"กฎคืออะไร"** | **"เลขที่ถูกคือเท่าไหร่"** |

**ระบบจะไม่ร่างกฎจากไฟล์ข้อมูลเด็ดขาด** — เพราะกฎที่เดาจากข้อมูล 500 แถว จะอธิบายได้แค่ข้อมูลชุดนั้นชุดเดียว
ทำได้แค่**ตั้งข้อสงสัยพร้อมบอกตัวหาร** แล้วเอาเข้ารอบยืนยันเหมือนทุกเรื่อง เช่น

> *"ในไฟล์ 47 แถวจาก 500 ที่ยอดเกิน 1,000 ถูกลด 7% ทั้งหมด — เป็นกฎ หรือบังเอิญ"*
> 1) เป็นกฎ  2) บังเอิญ  3) ยังไม่แน่ใจ ต้องถามลูกค้า → 🛑 การ์ดแดง

ประโยชน์จริงของมันมาทีหลัง: เป็น**เลขเฉลย**ที่ลูกค้าเชื่ออยู่แล้ว เอาไว้ทาบกับเลขที่เราคำนวณเอง
ตรงไหนไม่ตรง = ตรงนั้นมีกฎที่ยังไม่มีใครบอก · **ระหว่างนี้มันจะนอนเฉย ๆ ยังไม่ถูกใช้ ซึ่งถูกต้องแล้ว ไม่ใช่งานค้าง**

### ⚠️ ระบบจะถามเรื่องข้อมูลส่วนบุคคล **ก่อน** เขียนไฟล์

ไฟล์ข้อมูลจริงมักมีชื่อคน เบอร์โทร เลขบัตร และ `docs/` อยู่ใต้ git
**เขียนลงไปครั้งเดียวคืออยู่ใน history ตลอดไป — ลบไฟล์ทีหลังก็ไม่ได้ลบออกจาก history**

ระบบจึงเสนอปิดบังคอลัมน์ที่เป็นข้อมูลส่วนบุคคลให้ก่อน แล้วบันทึกคำตอบไว้ว่าปิดบังหรือไม่ปิด
ตอบว่า "ไม่ต้องปิด" ได้ ถ้าตั้งใจ — แต่**ระบบจะไม่ตัดสินใจแทน และจะไม่เขียนไฟล์โดยไม่ถาม**

## การ์ดแดง 🛑 คืออะไร

ตอบว่า **"ยังไม่แน่ใจ / ต้องถามลูกค้า"** เมื่อไหร่ → เกิดการ์ดแดง `Q-xxx` ทันที

**นี่คือคำตอบที่มีค่าที่สุด ไม่ใช่ความล้มเหลว** — และการ์ดแดงที่ยังเปิดอยู่ **บล็อกไม่ให้จบ Phase 1**
เพื่อกันไม่ให้เดาแล้วไปเจอตอนเขียนโค้ดไปครึ่งทางแล้ว

ต่างจาก **คิวส่งต่อ ⏭ (`DQ-xxx`)** ซึ่งคือคำถามที่ *รู้ว่าจะตอบยังไง แต่ต้องเห็น entity ก่อน*
(เช่น ปัดกี่ตำแหน่ง, `decimal(p,s)` เท่าไหร่) — พวกนี้**ไม่บล็อก Phase 1** ไปตอบตอน Phase 2

## สัญญาการคำนวณ — `/req:calc`

**กฎบอกว่าต้องเป็นอะไร สัญญาบอกว่าคิดเลขยังไง** และสองอย่างนี้แยกกันเพราะกฎที่ถูกต้องข้อเดียว
ให้คนสองคนเขียนโค้ดได้ผลต่างกันหลักสตางค์ — ทุกครั้งที่เกิด สาวกลับได้ว่ามีหัวข้อหนึ่งที่ไม่มีใครเขียนไว้

`/req:calc BR-xxx` จะถามทีละหัวข้อ **7 อย่าง** แล้วเก็บเป็นโหนด `CALC-xxx` ผูกกับกฎเวอร์ชันนั้น

| ถาม | ตัวอย่าง | ถ้าปล่อยว่าง |
|---|---|---|
| สูตร | `total = base_fee + surcharge(distance_km)` | ต่างคนต่างจำสูตร |
| input + ชนิด | `base_fee money(2)` · `distance_km int` | ปนชนิด ตัดทศนิยมทิ้งเงียบ ๆ |
| ชนิดตัวเลข | `decimal` | **ห้าม float** — float เก็บ 0.1 ไม่ได้ เงินเพี้ยนแล้วแก้ปลายทางไม่ได้ |
| วิธีปัด | `HALF_UP` | .NET ปัดครึ่งไปเลขคู่เป็นค่าเริ่มต้น |
| **ปัดตรงไหน** | ปัดทุกจุดที่เกิดค่าเงิน | ปัดทุกงวด vs ปัดตอนท้าย ต่างกันหลักบาท |
| เศษที่เหลือ | งวดสุดท้ายรับเศษให้ยอดปิดที่ 0 | ยอดค้าง 0.03 บาทตลอดกาล |
| ขอบเขต | `n = 0` · `r = 0` · ค่าต่ำสุด | หารด้วยศูนย์ตอนขึ้นระบบจริง |

**คำสั่งนี้ไม่คิดเลขให้** — เก็บแค่สัญญา ส่วนการกดเลขจริงแล้วให้คนยืนยันเป็นงานของ `/req:golden` (หัวข้อถัดไป)
ตอบ "ยังไม่แน่ใจ" → การ์ดแดง 🛑 · ข้อที่ต้องเห็น entity ก่อน → คิวส่งต่อ ⏭ (กติกาเดิม ไม่มีอะไรใหม่)

### ตัวอย่างเดินจริง — BR-06 ของ MiniLoan

หยิบจาก `docs/requirement/requirements.md` ของจริง ไม่ได้แต่งขึ้น:

> **BR-06 การคำนวณงวดผ่อน (Amortization)**
> - งวดผ่อนเท่ากันทุกงวด (EMI): `EMI = P × r × (1+r)^n / ((1+r)^n − 1)`
> - แต่ละงวดแยกเป็นดอกเบี้ย (ยอดคงเหลือ × r) และเงินต้น (EMI − ดอกเบี้ย)
> - งวดสุดท้ายปัดเศษให้ยอดคงเหลือเป็น 0 พอดี

อ่านผ่าน ๆ เหมือนครบแล้ว — มีสูตร มีนิยามตัวแปร มีกติกางวดสุดท้าย · **แต่เทียบกับ 7 ช่องแล้วได้แค่ 3**

| ช่อง | BR-06 เขียนไว้ไหม |
|---|---|
| สูตร | ✅ `EMI = P × r × (1+r)^n / ((1+r)^n − 1)` |
| input + ชนิด | 🟡 มีชื่อ (`P` `r` `n`) แต่**ไม่มีชนิด** — `r` เป็น `rate(10)` หรือ `decimal(9,6)` |
| ชนิดตัวเลข | ❌ **ไม่ได้เขียน** |
| วิธีปัด | ❌ **ไม่ได้เขียน** |
| **ปัดตรงไหน** | ❌ **ไม่ได้เขียน** ← ช่องที่แพงที่สุด |
| เศษที่เหลือ | ✅ "งวดสุดท้ายปัดให้ยอดเป็น 0 พอดี" |
| ขอบเขต | ❌ ไม่ได้เขียน — `n = 6` ต่ำสุดตาม BR-04 แต่ `r = 0` (ดอกเบี้ย 0%) จะหารด้วยศูนย์ |

**ช่อง "ปัดตรงไหน" ช่องเดียวเปลี่ยนยอดจริง** — ไม่ต้องเชื่อ ลองรันเอง (P=100,000 · n=12 · 25%/ปี ตาม BR-04):

```js
const P = 100000, n = 12, r = 0.25 / 12;              // MiniLoan BR-04 + BR-06
const emi = (P * r * (1 + r) ** n) / ((1 + r) ** n - 1);
const r2 = (x) => Math.round(x * 100) / 100;          // HALF_UP 2 ตำแหน่ง

const walk = (round) => {                             // round = ปัดทุกงวดหรือไม่
  const f = round ? r2 : (x) => x, pay = round ? r2(emi) : emi;
  let bal = P, total = 0;
  for (let i = 1; i < n; i++) { bal = f(bal - (pay - f(bal * r))); total += pay; }
  const last = f(bal + f(bal * r));
  return { pay: r2(pay), last: r2(last), total: r2(total + last) };
};
console.log("ปัดทุกงวด ", walk(true));
console.log("ปัดตอนท้าย", walk(false));
```

```
ปัดทุกงวด  { pay: 9504.42, last: 9504.43, total: 114053.05 }
ปัดตอนท้าย { pay: 9504.42, last: 9504.42, total: 114053.04 }
```

**สูตรเดียวกัน กฎเดียวกัน ผลต่างกัน** · งวดสุดท้าย `9,504.43` กับ `9,504.42` — คือเลขที่สไลด์ยกเป็นตัวอย่าง
และไม่มีใครรู้จนกระทั่งกดเลข · ยอดรวมต่าง 1 สตางค์ต่อสัญญา คูณด้วยจำนวนสัญญาทั้งพอร์ตแล้วเป็นตัวเลขที่บัญชีต้องอธิบาย

**บทสนทนาที่ `/req:calc` จะพาเดิน** — ทีละหัวข้อ ไม่รวบถาม:

```
/req:calc BR-loan-006

1/7 สูตร — ยกมาตรงตัวที่ลูกค้าพูด
    EMI = P × r × (1+r)^n / ((1+r)^n − 1)                    ← มีใน TOR แล้ว ยืนยันไหม

2/7 input + ชนิด
    P  money(2)      เงินต้น
    r  rate(10)      ดอกเบี้ยต่อเดือน = ต่อปี / 12
    n  int           จำนวนงวด 6-60 (BR-04)

3/7 ชนิดตัวเลข      → decimal  ✅   (float ไม่ใช่ตัวเลือก เก็บ 0.1 ไม่ได้)

4/7 วิธีปัด          → HALF_UP ✅

5/7 ปัดตรงไหน       ← หัวข้อที่ TOR ไม่ได้เขียน
    ก) ปัดทุกงวด ทั้งดอกเบี้ยและยอดคงเหลือ  → งวดสุดท้าย 9,504.43
    ข) ไม่ปัดระหว่างทาง ปัดครั้งเดียวตอนท้าย → งวดสุดท้าย 9,504.42
    ค) ยังไม่แน่ใจ → 🛑 การ์ดแดง

6/7 เศษที่เหลือ      → งวดสุดท้ายรับเศษให้ยอดปิดที่ 0  ✅ (TOR เขียนไว้แล้ว)

7/7 ขอบเขต
    n = 6 งวดต่ำสุด · r = 0 (ดอกเบี้ย 0%) → สูตรหารด้วยศูนย์ ต้องตกลงว่าทำยังไง
    → ตอบว่า "ยังไม่เคยมีเคสนี้" = ⏭ คิวส่งต่อ ไม่ใช่เดาให้
```

ข้อ 5 คือเหตุผลทั้งหมดที่คำสั่งนี้มีอยู่ — **ถามเป็นตัวเลือกที่มีเลขกำกับ ไม่ใช่ถามว่า "อยากปัดยังไง"**
เพราะคำถามแรกคนตอบได้ คำถามหลังคนตอบว่า "ก็ปัดตามปกติ" ซึ่งไม่มีความหมาย

**ได้อะไรออกมา:**

```
.aeon/spec.json          + CALC-loan-002@v1  ผูกกับ BR-loan-006@v1
                         + DQ-xxx (decimal(p,s) รอเห็น entity) · Q-xxx ถ้าตอบ "ยังไม่แน่ใจ"
                         + SRC-xxx  บทสนทนารอบนี้ (kind: chat) เป็นที่มาของสัญญา
docs/requirements/REQ-loan-002.md   หัวข้อ "สัญญาการคำนวณ"
docs/wiki/calculations/CALC-loan-002@v1.md   หน้าเต็ม + ลิงก์กลับไปกฎ
```

ขั้นถัดไปคือ `/req:golden CALC-loan-002@v1` — เขียนสคริปต์ รันจริง เอาตารางเลขมาให้เซ็น
**สูตรที่ตกลงแล้วยังไม่ใช่ตัวเลขที่มีใครตรวจ** และถ้าเลขที่รันออกมาไม่ตรงกับที่ลูกค้าเชื่ออยู่
ให้ย้อนมาแก้**สัญญา** ไม่ใช่แก้เลขเฉลย (ลูป L2)

> **สั่งเฉพาะกฎที่มีการคิดเลข** ไม่ต้องสั่งทุกกฎ · และถ้ากฎนั้นมีสัญญาอยู่แล้ว ระบบจะ**ไม่เขียนทับ** แต่บอกว่ามีแล้ว
> (การเปลี่ยนสัญญาคือ "การเปลี่ยนแปลง" ซึ่งเป็นงานของ `/req:change` — หัวข้อ *"เมื่อกฎเปลี่ยน"* ข้างล่าง)

ดูของจริงได้ที่ `plugins/req/scripts/fixtures/clean/docs/requirements/REQ-job-001.md` หัวข้อ *"สัญญาการคำนวณ"*

## เลขเฉลย — `/req:golden`

**สูตรที่ทุกคนเห็นด้วยแล้ว ไม่เท่ากับตัวเลขที่มีใครตรวจแล้ว** — สไลด์ยกตัวอย่าง EMI งวดสุดท้าย 9,504.**43**
ที่ไม่มีใครรู้จนกระทั่งกดเลขจริง · `/req:golden` คือคำสั่งเดียวในชุดที่เป็นชนิด **"พิสูจน์"** ไม่ใช่ "เก็บสิ่งที่คนพูด"

```
/req:golden BR-job-016
→ เขียนสคริปต์ลง .aeon/golden/CALC-job-001@v1.mjs → รันจริง → เอาผลมาให้ดูเป็นตาราง
→ พี่ปูเซ็น → GD-job-001 (verified_by + verified_at)
```

**4 ข้อที่ห้ามละเมิด:**

| ข้อ | ทำไม |
|---|---|
| **ห้ามคิดเลขในหัว** ต้องรันสคริปต์แล้วโชว์ทั้งโค้ดและผล | ผลจากการ "คิด" ของโมเดล แยกไม่ออกจากการเดาที่ฟังดูเข้าท่า |
| **ตัวเลขเป็นข้อเสนอจนกว่าคนจะเซ็น** | `verified_by` ว่าง = สถานะที่ถูกต้อง ไม่ใช่ของค้าง · check #13 แค่เตือน ⚠️ |
| **เลขไม่ตรงสัญญา → แก้สัญญา ไม่ใช่แก้เลข** | แก้เลขให้เข้ากับสูตร = ทำลายตัวตรวจอิสระตัวเดียวที่ Phase 1 มี แบบเงียบ ๆ |
| **ข้อมูลลูกค้าเป็น input ไม่ใช่กฎ** | เอาแถวจริงมาป้อนแล้ว diff — **ตรงไหนไม่ตรง คือกฎที่ยังไม่มีใครบอก** |

ข้อสุดท้ายคือจุดที่ข้อมูลตัวอย่าง 500 แถวจากตอน `/req:capture` **ได้ใช้จริงเป็นครั้งแรก** — มันนอนรออยู่ตั้งแต่ต้น
เพื่อรอวันนี้ ไม่ใช่งานค้างที่ลืม (ตรงกับที่เขียนไว้หัวข้อ *"ข้อมูลตัวอย่างจากลูกค้า"* ข้างบน)

**สคริปต์ไม่ถูกทิ้ง** — เก็บที่ `<state-dir>/golden/<CALC-id>.mjs` เปิดอ่านได้ รันซ้ำได้
เลขที่ไม่มีใครคำนวณซ้ำได้ คือเลขที่อีกหกเดือนไม่มีใครกล้ายืนยัน

ดูของจริงได้ที่ `plugins/req/scripts/fixtures/clean/` — สคริปต์อยู่ที่ `.aeon/golden/CALC-job-001@v1.mjs`
และตารางเลขเฉลย 7 แถวอยู่ในเอกสาร `docs/requirements/REQ-job-001.md`

## เมื่อกฎเปลี่ยน — `/req:change` และการจับได้ตั้งแต่ `/req:capture`

### ความพังที่เงียบที่สุดในระบบ ที่รอบนี้ปิดไป

ลูกค้าส่งไลน์มาว่า *"ดอกเบี้ยเหลือ 23%"* ทั้งที่ TOR เขียน 25% · ระบบเดิมจะ**ร่างเป็นกฎใหม่**

```
BR-loan-004@v1  "ดอกเบี้ย 25% ต่อปี"   ✅ ใช้อยู่  มีตัวอย่าง 2 ตัว
BR-loan-009@v1  "ดอกเบี้ย 23% ต่อปี"   ✅ ใช้อยู่  มีตัวอย่าง 2 ตัว   ← ร่างใหม่จากไลน์
```

**ตัวตรวจเขียวหมดทุกข้อ** — คนละ `base_id` กัน · coverage 100% · ไม่มีการ์ดแดง
แต่ในไฟล์มีกฎสองข้อที่ขัดกันเอง และไม่มีใครรู้ว่าข้อไหนจริง จนกว่าจะเขียนโค้ดไปแล้ว

ตอนนี้ `/req:capture` **ต้องตัดสินทุกกฎที่ร่างได้ว่าเป็น 1 ใน 4 อย่าง** ก่อนเขียนอะไรลงไฟล์:

| | แปลว่า | ระบบทำอะไร |
|---|---|---|
| 🆕 **ของใหม่** | ไม่ชนกับกฎไหน | ร่างเป็น `@v1` ตามปกติ |
| ♻️ **เรื่องเดิม** | พูดซ้ำ ความหมายเดิม | **ไม่สร้างกฎใหม่** เพิ่มแค่ที่มาให้กฎเดิม (แหล่งที่สองยืนยันกฎเดียวกัน = ของดี) |
| ⚠️ **เปลี่ยน** | ขัดกับกฎที่ใช้อยู่ | 🛑 **หยุด แจ้ง ถาม — ไม่เขียน ไม่ regenerate** |
| ❓ **ไม่แน่ใจ** | บอกไม่ได้ว่าขยายความหรือขัดกัน | 🛑 หยุดเหมือนกัน · ตอบไม่แน่ใจ → การ์ดแดง |

> **ข้อ 4 ต้องมีจริง** เพราะเคสที่เจอบ่อยที่สุดไม่ใช่ขัดกันชัด ๆ แต่เป็น *"อายุ 20–60"* → *"อายุ 20–60 และต้องไม่เป็นพนักงานสัญญาจ้าง"*
> ถ้าบังคับให้เลือกแค่ ใหม่/เปลี่ยน โมเดลจะเดา และเดาผิดครึ่งหนึ่ง

### เจอแล้วจะ "แช่แข็ง" — และแช่ทั้ง REQ

**เขียน:** ไฟล์แนบ + hash + การอ่านไฟล์ (หลักฐานเป็นกลาง ไม่ขึ้นกับว่าตกลงยังไง · และรูป paste ตายพร้อมหน้าต่าง)
**ไม่เขียนอะไรเลยใน REQ นั้น** รวมถึงที่มาของรายการที่ไม่ได้ขัดกัน — เพราะที่มาอยู่บนโหนดกฎ เขียนแล้วเอกสารจะค้าง
ส่วน REQ อื่นใน batch เดียวกันที่ไม่มีรายการขัดกัน **ทำต่อจนจบตามปกติ** (แช่ทั้ง batch = ลงโทษคนใช้)

### `/req:change` — ทางเดียวที่จะเกิด `@v2`

```
/req:change BR-job-011
```

บังคับ 4 อย่าง: **กรอกเหตุผล** · **ถามตัวอย่างทีละตัว**ว่ายังพิสูจน์ข้อความใหม่ได้ไหม
(ตอบว่าไม่ได้ → กฎใหม่มีตัวอย่าง 0 → **coverage ตก ซึ่งถูกต้อง**) · **บอกรัศมีผลกระทบก่อนเขียน** ·
ลง **`effective_from` บนตัวโหนดเวอร์ชันเอง**

`effective_from` ต่างจาก `superseded_at`: อันแรกคือ *"มีผลจริงในโลกเมื่อไหร่"* อันหลังคือ *"เลิกเป็นตัวปัจจุบันในไฟล์เมื่อไหร่"*
สองอันนี้ต่างกันทุกครั้งที่ตกลงกันก่อนวันมีผล ซึ่งเป็นเรื่องปกติ

### `CHG-xxx` — ทำไมต้องเป็นโหนดแยก ไม่ใช่บรรทัดใน log

เพราะ **การเปลี่ยนครั้งเดียวขยับหลายโหนดพร้อมกัน** — ลดดอกเบี้ยทีเดียวขยับทั้งกฎ ทั้งสัญญาการคำนวณ
และทำให้เลขเฉลยตาย · ถ้าเก็บเหตุผลไว้ในแต่ละโหนด มันจะถูกก๊อป 3 ที่ แล้วไม่มีใครรู้ว่าเป็นเรื่องเดียวกัน

`CHG` ตอบคำถามที่ `change_reason` ตอบไม่ได้: *"รอบวันที่ 13 ส.ค. แก้อะไรไปบ้าง ใครสั่ง อนุมัติโดยใคร มาจากเอกสารไหน"*

ดูของจริงได้ที่ `fixtures/clean/docs/requirements/REQ-job-001.md` หัวข้อ *"บันทึกการเปลี่ยนแปลง"*

## ตั้งกรอบก่อนถามกฎ — ชั้น 1 ของคลังคำถาม

คลังคำถามมี **2 ชั้น** และ `/req:ask` เลือกให้เอง

| ชั้น | ยิงเมื่อไหร่ | หมวด | จำนวน |
|---|---|---|---|
| **1 · กรอบ** | **ครั้งเดียวต่อโมดูล** หลัง `/req:capture` ก่อนถามกฎข้อแรก | เป้าหมายปลายทาง · ขอบเขต · ผู้เกี่ยวข้อง · ศัพท์กลาง (ขั้น 1–4) | 6 ข้อ = 2 รอบ |
| **2 · กฎ** | ทุกรอบ ต่อ REQ | 10 หมวดเดิม (ขั้น 5–7) | 15 ข้อ |

**รอบ A** — สำเร็จแปลว่าอะไร และรอบนี้ทำถึงไหน
**รอบ B** — ใครแตะข้อมูลนี้บ้าง และเรียกของแต่ละอย่างว่าอะไร

ข้อที่ 3 ของรอบ A คือ **ลูป L4** ที่จงใจถามเองแทนที่จะรอให้มันเกิด —
*"ตัดของที่เพิ่งบอกว่าไม่อยู่ในรอบนี้ออกแล้ว ยังบรรลุเป้าหมายที่เพิ่งตอบไปไหม"*
(แบบเดียวกับที่ MiniLoan เจอว่า ตัด collection ออกแล้วยังเรียกว่าระบบสินเชื่อได้ไหม)
ถามหลังข้อ 2 เสมอ เพราะยังไม่รู้ว่าตัดอะไร ก็ถามไม่ได้ว่าตัดแล้วเป็นยังไง

**ต้องมี `/req:capture` มาก่อนเสมอ** — การ์ดแดงของชั้น 1 ต้องอ้างที่มาเป็น `SRC-xxx`
(ตอนนั้นยังไม่มีกฎให้อ้าง และ schema ยอมให้ `raised_by` เป็น `SRC` หรือ `BR-xxx@vN` เท่านั้น)
ยังไม่มีอินพุต → ระบบบอกให้ไป `/req:capture` ก่อน ไม่ยิงคำถามลอย ๆ

**ชั้น 1 เขียนอะไรได้บ้าง** — ของที่มีอยู่แล้วทั้งหมด ไม่เพิ่ม field ใหม่ใน `spec.json`

| หมวด | ลงที่ไหน |
|---|---|
| เป้าหมายปลายทาง | `goal` + `business_value` ของ REQ |
| ขอบเขต | อยู่ในขอบเขต = มี REQ · **นอกขอบเขตลงในเนื้อความ `narrative`** + รายงานตอนปิดรอบ · เถียงกันไม่จบ = การ์ดแดง |
| ผู้เกี่ยวข้อง | `actor` ของ REQ (+ คำศัพท์ ถ้าเป็น actor ที่เพิ่งมีชื่อ) |
| ศัพท์กลาง | `glossary` — คำไทย · เรียกอีกอย่างว่า · ห้ามสับสนกับ |

**ชั้น 1 ไม่ร่างกฎเอง** เพราะกฎเริ่มที่ขั้น 5 — คำถาม *"actor คนนี้ทำอะไรไม่ได้"* ตั้งใจให้ได้คำตอบรูปกฎ
ระบบจะจดไว้ในเนื้อความ แล้วบอกตอนปิดรอบว่า *"หมวดสิทธิ์ชั้น 2 ค้างอยู่ 1 ข้อ"* ให้รอบหมวดสิทธิ์เป็นคนร่าง `BR`
(ถ้าร่างตรงนี้ด้วย จะกลายเป็นกฎเกิดได้จากสองทาง ซึ่งเป็นความพังที่ทั้งระบบนี้ตั้งใจกัน)

> ⚠️ **ชั้น 1 ยังเป็นร่าง (`provisional`) โดยตั้งใจ** — กติกาของคลังคำถามคือ
> *เพิ่มได้เฉพาะคำถามที่เคยงัดกฎที่ลืมออกมาได้จริงจากงานลูกค้าจริง*
> คำถาม 6 ข้อนี้มาจากการ์ด pipeline ซึ่งเป็น**ที่มาของถ้อยคำ ไม่ใช่หลักฐาน** — ยังไม่เคยผ่านงานลูกค้าจริง
> ใช้ได้ตามปกติ แต่ระบบจะบอกว่ายังเป็นร่าง และจะเลื่อนเป็นทางการ**ทีละข้อ**เมื่อข้อนั้นงัดของจริงได้แล้ว

**ยังไม่มีที่เก็บ "นอกขอบเขต" ที่ query ได้** — `spec.json` ไม่มี field นี้ ตอนนี้ลงได้แค่ในเนื้อความ
จดไว้เป็นช่องว่างที่ประกาศแล้วใน `tiers.1.declared_gap` ของคลังคำถาม ไม่ได้แอบเติม field ใหม่ให้

## คำศัพท์ต้องนิ่งก่อนถามกฎ

ลูกค้าพูดว่า **"งาน"** → หมายถึง `Job` (ทั้งใบสั่ง) หรือ `Trip` (เที่ยววิ่งหนึ่งรอบ)?
ถ้าไม่เคาะก่อน **กฎทุกข้อที่พูดถึง "งาน" จะกำกวมตั้งแต่เกิด** แล้วไปแตกตอนเขียนโค้ด

ระบบเก็บไว้ใน `glossary` — คำไทย · ชื่อในระบบ · นิยาม · **เรียกอีกอย่างว่า** (คำที่ลูกค้าใช้เรียกสิ่งเดียวกัน) · **ห้ามสับสนกับ** (คำที่ตั้งใจให้ต่างกัน ← จุดที่เถียงกับลูกค้าบ่อยที่สุด)

> ตอนนี้คำศัพท์ที่ยังไม่นิยาม **แค่เตือน ⚠️ ไม่บล็อก** Phase 1 — ถ้าใช้จริงแล้วเห็นว่าจำเป็น ค่อยเลื่อนเป็นบล็อก
> **เรื่องนี้ทำงานสองทาง:** คำศัพท์ช่วยตั้งคำถามกฎ · และคำตอบกฎก็คลอดคำศัพท์ใหม่ (Phase 0 คลอด `ApprovalPolicy` กับ `JobCostAdjustment` แบบนี้เป๊ะ)

## ⭐ คืออะไร

ตัวเลือกที่มีดาว = **นิสัยการออกแบบของพี่ปูเอง** ที่บันทึกไว้จากรอบทดสอบจริง
(ง่าย-ตรงไปตรงมา-ระเบิดเสียงดัง: ปัดทุกจุด · API ล่มก็ล้มทันที · กันซ้ำที่ DB · เห็นเฉพาะของตัวเอง)

ระบบจะ**เลือกไว้ให้แล้ว** กดยืนยันทีเดียวจบ — แต่**ยังต้องถามทุกครั้ง** เพราะบางงาน
(โดยเฉพาะองค์กรใหญ่) ต้องการทางตรงข้าม เช่น retry queue หรือ effective date

**ดาวของชั้น 1 คนละความหมาย** — นิสัยการออกแบบซ้ำข้ามโปรเจกต์ได้ แต่**เป้าหมายของโมดูลซ้ำไม่ได้**
ดาวของชั้น 1 จึงไม่ใช่นิสัย แต่คือ**สิ่งที่อ่านได้จากอินพุตที่เพิ่งใส่เข้ามา** และต้องโชว์ที่มาติดมาด้วยเสมอ
`⭐ ข (จาก SRC-002 หน้า 1 §3.2: "…")` — ถ้าอินพุตไม่ได้บอกอะไรเลย จะถามแบบ**ไม่มีดาว** และบอกว่าอินพุตเงียบ

## ตัวตรวจ

```
node plugins/req/scripts/verify-rules.mjs --root . --cp1
```

ตรวจ **14 ข้อ ไม่มีการให้ AI ตัดสินเลยสักข้อ** — `0` เขียว · `1` เจอปัญหา · `2` ไฟล์พัง

| ระดับ | ข้อ | แปลว่า |
|---|---|---|
| ⚠️ เตือนอย่างเดียว | **11** คำศัพท์ · **13** เลขเฉลย · **14** การเปลี่ยนกฎ | ไม่บล็อก — 3 ข้อนี้เท่านั้น |
| ⏭ ของ CP2 | **5** คิวส่งต่อ | ไม่เคยบล็อก CP1 ตั้งใจให้เป็นแบบนั้น |
| ❌ บล็อก | ที่เหลือทั้งหมด รวม **ข้อ 12** | จบ Phase 1 ไม่ได้จนกว่าจะแก้ |

**ข้อ 12 ตรวจว่า `docs/wiki/` ยังตรงกับ `spec.json` อยู่ไหม — และมันบล็อก ไม่ใช่คำเตือน**
ทุกหน้ามีลายนิ้วมือ (`spec_hash`) ของข้อมูลที่มันเรนเดอร์มา
แก้ `spec.json` แล้วลืม regenerate = แดงทันที ไม่ใช่เงียบ
และถ้าเปลี่ยนชื่อ id แล้วหน้าเก่าค้างอยู่ มันจะบอกว่าเป็น "หน้ากำพร้า" — แต่**ไม่ลบให้เอง**
เพราะการลบไฟล์เป็นการตัดสินใจ ไม่ใช่ผลข้างเคียงของการสั่ง regenerate

```
node plugins/req/scripts/wiki.mjs --root .            # ดูเฉยๆ ว่าหน้าไหนค้าง
node plugins/req/scripts/wiki.mjs --root . --write    # เขียนใหม่เฉพาะหน้าที่ค้าง
```

ดูตัวอย่างของจริงได้ที่ `plugins/req/scripts/fixtures/` — `clean/` ผ่าน, `dirty/` จงใจผิดครบทุกข้อ

**ถ้าพี่ปูแก้ `spec.json` เองแล้วเพิ่ม/ลบกฎ** ตัวเลขสรุป (`rollup`) จะไม่ตรง สั่ง `/req:capture`
เปล่าๆ ได้เลย (มันเรียกสคริปต์ให้) หรือถ้าอยากรันเอง:

```
node plugins/req/scripts/rollup.mjs --root .            # ดูเฉยๆ ไม่แก้ไฟล์
node plugins/req/scripts/rollup.mjs --root . --write    # แก้ให้ตรง
```

> **ตัวตรวจเขียว ≠ อนุมัติแล้ว** — CP1 พี่ปูเป็นคนเซ็น ตัวตรวจแค่บอกว่าถามได้แล้ว

## เปลี่ยนชื่อโฟลเดอร์ `.aeon/` ได้

`.aeon/` เป็นแค่**ค่าเริ่มต้น** ไม่ใช่ชื่อตายตัว — ตั้งชื่อนี้เพื่อให้รู้ว่าเป็นที่รวมของ marketplace `aeon`
ถ้าอยากใช้ชื่ออื่น (เช่นเปลี่ยนชื่อ marketplace ทีหลัง หรือโปรเจกต์มีธรรมเนียมของตัวเอง) ทำได้ 2 ทาง

```bash
# ครั้งเดียว — ส่ง flag
node plugins/req/scripts/verify-rules.mjs --root . --state-dir .miniloan --cp1

# ถาวรทั้ง shell / ทั้งโปรเจกต์ — ตั้ง env
export AEON_STATE_DIR=.miniloan       # Windows PowerShell: $env:AEON_STATE_DIR = ".miniloan"
mv .aeon .miniloan                    # อย่าลืมย้ายโฟลเดอร์จริงด้วย
```

**ลำดับความสำคัญ (บนชนะล่าง) — ประกาศทั้งหมด ไม่มีการเดา:**

| # | ช่องทาง | ใช้เมื่อ |
|---|---|---|
| 1 | `--spec <path>` | ชี้ไฟล์ตรง ๆ ข้ามเรื่องโฟลเดอร์ไปเลย |
| 2 | `--state-dir <ชื่อ>` | ครั้งเดียว รันนี้เท่านั้น |
| 3 | `$AEON_STATE_DIR` | ทั้ง shell / ทั้งโปรเจกต์ |
| 4 | `.aeon` | ค่าเริ่มต้น ไม่ต้องตั้งอะไร |

> **ระบบจะไม่ไล่หาโฟลเดอร์ที่มี `spec.json` ให้เอง** ตั้งใจให้เป็นแบบนั้น — ถ้าเปลี่ยนชื่อเป็น `.miniloan` แล้วยังมี `.aeon/spec.json` เก่าค้างอยู่
> การไล่หาจะไปเจอไฟล์เก่าแล้วทำงานผิดแบบเงียบ ๆ · หาไม่เจอ = **exit 2 พร้อมบอก path ที่หา** ไม่ใช่เดา

อยากรู้ว่าตอนนี้ระบบใช้โฟลเดอร์ไหนอยู่:

```bash
node plugins/req/scripts/state-dir.mjs                # → .aeon
node plugins/req/scripts/state-dir.mjs --root . --path  # → path เต็มของ spec.json
```
