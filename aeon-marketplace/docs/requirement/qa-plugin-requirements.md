# QA Plugin — Requirement Specification

> **สถานะ:** Draft v0.1 (สำหรับใช้เป็นโจทย์ในการสร้าง plugin)
> **ผู้เขียนความต้องการ:** User
> **เอกสารที่ต้องอ่านคู่กัน:** Design Plugin Spec (§3, §6, §19), Dev Plugin Spec (§9, §10, §16)
> **หมายเหตุจากการเรียบเรียง:** โจทย์ตั้งต้นเขียนว่า "qa plugin สำหรับออกแบบหน้าจอ" ซึ่งน่าจะติดมาจากเอกสารของ design plugin — ในเอกสารนี้ตีความว่า **ขอบเขตคือการทดสอบระบบ** ตามรายละเอียดที่ระบุไว้ทั้งหมด

---

## 0. สรุปย่อสำหรับผู้เรียน

QA Plugin คือ **ตัวพิสูจน์ว่าสิ่งที่สร้างออกมา ตรงกับสิ่งที่ลูกค้าขอไว้จริง — และพิสูจน์ด้วยหลักฐานที่ตรวจซ้ำได้**

**Analogy:** คิดถึงการตรวจรับบ้าน

- คนตรวจไม่ได้เดินดูเอาเองตามใจ แต่ถือเช็คลิสต์ที่ **ออกมาจากแบบก่อสร้าง** ถ้าแบบบอกว่าต้องมีปลั๊กสามจุด เช็คลิสต์ต้องมีสามข้อ
- ทุกจุดที่ตรวจต้อง **ถ่ายรูปเป็นหลักฐาน** และรูปต้องรู้ว่าเป็นห้องไหน จุดไหน ตรวจรอบไหน ไม่ใช่กองรวมกันแล้วมาไล่เดาทีหลัง
- ต้องมี **ใบตรวจแยกแต่ละรอบ** รอบแรกผ่านกี่ข้อ รอบแก้แล้วผ่านเพิ่มกี่ข้อ เพื่อให้เทียบกันได้
- และที่สำคัญที่สุด — **คนตรวจต้องไม่ใช่คนสร้าง** ถ้าคนสร้างตรวจงานตัวเองแล้วบอกว่าผ่าน ใบตรวจนั้นไม่มีค่า

ข้อสุดท้ายคือเหตุผลที่ QA plugin ต้องเป็นเจ้าของผลการทดสอบแต่ผู้เดียว และเหตุผลที่คำตัดสินผ่าน/ไม่ผ่าน **ต้องมาจากคำสั่งที่รันได้ ไม่ใช่จากความเห็นของ AI**

## 1. เป้าหมาย และ Non-Goals

### 1.1 เป้าหมาย

| ID | เป้าหมาย | วัดผลอย่างไร |
|---|---|---|
| G1 | แปลง scenario จาก design ให้เป็นชุดทดสอบที่รันได้จริง | ทุก scenario มี test case ที่รันได้ |
| G2 | ตอบได้ทันทีว่าหน้าจอหนึ่ง ๆ ต้องทดสอบอะไรบ้าง ใช้ข้อมูลอะไร เกี่ยวกับ workflow ไหน | ตอบได้โดยไม่ต้องให้คนอธิบายเพิ่ม |
| G3 | รู้ว่าเทสแต่ละตัวมาจาก requirement ข้อไหน spec ข้อไหน และครอบคลุมโค้ดส่วนไหน | ตอบได้ทั้งไปและกลับ |
| G4 | สั่งทดสอบพร้อมเก็บภาพหลักฐานที่จัดหมวดหมู่แล้วได้ | เปิดโฟลเดอร์แล้วรู้ทันทีว่ารูปไหนของอะไร รอบไหน |
| G5 | ออกรายงานทดสอบตามขอบเขตที่เลือกได้ (ทั้งระบบ / โมดูล / หน้าจอ) | รายงานมีทั้งผลและความครอบคลุมเทียบ requirement |
| G6 | ดูประวัติการทดสอบย้อนหลังและเทียบระหว่างรอบได้ | ตอบได้ว่ารอบนี้ดีขึ้นหรือแย่ลงกว่ารอบก่อน |
| G7 | รองรับหลาย stack และหลายเครื่องมือทดสอบ | .NET / Next.js / Python และเครื่องมือที่ผู้ใช้เลือก |
| G8 | เมื่อ requirement เปลี่ยน รู้ทันทีว่าต้องรันเทสชุดไหนซ้ำ | ระบุชุดที่ต้องรันซ้ำได้โดยไม่ต้องรันทั้งหมด |
| G9 | เมื่อเจอปัญหา ส่งกลับไปยัง dev หรือ design ได้โดยข้อมูลไม่หาย | ทุกข้อบกพร่องมีปลายทางและติดตามได้ |

### 1.2 Non-Goals

- ไม่ออกแบบระบบ ไม่กำหนดว่าอะไรถูกอะไรผิดเชิงธุรกิจเอง — เกณฑ์มาจาก design
- ไม่แก้โค้ดของระบบ (แก้ได้เฉพาะโค้ดทดสอบที่ตัวเองเป็นเจ้าของ)
- ไม่ตัดสินใจว่าจะปล่อยงานหรือไม่ — รายงานให้ แล้วมนุษย์ตัดสิน
- ไม่ทำ load test ระดับโครงสร้างพื้นฐาน หรือ penetration test เชิงลึก (ระบุเป็นข้อจำกัดไว้ก่อน ดู QD10)
- ไม่ deploy ระบบเอง — ใช้วิธียกระบบขึ้นที่ dev เตรียมไว้

## 2. ผู้เกี่ยวข้อง

| Actor | ต้องการอะไร |
|---|---|
| QA / ผู้ทดสอบ (มนุษย์) | สั่งรัน ดูผล ออกรายงาน ถามว่าหน้าจอนี้ทดสอบอะไร |
| Developer | รู้ว่าเทสไหนพัง เพราะอะไร ที่ไฟล์ไหน |
| ลูกค้า / ผู้ตรวจรับ | รายงานที่อ่านรู้เรื่อง มีหลักฐานภาพ และบอกได้ว่าความต้องการข้อไหนผ่านแล้ว |
| AI Agent (qa) | รู้ว่าต้องทดสอบอะไร ด้วยเครื่องมืออะไร ยกระบบขึ้นอย่างไร |
| AI Agent (design/dev) | รับข้อบกพร่องและคำถามกลับไปแก้ |

## 3. ตำแหน่งใน Marketplace

```
req ──▶ design ──▶ dev ──▶ qa ──▶ deliver
         ▲                  │
         └──── findings ────┘
```

### 3.1 Inbound Contract

| จาก | ต้องอ่านได้ | ใช้ทำอะไร | จำเป็น |
|---|---|---|---|
| design | Test scenario | ต้นทางของ test case ทุกตัว | บังคับ |
| design | รายการหน้าจอ + ฟิลด์ + validation | สร้าง UI test | บังคับถ้ามี UI |
| design | สัญญา API | สร้าง API test | บังคับถ้ามี API |
| design | ผังสถานะ | สร้าง workflow test | บังคับถ้ามี |
| design | ตารางสิทธิ์ | ทดสอบการเข้าถึงตามบทบาท | บังคับ |
| design | ข้อกำหนดที่ไม่ใช่เชิงหน้าที่ พร้อมตัวเลข | ทดสอบ NFR | บังคับ |
| dev | แผนที่ spec → ไฟล์โค้ด | รู้ว่าเทสครอบคลุมโค้ดส่วนไหน | บังคับ |
| dev | วิธียกระบบขึ้นและค่าตั้งค่าที่ต้องใช้ | เตรียมสภาพแวดล้อมทดสอบ | บังคับ |
| dev | โครงสร้างข้อมูลและวิธีล้างข้อมูล | เตรียมและรีเซ็ตข้อมูลทดสอบ | บังคับ |
| req | เป้าหมายและตัวชี้วัดที่ตกลงกับลูกค้า | ใช้เป็นเกณฑ์ตัดสินขั้นสุดท้าย | ควรมี |

**กติกาเหล็ก:** ถ้า scenario ไม่ระบุผลลัพธ์ที่คาดหวังชัดเจน **ห้าม QA เดาเกณฑ์เอง** ต้องเปิดคำถามกลับไปที่ design
เทสที่เกณฑ์ผ่าน/ไม่ผ่านถูกคิดขึ้นเองโดยผู้ทดสอบ ไม่ได้พิสูจน์อะไรเลยนอกจากว่าระบบทำตามที่ผู้ทดสอบคิด

### 3.2 Outbound Contract

| ผู้รับ | ต้องได้อะไร |
|---|---|
| `deliver` | ความครอบคลุมเทียบ requirement, ผลรอบล่าสุด, รายการที่ยังไม่ผ่าน, หลักฐานภาพ |
| `dev` | ข้อบกพร่องพร้อมขั้นตอนทำซ้ำ ภาพ log และตำแหน่งโค้ดที่เกี่ยวข้อง |
| `design` | จุดที่ spec กำกวมจนทดสอบไม่ได้ หรือขัดแย้งกันเอง |

## 4. หลักการออกแบบ

| # | หลักการ | เหตุผล |
|---|---|---|
| P1 | **คำตัดสินผ่าน/ไม่ผ่านต้องมาจากคำสั่งที่รันได้ ไม่ใช่จากการที่ AI ดูแล้วบอกว่าใช้ได้** | ถ้า verdict มาจากดุลพินิจของ LLM มันคือความเห็น ไม่ใช่การทดสอบ |
| P2 | **เทสต้องสาวกลับได้ทั้งสามทาง — requirement, spec, และโค้ด** | ไม่งั้นตอบไม่ได้ว่าเทสนี้มีไว้ทำไม และเทสที่ตอบไม่ได้ว่ามีไว้ทำไม จะถูกลบทิ้งในที่สุด |
| P3 | **QA เป็นเจ้าของผลการทดสอบแต่ผู้เดียว ห้าม plugin อื่นเขียน** | คนสร้างตรวจงานตัวเองแล้วว่าผ่าน = ใบตรวจไม่มีค่า |
| P4 | **การทดสอบต้องทำซ้ำได้และเป็นอิสระจากลำดับ** | เทสที่ผลไม่คงที่ ทำลายความน่าเชื่อถือของทั้งระบบเร็วกว่าการไม่มีเทสเลย |
| P5 | **แยกเทสที่ใช้เป็นด่าน ออกจากเทสที่ใช้สำรวจ** | เครื่องมือแบบ agentic มีค่าในการหาของที่ไม่ได้คิดไว้ แต่ใช้เป็นเกณฑ์ตัดสินไม่ได้ (ดู §6.3) |
| P6 | **หลักฐานต้องเก็บอย่างมีระบบตั้งแต่วินาทีที่เกิด** | รูปที่ไม่รู้ว่าของอะไร รอบไหน คือขยะที่กินพื้นที่ |
| P7 | **ไม่เดาเกณฑ์ ไม่เดาข้อมูล ไม่เดาเครื่องมือ — ถามแล้วจำ** | สืบทอดจาก dev plugin |
| P8 | **1 ไฟล์ = 1 เจ้าของ ใช้กับ JSON ด้วย** | สืบทอด — และเป็นข้อที่ QA เสี่ยงโดนมากที่สุด เพราะผลเทสหายง่าย |
| P9 | **ความครอบคลุมที่วัดคือความครอบคลุมของความต้องการ ไม่ใช่ของบรรทัดโค้ด** | code coverage สูงแต่ requirement ไม่ครบ คือการหลอกตัวเอง |

## 5. Artifact ที่ QA เป็นเจ้าของ

| Artifact | รูปแบบ | หน้าที่ |
|---|---|---|
| Test Tool Profile | JSON | stack ของแต่ละ component → เครื่องมือทดสอบที่เลือก + เหตุผล |
| Test Case | JSON | รายการเทสพร้อม trace, ประเภท, ขั้นตอน, เกณฑ์ผ่าน, คำสั่งรัน |
| Test Data Set | JSON + ไฟล์ข้อมูล | ชุดข้อมูลตั้งต้นสำหรับแต่ละกรณี |
| Test Run | JSON | บันทึกการรันแต่ละรอบ — เมื่อไร รันอะไร ผลอย่างไร บนสภาพแวดล้อมไหน |
| Evidence Index | JSON | ทะเบียนภาพ/วิดีโอ/log ผูกกับ test case และ run |
| Finding | JSON | ข้อบกพร่องที่พบ พร้อมปลายทางที่ต้องส่งกลับ |
| Trace (qa) | JSON | edge ที่ qa เพิ่มเท่านั้น |
| Test Report | Markdown → เอกสาร | รายงานตามขอบเขตที่เลือก |
| QA Journal | JSONL (append-only) | คำถามและการตัดสินใจระหว่างทดสอบ |
| Test Project | โค้ด | โปรเจกต์ทดสอบจริง — QA เป็นเจ้าของ ไม่ใช่ dev |

**สิ่งที่ QA ห้ามเขียนเด็ดขาด:** scenario ของ design, โค้ดระบบของ dev, tech profile ของ dev

## 6. ประเภทของการทดสอบ และการเลือกเครื่องมือ

### 6.1 ชั้นของการทดสอบ และใครเป็นเจ้าของ

> นี่คือเรื่องที่ต้องตัดสินให้ชัดก่อนอย่างอื่น เพราะเป็นรอยต่อระหว่าง dev กับ qa ที่ทับกันได้ง่ายที่สุด

| ชั้น | ทดสอบอะไร | เจ้าของที่เสนอ | ต้นทาง |
|---|---|---|---|
| Unit | ตรรกะและ invariant ในชั้นโดเมน | dev (เขียนคู่กับโค้ด) | กฎธุรกิจจาก design |
| Integration | โมดูลคุยกันได้ ต่อฐานข้อมูลจริงได้ | dev หรือ qa (ดู QD1) | สัญญา API |
| API / Contract | endpoint ตรงตามสัญญา | **qa** | สัญญา API จาก design |
| UI / E2E | ผู้ใช้ทำงานจนจบได้จริง | **qa** | scenario + หน้าจอ |
| Workflow | สถานะเปลี่ยนถูกตามผัง ทั้งเส้นทางปกติและผิดปกติ | **qa** | ผังสถานะ |
| Permission | บทบาทเข้าถึงได้ตามตาราง และที่สำคัญคือ **เข้าถึงไม่ได้ตามตาราง** | **qa** | ตารางสิทธิ์ |
| NFR | เวลาตอบสนอง ปริมาณงาน ตามตัวเลขที่ระบุ | **qa** | ข้อกำหนดที่ไม่ใช่เชิงหน้าที่ |
| Exploratory | หาสิ่งที่ไม่มีใครคิดถึง | **qa** (agentic) | ไม่มีต้นทางตายตัว |

**ข้อที่มักถูกลืม:** การทดสอบสิทธิ์ต้องพิสูจน์ *ทางลบ* ด้วย — ไม่ใช่แค่ผู้จัดการเข้าหน้านี้ได้ แต่ต้องพิสูจน์ว่าพนักงานทั่วไปเรียก API ตรง ๆ แล้วถูกปฏิเสธจริง การซ่อนปุ่มไม่ใช่การคุมสิทธิ์

### 6.2 การเลือกเครื่องมือ

ต้องมีตารางเงื่อนไข → เครื่องมือ ในลักษณะเดียวกับ skill routing ของ dev

| เงื่อนไข | ตัวอย่างเครื่องมือ |
|---|---|
| ทดสอบ UI บนเบราว์เซอร์ | Playwright (ค่าเริ่มต้นที่แนะนำ) |
| ทดสอบ UI ที่ต้องใช้เบราว์เซอร์เดิมของผู้ใช้ | เครื่องมือควบคุมเบราว์เซอร์แบบ agentic |
| ทดสอบ API | เครื่องมือฝั่ง stack นั้น ๆ |
| ทดสอบ unit/integration ฝั่ง .NET | เครื่องมือทดสอบมาตรฐานของ .NET |
| ทดสอบฝั่ง Python | เครื่องมือทดสอบมาตรฐานของ Python |
| ไม่มีเงื่อนไขไหนตรง | **ถามผู้ใช้ ห้ามเดา** |

กติกาเดียวกับ dev: ถามครั้งเดียว บันทึกก่อนตอบ ไม่ถามซ้ำ ผู้ใช้ override ได้ และทุกการเลือกต้องบันทึกเหตุผล

### 6.3 แยกเทสที่เป็นด่าน ออกจากเทสที่ใช้สำรวจ

**นี่คือประเด็นที่โจทย์ตั้งต้นยังไม่ได้แยก และถ้าไม่แยกจะเกิดปัญหาแน่นอน**

| | เทสที่เป็นด่าน (Gate) | เทสสำรวจ (Exploratory) |
|---|---|---|
| ผลลัพธ์ | ผ่าน / ไม่ผ่าน | รายการข้อสังเกต |
| ความคงที่ | ต้องได้ผลเดิมทุกครั้ง | ไม่คงที่โดยธรรมชาติ |
| เครื่องมือ | script ที่กำหนดขั้นตอนตายตัว | agent ที่ตัดสินใจเองระหว่างทาง |
| ใช้ตัดสินการส่งมอบได้ไหม | **ได้** | **ไม่ได้** |
| ผลลัพธ์ที่ควรได้ | อัปเดตสถานะ test case | สร้าง finding ให้คนพิจารณา |

การให้ AI เปิดเบราว์เซอร์ดูแล้วสรุปว่า "หน้านี้ใช้งานได้ปกติ" มีประโยชน์มากในการหาของแปลก ๆ ที่ไม่มีใครคิดถึง แต่เอาไปเป็นเกณฑ์ตัดสินไม่ได้ เพราะรันสองครั้งอาจได้คำตอบคนละอย่าง — และถ้าปล่อยให้มันไปอัปเดตสถานะว่า "ผ่าน" ระบบทั้งหมดจะเชื่อถือไม่ได้ทันที

---

## 7. การตอบคำถามของผู้ใช้

โจทย์ระบุว่าต้องถามได้ว่า "หน้าจอนี้ทดสอบอะไรบ้าง มีข้อมูลอะไร มี workflow อะไรเกี่ยวข้อง"

ความสามารถนี้ไม่ใช่ฟีเจอร์แยก แต่เป็น **ผลพลอยได้ของการที่ trace ครบ** ถ้าเชื่อมโยงถูกต้องตั้งแต่ต้น คำถามพวกนี้ตอบได้เองโดยไม่ต้องเขียนตรรกะพิเศษ

คำถามที่ต้องตอบได้:

1. หน้าจอนี้มีเทสอะไรบ้าง แต่ละตัวประเภทไหน สถานะล่าสุดเป็นอย่างไร
2. หน้าจอนี้ใช้ข้อมูลทดสอบชุดไหน ต้องเตรียมอะไรก่อน
3. หน้าจอนี้เกี่ยวข้องกับ workflow ไหน และอยู่ขั้นตอนไหนของ workflow นั้น
4. เทสตัวนี้มาจาก requirement ข้อไหน scenario ไหน และแตะโค้ดไฟล์ไหน
5. requirement ข้อนี้ทดสอบครบหรือยัง ถ้ายัง ขาดอะไร
6. ถ้าแก้ไฟล์โค้ดนี้ ต้องรันเทสตัวไหนซ้ำบ้าง
7. เทสตัวนี้เคยพังกี่ครั้งในสิบรอบหลัง (ใช้จับเทสที่ผลไม่คงที่)

ข้อ 6 คือประโยชน์สูงสุดของการทำ traceability ทั้งหมด และข้อ 7 คือสิ่งที่กันไม่ให้ทีมเริ่ม "รันใหม่อีกทีเดี๋ยวก็ผ่าน"

## 8. การรันทดสอบและการเก็บหลักฐาน

### 8.1 การรัน

- ต้องเลือกขอบเขตได้: ทั้งระบบ / โมดูล / หน้าจอ / เทสตัวเดียว / เฉพาะที่เคยพัง / เฉพาะที่กระทบจากการเปลี่ยนแปลงล่าสุด
- ก่อนรันต้องยกระบบขึ้นด้วยวิธีที่ dev เตรียมไว้ และต้องตรวจว่าพร้อมจริงก่อนเริ่ม
- ต้องรีเซ็ตข้อมูลให้อยู่ในสถานะที่รู้แน่นอนก่อนแต่ละรอบ
- ต้องบันทึกไว้เสมอว่ารันบนโค้ดเวอร์ชันไหน สภาพแวดล้อมไหน เพราะผลที่ไม่รู้ว่ามาจากโค้ดตัวไหน เอาไปเทียบกับรอบอื่นไม่ได้

### 8.2 หลักฐานภาพ

ตามโจทย์: เก็บภายใต้โฟลเดอร์ของ QA และต้องแยกหมวดหมู่

**ข้อกำหนดที่ต้องมี**

- ต้องดูจากชื่อหรือตำแหน่งไฟล์แล้วรู้ได้ทันทีว่าเป็นเทสตัวไหน รอบไหน ขั้นตอนที่เท่าไร ผลเป็นอย่างไร โดยไม่ต้องเปิดไฟล์ทะเบียนดู
- ต้องแยกได้อย่างน้อยตาม: รอบการรัน, โมดูล/หน้าจอ, และผลลัพธ์ (ผ่าน/ไม่ผ่าน)
- เทสที่ไม่ผ่าน ต้องเก็บหลักฐานมากกว่าเทสที่ผ่าน — ภาพก่อนเกิดเหตุ ภาพตอนเกิดเหตุ log และสถานะข้อมูลขณะนั้น
- ต้องมีทะเบียนกลางที่ผูกภาพเข้ากับ test case และรอบการรัน

**สองข้อที่โจทย์ยังไม่ได้พูดถึงแต่จะเป็นปัญหาแน่นอน**

*หนึ่ง — นโยบายการเก็บ* ภาพจากการรัน E2E กินพื้นที่เร็วมาก ถ้ารันวันละหลายรอบและเก็บทุกภาพตลอดไป repo จะบวมจนใช้งานไม่ได้ภายในไม่กี่สัปดาห์ ต้องตัดสินตั้งแต่ต้นว่าเก็บของรอบที่ผ่านนานแค่ไหน และของรอบที่ไม่ผ่านนานแค่ไหน (ปกติควรเก็บของที่ไม่ผ่านนานกว่า)

*สอง — ข้อมูลส่วนบุคคลในภาพ* ถ้าทดสอบด้วยข้อมูลที่คล้ายของจริง ภาพหน้าจอจะกลายเป็นข้อมูลส่วนบุคคลทันที และมันถูก commit เข้า repo ไปแล้ว ต้องตัดสินว่าจะใช้ข้อมูลสมมติล้วน หรือต้องปิดบังก่อนบันทึก

## 9. ประวัติการทดสอบ

การรันแต่ละรอบต้องเป็นของที่มีตัวตน ไม่ใช่แค่ข้อความที่พิมพ์ออกมาแล้วหายไป

แต่ละรอบต้องบันทึก: รันเมื่อไร ใครหรืออะไรสั่งรัน ขอบเขตที่รัน โค้ดเวอร์ชันไหน สภาพแวดล้อมอะไร ผลรายตัว ระยะเวลา และหลักฐานที่เก็บได้

**สิ่งที่ต้องตอบได้จากประวัติ**

- รอบนี้เทียบกับรอบก่อน อะไรดีขึ้น อะไรแย่ลง
- เทสตัวนี้เริ่มพังตั้งแต่รอบไหน และตอนนั้นโค้ดเปลี่ยนอะไร
- เทสตัวไหนผลไม่คงที่ (บางรอบผ่าน บางรอบไม่ผ่าน ทั้งที่โค้ดไม่เปลี่ยน)
- ความครอบคลุมเทียบ requirement เพิ่มขึ้นหรือลดลง

**เรื่องเทสที่ผลไม่คงที่ต้องมีนโยบายชัดเจน** ไม่ใช่ปล่อยให้คนตัดสินหน้างานว่า "รันใหม่อีกที" เพราะเมื่อไรที่ทีมเริ่มทำแบบนั้น เทสทั้งชุดจะหมดความหมายภายในเดือนเดียว ต้องมีการทำเครื่องหมายว่าตัวไหนน่าสงสัย และแยกมันออกจากด่านตัดสินจนกว่าจะแก้

---

## 10. รายงานการทดสอบ

ต้องเลือกขอบเขตได้ตามโจทย์ — ทั้งระบบ โมดูล หรือหน้าจอ

**เนื้อหาที่รายงานต้องมี**

- สรุปว่าผ่านกี่ข้อ ไม่ผ่านกี่ข้อ ยังไม่ได้ทดสอบกี่ข้อ
- **ความครอบคลุมเทียบกับความต้องการ** ไม่ใช่แค่จำนวนเทสที่ผ่าน — ต้องบอกได้ว่ามี requirement ข้อไหนที่ยังไม่มีเทสรองรับเลย
- รายการที่ไม่ผ่าน พร้อมหลักฐานภาพและขั้นตอนทำซ้ำ
- เทียบกับรอบก่อนหน้า
- รายการที่ผลไม่คงที่ แยกออกมาต่างหาก
- สภาพแวดล้อมและเวอร์ชันที่ใช้ทดสอบ

**ข้อที่สำคัญที่สุดคือความครอบคลุม** เพราะ "เทส 200 ตัวผ่านหมด" ไม่ได้แปลว่าระบบใช้ได้ ถ้า requirement ครึ่งหนึ่งไม่มีเทสแตะเลย

รายงานต้องมีสองระดับ: ฉบับที่ลูกค้าอ่านได้ (เน้นว่าสิ่งที่ขอไว้ใช้ได้หรือยัง) และฉบับที่ทีมใช้ (เน้นว่าอะไรพังที่ไหน)

---

## 11. ข้อบกพร่องและการส่งกลับ

เมื่อเทสไม่ผ่าน ต้องเกิดของที่ติดตามได้ ไม่ใช่แค่ข้อความแดง ๆ ในผลการรัน

ข้อบกพร่องแต่ละรายการต้องมี: เทสที่พบ, requirement และ spec ต้นทาง, ขั้นตอนทำซ้ำ, ผลที่คาดหวังกับผลที่เกิดจริง, หลักฐาน, ความรุนแรง, และ **ปลายทางที่ต้องส่งไป**

ปลายทางมีสามแบบ และต้องแยกให้ออก:

| ประเภท | ความหมาย | ส่งไปที่ |
|---|---|---|
| โค้ดไม่ตรง spec | spec ถูก แต่ทำมาผิด | dev |
| spec มีปัญหา | กำกวม ขัดแย้งกันเอง หรือทดสอบไม่ได้ | design |
| ความต้องการเปลี่ยน | ทำถูกตาม spec แล้ว แต่ลูกค้าไม่ได้อยากได้แบบนี้ | req |

**การแยกสามอย่างนี้สำคัญมาก** เพราะทีมมักส่งทุกอย่างไปที่ dev แล้ว dev ก็แก้โค้ดให้ตรงกับที่ QA เข้าใจ ทั้งที่ปัญหาจริงอยู่ที่ spec — พอถึงตอนส่งมอบก็พบว่าระบบไม่ตรงกับที่ลูกค้าขอ ทั้งที่เทสผ่านหมด

---

## 12. การเลือกชุดทดสอบเมื่อมีการเปลี่ยนแปลง

เมื่อ requirement หรือ spec หรือโค้ดเปลี่ยน ต้องระบุได้ว่าต้องรันเทสชุดไหนซ้ำ โดยไม่ต้องรันทั้งหมด

วิธีคือเดินตามกราฟย้อนกลับ จากสิ่งที่เปลี่ยน ไปหา test case ที่ผูกอยู่

**ข้อควรระวัง:** การเลือกรันเฉพาะบางส่วนเป็นดาบสองคม ถ้ากราฟไม่ครบ จะพลาดของที่ควรรัน แล้วปล่อยของเสียผ่านไป
ดังนั้นต้องมีกฎว่า **ถ้าความมั่นใจในกราฟไม่พอ ให้รันเต็ม** และต้องรันเต็มตามรอบเวลาที่กำหนดอยู่ดี ไม่ว่าจะมีการเปลี่ยนแปลงหรือไม่

---

## 13. Traceability ที่ QA ต้องเพิ่ม

QA เป็นเจ้าของ node ประเภท test case, การรัน, หลักฐาน และข้อบกพร่อง และเพิ่ม edge ได้อย่างเดียว

```
SCN ──testedBy──▶ TC
TC ──covers──▶ SRC            (เชื่อมกับโค้ดที่ dev บันทึกไว้)
TC ──uses──▶ DATA             (ชุดข้อมูลทดสอบ)
TC ──executedIn──▶ RUN        (การรันแต่ละรอบ)
RUN ──produces──▶ EVIDENCE    (ภาพ วิดีโอ log)
TC ──found──▶ FINDING ──routedTo──▶ [dev | design | req]
```

เมื่อกราฟครบทั้งสี่ plugin จะตอบคำถามที่เป็นเป้าหมายสูงสุดได้:

> **"ความต้องการข้อนี้ ออกแบบไว้อย่างไร ทำเป็นโค้ดไฟล์ไหน ทดสอบด้วยเทสตัวไหน ผลล่าสุดเป็นอย่างไร และมีหลักฐานอะไร"**

ถ้าตอบคำถามนี้ได้ในประโยคเดียว แปลว่าทั้ง marketplace ทำงานถูกต้อง

## 14. Validation Rules

| ID | กฎ | ระดับ |
|---|---|---|
| QV1 | ทุก scenario จาก design ต้องมี test case อย่างน้อยหนึ่งตัว | Error |
| QV2 | ทุก test case ต้องสาวกลับถึง scenario และ requirement ได้ | Error |

| QV4 | ทุก requirement ต้องมีเทสรองรับ หรือมีเหตุผลบันทึกไว้ว่าทำไมไม่ทดสอบ | Error |

| QV7 | ทุกสถานะและทุกการเปลี่ยนสถานะในผัง ต้องมีเทสครอบคลุม | Error |
| QV8 | ทุกภาพหลักฐานต้องผูกกับ test case และรอบการรันได้ ไม่มีภาพลอย | Error |
| QV9 | ทุกการรันต้องบันทึกเวอร์ชันโค้ดและสภาพแวดล้อม | Error |
| QV10 | ห้ามมี test case ที่สถานะผ่าน โดยไม่มีการรันจริงรองรับ | Error |
| QV11 | ผลจากเครื่องมือแบบ agentic ห้ามใช้เปลี่ยนสถานะผ่าน/ไม่ผ่านของ test case ที่เป็นด่าน | Error |
| QV12 | ทุกข้อบกพร่องต้องระบุปลายทางว่าส่งไปที่ dev, design หรือ req | Error |
| QV13 | เทสที่ผลไม่คงที่ต้องถูกทำเครื่องหมาย และต้องไม่ถูกนับเป็นด่านตัดสิน | Warning |
| QV14 | ข้อมูลทดสอบต้องไม่มีข้อมูลส่วนบุคคลจริง | Error |

| QV16 | QA ต้องไม่ได้เขียนไฟล์ที่ plugin อื่นเป็นเจ้าของ | Error |
| QV17 | ต้องไม่มีของที่ล้าสมัยค้างอยู่หลังจากมีการเปลี่ยนแปลงจากต้นน้ำ | Error |

QV10 กับ QV11 เป็นสองข้อที่ปกป้องคุณค่าทั้งหมดของ plugin นี้ ถ้าสองข้อนี้หลุด รายงานที่ออกมาจะสวยแต่ไม่มีความหมาย

## 15. ความต่อเนื่องข้าม Session และข้าม Plugin

สืบทอดกลไกจาก design §19 และเพิ่มประเด็นเฉพาะของ QA

| รอยรั่ว | อาการเฉพาะของ QA | สิ่งที่ต้องมี |
|---|---|---|
| ผลเทสหายเงียบ | plugin อื่นสร้างไฟล์ใหม่ทับไฟล์ที่ QA เขียนผลไว้ | 1 ไฟล์ 1 เจ้าของ — QA ถือผลไว้ในไฟล์ของตัวเอง |
| ประวัติหาย | ผลรอบเก่าถูกเขียนทับด้วยรอบใหม่ | การรันแต่ละรอบต้องเป็นรายการใหม่เสมอ ห้ามทับ |
| หลักฐานกำพร้า | ภาพยังอยู่แต่ไม่รู้ว่าของอะไร | ทะเบียนต้องเขียนพร้อมภาพ ไม่ใช่เขียนทีหลัง |
| ลืมว่าทำไมข้ามเทสตัวนี้ | รอบหน้ามีคนกลับมาเปิดใหม่แล้วพังอีก | ทุกการยกเว้นต้องมีเหตุผลและวันหมดอายุ |
| ข้อบกพร่องหายระหว่างทาง | รายงานปากเปล่าแล้วไม่มีใครจำ | ข้อบกพร่องต้องเป็นของที่มีตัวตนและมีสถานะ |

**กฎ persist-before-answer ใช้กับ QA ด้วย** — ห้ามรายงานผลก่อนบันทึก เพราะผลที่รายงานแล้วไม่ได้บันทึก คือผลที่หายไปแล้ว

## 18. ลำดับการสร้าง

**Milestone 1 — รู้ว่าต้องทดสอบอะไร**
ตั้งต้น → แปลง scenario เป็น test case พร้อม trace → ตอบคำถามว่าหน้าจอนี้ทดสอบอะไร
*เป้าหมาย: พิสูจน์ว่าเทสไม่ได้คิดขึ้นเอง แต่มาจาก spec*

**Milestone 2 — รันได้จริงและมีหลักฐาน**
เลือกเครื่องมือ → สร้างโปรเจกต์ทดสอบ → รันพร้อมเก็บภาพที่จัดหมวดหมู่
*เป้าหมาย: พิสูจน์ว่าผลมาจากการรันจริง ไม่ใช่จากการที่ AI บอกว่าน่าจะผ่าน*

**Milestone 3 — ประวัติและรายงาน**
บันทึกการรันแต่ละรอบ → เทียบรอบ → ออกรายงานตามขอบเขต
*เป้าหมาย: พิสูจน์ว่าเทียบข้ามรอบได้ และรายงานความครอบคลุมได้ ไม่ใช่แค่จำนวนผ่าน*

**Milestone 4 — เชื่อมกับคนอื่น**
เลือกชุดรันซ้ำจากการเปลี่ยนแปลง → ส่งข้อบกพร่องกลับ → ส่งต่อ deliver

## 19. Acceptance Checklist สำหรับตรวจงานผู้เรียน

- [ ] ถามว่า "หน้าจอนี้ทดสอบอะไรบ้าง" — ตอบได้ครบทั้งเทส ข้อมูล และ workflow จากข้อมูลที่บันทึกไว้
- [ ] มี scenario ที่ยังไม่มีเทส แล้วสั่งตรวจ — ต้องจับได้
- [ ] มี requirement ที่ไม่มีเทสแตะเลย แล้วออกรายงาน — รายงานต้องบอกว่าครอบคลุมไม่ครบ ไม่ใช่แสดงแค่ว่าผ่าน 100%
- [ ] สั่งรันแล้วดูโฟลเดอร์ภาพ — ต้องรู้ได้จากชื่อและตำแหน่งว่าภาพไหนของเทสไหน รอบไหน ผลอะไร
- [ ] รันสองรอบ — รอบที่สองต้องไม่ทับประวัติรอบแรก และเทียบสองรอบได้
- [ ] ให้ agent เปิดเบราว์เซอร์ดูแล้วบอกว่าหน้าเว็บใช้ได้ — ต้องไม่ทำให้สถานะ test case กลายเป็นผ่าน
- [ ] มาร์คเทสว่าผ่านโดยไม่มีการรันจริง — ระบบต้องปฏิเสธ
- [ ] ทำให้เทสตัวหนึ่งพังสลับผ่าน — ระบบต้องทำเครื่องหมายว่าไม่คงที่ และไม่นับเป็นด่าน
- [ ] แก้ requirement หนึ่งข้อ — ระบุได้ว่าต้องรันเทสตัวไหนซ้ำ โดยไม่ต้องรันทั้งหมด
- [ ] เจอข้อบกพร่องที่เกิดจาก spec กำกวม — ต้องส่งกลับ design ไม่ใช่ส่ง dev
- [ ] ทดสอบสิทธิ์ — ต้องมีเทสที่พิสูจน์ว่าบทบาทที่ไม่มีสิทธิ์เรียก API ตรง ๆ แล้วถูกปฏิเสธ
- [ ] เปลี่ยน stack จาก .NET เป็น Python — ต้องแตะแค่ตารางเลือกเครื่องมือ ไม่ต้องรื้อแกน

### 19.1 Cold Start Test

ปิดทุกอย่าง เปิดใหม่โดยมีแค่ไฟล์ในดิสก์ แล้วถาม

1. โปรเจกต์นี้ทดสอบด้วยเครื่องมืออะไร ใครเป็นคนเลือก และเพราะอะไร
2. ตอนนี้ผ่านกี่ข้อ ไม่ผ่านกี่ข้อ ยังไม่ทดสอบกี่ข้อ
3. ความต้องการข้อนี้ ทดสอบด้วยเทสตัวไหน ผลล่าสุดเป็นอย่างไร มีหลักฐานอะไร
4. เทสตัวนี้เริ่มพังตั้งแต่รอบไหน
5. มีข้อบกพร่องอะไรค้างอยู่ และค้างอยู่ที่ใคร

### 19.2 บททดสอบสุดท้ายของทั้ง Marketplace

เมื่อครบทั้งสี่ plugin ให้ถามคำถามเดียวนี้:

> ความต้องการข้อนี้ — ลูกค้าขอไว้ว่าอย่างไร ออกแบบเป็นอะไร ทำเป็นโค้ดไฟล์ไหน ทดสอบด้วยเทสตัวไหน ผลล่าสุดเป็นอย่างไร และมีหลักฐานภาพไหม

ตอบได้ครบในคำตอบเดียวโดยไม่ต้องเปิดหาเอง = ระบบทั้งหมดทำงานถูกต้อง

## ภาคผนวก: อภิธานศัพท์เฉพาะของ QA Plugin

| คำ | ความหมาย |
|---|---|
| Scenario | เจตนาของการทดสอบระดับธุรกิจ — มาจาก design |
| Test Case | ขั้นตอนที่รันได้จริงพร้อมเกณฑ์ผ่าน — เป็นของ QA |
| Run | การรันหนึ่งรอบ พร้อมบริบทว่ารันบนอะไรเมื่อไร |
| Evidence | หลักฐานที่เกิดจากการรัน — ภาพ วิดีโอ log |
| Finding | ข้อบกพร่องที่ต้องมีปลายทางและสถานะ |
| Gate test | เทสที่ผลคงที่ ใช้ตัดสินผ่าน/ไม่ผ่านได้ |
| Exploratory test | การสำรวจหาของที่ไม่ได้คิดไว้ ผลเป็นข้อสังเกต ไม่ใช่คำตัดสิน |
| Flaky | เทสที่ผลไม่คงที่ทั้งที่โค้ดไม่เปลี่ยน |
| Requirement coverage | สัดส่วนความต้องการที่มีเทสรองรับ — ต่างจาก code coverage |
