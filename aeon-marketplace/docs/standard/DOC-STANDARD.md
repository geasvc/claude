## 1. หลักการเดียวที่ทุกข้องอกออกมาจากมัน

> ## สถานะอยู่ใน JSON · ความรู้อยู่ใน Markdown · Markdown ถูก generate จาก JSON ทุกที่ที่มีสคริปต์พิสูจน์ความตรงกันได้

ทั้งสามแหล่งบรรจบกันตรงนี้ และแต่ละแหล่งเติมชิ้นที่อีกสองแหล่งไม่มี:

- **OKF** บอกว่า knowledge เป็น markdown + frontmatter ได้ดีที่สุด (ทุกเครื่องมืออ่านออก ไม่ต้องมี SDK)
- **LLMWIKI** บอกว่าต้องมีชั้น raw / wiki / schema แยกกัน และมี `index.md` `log.md` เป็นกระดูก
- **บทความ harness** เติมเหตุผลที่อีกสองแหล่งไม่ได้พูด ว่าทำไม**สถานะ**ต้องเป็น JSON ไม่ใช่ markdown:

  > *"the model is less likely to inappropriately change or overwrite JSON files"*

  โมเดลลังเลที่จะแก้ JSON แต่แก้ markdown ได้อย่างสบายใจ · ของที่ห้ามเพี้ยนจึงต้องอยู่ในรูปที่โมเดลไม่กล้าแตะ

**`req` ทำแบบนี้อยู่แล้วโดยยังไม่ได้ตั้งชื่อ** — `<state-dir>/spec.json` (ค่าเริ่มต้น `.aeon/`) คือความจริง · `docs/**.md` คือ render ·
`doc-hash.mjs` คือตัวพิสูจน์ว่าสองอย่างยังตรงกัน · มาตรฐานนี้แค่ตั้งชื่อให้มัน แล้วบังคับใช้ให้ทั่วทั้ง repo

**ผลที่ตามมาทันที:** ถ้าข้อมูลชิ้นหนึ่งมีสคริปต์ตรวจความตรงกันได้ → **ห้ามพิมพ์มันด้วยมือลง markdown**
ถ้าตรวจไม่ได้ → มันไม่ใช่สถานะ มันคือความรู้ ให้เขียนเป็น markdown ให้คนอ่านรู้เรื่อง

## 2. เอกสาร 4 ชั้น — คนละกติกา ห้ามปนกันในไฟล์เดียว

| ชั้น | คือ | แก้ด้วยมือ | สคริปต์เขียนทับ | ตัวอย่างจริง |
|---|---|---|---|---|
| **A · Generated** | render จาก JSON | ❌ **ห้าม** | ✅ ทุกครั้ง | `docs/requirements/REQ-*.md` · `docs/wiki/**` |
| **B · Authored** | ความรู้ที่คนคิด | ✅ เฉพาะคน | ❌ **ห้าม** | `SKILL.md` · `USER-GUIDE.md` · `*-Bootstrap.md` · เอกสารออกแบบ |
| **C · Append-only** | บันทึกตามเวลา | ✅ **ต่อท้ายเท่านั้น** | ต่อท้ายได้ ห้ามเขียนทับ | `log.md` · `field-test-log.md` |
| **D · Projection** | ย่อของ B ที่อยู่นอก repo | ✅ | — | brain note / สไลด์ ที่ย่อมาจาก `CLAUDE.md` |

### กติกาต่อชั้น

**A · Generated** — ต้องมี header ที่บอก 3 อย่าง: มาจากไหน · ห้ามแก้ · `spec-hash`
**ห้ามใช้ marker block แบบ "แก้ในนี้ได้"** เด็ดขาด — เพราะสุดท้ายจะมีคนแก้นอก marker แล้ว regenerate กินทิ้งเงียบ ๆ
พังครั้งเดียวแล้วจะไม่มีใครเชื่อ regeneration อีกเลย · อยากแก้ข้อความ → แก้ที่ field ใน JSON

**B · Authored** — ต้องมี **owner** และ **วันที่ทบทวนล่าสุด** · ห้ามมีสคริปต์ไหนเขียนทับ
`CLAUDE.md` เขียนกติกานี้ไว้แล้วสำหรับ `field-test-log.md`: *"It is hand-maintained, not generated: no script may rewrite it."*

**C · Append-only** — บรรทัดที่เขียนแล้วห้ามแก้ ห้ามลบ ห้ามเรียงใหม่ · ผิดก็ต่อท้ายบรรทัดแก้ไข
นี่คือ `log.md` ของ LLMWIKI และคือ *progress file* ของบทความ harness — **ของชิ้นเดียวกัน คนละชื่อ**

**D · Projection** — ของที่ย่อมาแล้วอยู่นอก repo (brain note, สไลด์, สรุปในแชท) ตรวจด้วยสคริปต์ไม่ได้
กติกาข้อเดียวแต่ห้ามพลาด: **ต้องระบุว่าย่อมาจากไฟล์ไหน และประกาศว่าไฟล์นั้นชนะเสมอ**
(CLAUDE.md ทำถูกอยู่แล้ว: *"เมื่อสองอันขัดกัน bootstrap ชนะ และ brain note ต้องถูกอัปเดต"*)
**ห้ามอ้าง Projection เป็นแหล่งอ้างอิงในการตัดสินใจ** ให้ไปเปิดต้นทางเสมอ

### นอกขอบเขตมาตรฐานนี้

`.remember/` และ `.brain/` เป็น **memory ของเครื่องมือ ไม่ใช่เอกสารของโปรเจกต์** — เครื่องมือเป็นเจ้าของรูปแบบ
มันทำหน้าที่ progress-file ตามบทความ harness อยู่แล้ว (`now.md` ต่อท้ายทุก session) แต่**ห้ามใช้แทน `log.md` ของ bundle**
เพราะมันไม่เข้า git และผูกกับเครื่องของคนใช้ — bundle ต้องอธิบายตัวเองได้จากไฟล์ที่อยู่ใน repo เท่านั้น

## 3. โครงไฟล์ — 3 ระดับ คนละกติกา

### 3.1 Marketplace

```
<repo>/
├── .claude-plugin/marketplace.json     # สัญญากับ Claude Code — schema ภายนอกเป็นคนคุม
├── CLAUDE.md                           # 🚪 ประตูเข้า (ดู §7)
├── docs/
│   ├── standard/DOC-STANDARD.md        # ไฟล์นี้
│   ├── <Project>-Bootstrap.md          # B · สเปกเต็ม — **ช่องว่าง ไม่ใช่ข้อบังคับ** (aeon ยังไม่มี)
│   ├── field-test-log.md               # C · ผลใช้จริง — ช่องว่างเหมือนกัน (aeon ยังไม่มี)
│   ├── design-registry.json            # **ความจริง**ของ wiki/ ข้างล่าง — สถานะอยู่ใน JSON (§1)
│   └── wiki/                           # A · OKF bundle ระดับ marketplace · generate ทั้งก้อน
│       ├── index.md · log.md · BUNDLE.md
│       ├── plugins/ · skills/ · commands/ · adr/
├── plugins/<name>/…
├── scripts/                            # ด่านและตัวเรนเดอร์ **ระดับ marketplace**
│   ├── verify-design.mjs               #   ตรวจทุก plugin (D1–D12b)
│   ├── wiki-authoring.mjs              #   render docs/wiki/ จาก design-registry.json
│   └── fixtures/{clean,dirty}/         #   ชุดทดสอบของด่านนั้น
└── schemas/*.schema.json               # สัญญาของ JSON ทุกตัว
```

> **`scripts/` ที่ root ≠ `plugins/<name>/scripts/`** — เส้นแบ่งคือ *ของนี้ตรวจใคร*
> ตัวที่ตรวจ **ทุก plugin** อยู่ที่ root · ตัวที่เป็นของ plugin ตัวเดียวและเดินทางไปกับมันตอนติดตั้ง อยู่ใต้ plugin นั้น
> เอาด่านระดับ marketplace ไปไว้ใน `plugins/req/` แปลว่าด่านที่ตรวจ plugin ตัวอื่นไปนั่งอยู่ในบ้านของ `req`

`marketplace.json` ตรวจโดย `json.schemastore.org/claude-code-marketplace.json`
**มาตรฐานนี้เพิ่มธรรมเนียมได้ แต่ห้ามขัดกับ schema นั้น** — ถ้าขัดกัน schema ภายนอกชนะ

> **`docs/wiki/` มีสองขอบเขต รูปแบบเดียวกัน อย่าสับสน:**
> **authoring bundle** (ตรงนี้) อยู่ใน repo ของ marketplace เก็บ concept ของ *เครื่องมือ* — `plugins/` `skills/` `commands/` `adr/`
> **project bundle** อยู่ในโปรเจกต์ของลูกค้าที่ใช้ plugin เก็บ concept ของ *งาน* — `requirements/` `rules/` `calculations/`
> คนละ repo จึงไม่ชนกัน · frontmatter · `index.md` · `log.md` · ตัวตรวจ ใช้กติกาชุดเดียวกันทั้งคู่

### 3.2 Plugin

```
plugins/<name>/
├── .claude-plugin/plugin.json
├── commands/*.md                       # B · สั้น ชี้ไป skill
├── skills/<skill-name>/
│   ├── SKILL.md                        # B · ≤ 500 บรรทัด
│   └── references/*.md                 # B · รายละเอียดที่ SKILL.md ไม่เก็บ
├── scripts/*.mjs                       # ตัวตรวจ deterministic
├── scripts/fixtures/{clean,dirty}/     # ชุดทดสอบตัวตรวจ
├── assets/*.json                       # ข้อมูลที่ skill อ่าน
└── USER-GUIDE.md                       # B · ภาษาไทย สำหรับคนใช้
```

**ชื่อ plugin ≠ ชื่อ skill** — plugin สั้นเพราะเป็น namespace ที่ต้องพิมพ์ (`/req:ask`)
skill ต้องบรรยายบทบาทเพราะ Claude ใช้มัน routing (`requirement-and-rule-mapping`)

**ทุก plugin ต้องมี `/<plugin>:help` ภาษาไทย** — ข้อบังคับเต็มอยู่ที่ **§3.5** ตรวจโดย D9 + D11

### 3.3 Skill

ระดับนี้ต่างจากอีกสองระดับตรงที่ **Claude อ่านมันทุกครั้งที่ทำงาน** ทุกบรรทัดจึงมีราคาเป็น token

| กติกา | ค่า | เหตุผล |
|---|---|---|
| `SKILL.md` | ≤ 500 บรรทัด | เกินกว่านี้ย้ายลง `references/` |
| ภาษา | **อังกฤษ** | ดู §3.4 |
| `description` | คมตั้งแต่เกิด | ทำอะไร + ใช้เมื่อไหร่ + คำ trigger + **เมื่อไหร่ห้ามใช้** |
| `references/` | มีตั้งแต่วันแรก | ไม่ใช่ค่อยแยกตอนไฟล์บวม |
| frontmatter | **เฉพาะที่ Claude Code กำหนด** (`name`, `description`) | ดู §4 |

### 3.4 ภาษา — ไฟล์เป็นอังกฤษ คำตอบเป็นไทย

**กติกาบังคับ ไม่ใช่ความชอบ:**

| ของ | ภาษา | เหตุผล |
|---|---|---|
| `SKILL.md` · `references/*.md` · `commands/*.md` | **อังกฤษ** | Claude อ่านทุกครั้งที่ทำงาน · ไทยกินโทเคนมากกว่าอังกฤษหลายเท่าต่อความหมายเท่ากัน และจ่ายซ้ำทุก session |
| identifier · JSON key · ชื่อไฟล์ · โค้ด | **อังกฤษ** | ต้องพิมพ์ ต้อง grep ต้องเข้ากับ schema |
| **คำตอบที่ skill พูดกลับหาผู้ใช้ตอนรัน** | **ไทยเสมอ** | คนใช้เป็นคนไทย · เอกสารอังกฤษไม่ได้แปลว่าต้องคุยอังกฤษ |
| `USER-GUIDE.md` · `<plugin>:help` · เอกสารที่คนเปิดอ่าน | **ไทย** | คนอ่าน ไม่ใช่ Claude อ่าน |
| ข้อความ UI / error ที่ยกมาอ้างใน example | **ไทย คำต่อคำ** | เป็นของที่ QA เอาไปเทียบจริง ห้ามถอดความ |

> **ต้องเขียนกติกา "ตอบเป็นไทย" ลงใน `SKILL.md` ตรง ๆ** ไม่ใช่ปล่อยให้เดาจากบริบท
> `SKILL.md` ที่เป็นอังกฤษทั้งไฟล์จะทำให้โมเดลตอบอังกฤษโดยอัตโนมัติ — ต้องมีบรรทัดสั่งไว้ชัด เช่น
> *"Reply to the user in Thai. Files written into the project stay as specified: identifiers, JSON keys,
> and code in English; user-facing document text in Thai."*
> (`req` เขียนไว้แล้วเป็น hard rule ข้อ 5 — ยกมาเป็นแบบให้ทุก skill ทำตาม)

### 3.5 ทุก plugin ต้องมี `<plugin>:help` ภาษาไทย

**บังคับ ไม่มีข้อยกเว้น** — plugin ที่ไม่มี `help` ถือว่ายังไม่พร้อมส่ง

| ข้อบังคับ | รายละเอียด |
|---|---|
| **มีจริง** | ไฟล์ `commands/help.md` และคำสั่ง `/<plugin>:help` ใช้งานได้ |
| **ภาษาไทย** | ทั้งไฟล์ — คนอ่าน ไม่ใช่ Claude อ่าน |
| **อธิบายครบทุกคำสั่ง** | ทุกไฟล์ใน `commands/` ต้องมีหัวข้อของตัวเองใน help · **ขาดแม้ตัวเดียว = ตัวตรวจแดง** |
| **ต่อคำสั่งต้องมี 3 อย่าง** | มันทำอะไร · **ตัวอย่างใช้งานจริงที่พิมพ์ตามได้เลย** · เขียนไฟล์อะไรบ้าง (หรือ 👁 ถ้าอ่านอย่างเดียว) |
| **บอกของที่ยังไม่ได้สร้าง** | คำสั่งที่ออกแบบไว้แต่ยังไม่มี ต้องขึ้นชื่อพร้อมป้ายว่ายังไม่มี — ไม่งั้นคนสั่งแล้วเจอ Claude เดาทำให้ |
| **`help` เป็น 👁 อ่านอย่างเดียว** | ห้ามเขียนไฟล์ใด ๆ |

> **ทำไมผูกกับ plugin ไม่ใช่ skill:** `:` คือ namespace ของ **plugin** และคำสั่งอยู่ที่ `plugins/<name>/commands/`
> ไม่ได้อยู่ในโฟลเดอร์ skill · plugin หนึ่งตัวมีได้หลาย skill แต่มี `help` เดียว —
> **`help` ต้องครอบคำสั่งของทุก skill ในนั้น** ไม่ใช่เฉพาะ skill หลัก
>
> **ทำไมต้องบังคับ:** `help` คือเอกสารเดียวที่คนใช้เปิดตอน**กำลังจะพิมพ์คำสั่ง** — `USER-GUIDE.md` คนอ่านตอนติดตั้ง
> แล้วไม่กลับมาอ่านอีก · plugin ที่ไม่มี `help` ผู้ใช้จะรู้จักแค่คำสั่งที่บังเอิญเคยเห็น

## 4. Frontmatter — และที่ที่ห้ามใส่

รูปแบบตาม OKF: **`type` เป็น field เดียวที่บังคับ** ที่เหลือผู้ผลิตกำหนดเอง

```yaml
---
type: Plugin                 # บังคับ · ต้องมาจากรายการปิดใน §5
title: req                   # ชื่อที่คนเรียก
description: Phase 1 — เก็บ requirement ดิบให้เป็นกฎที่ trace ได้
resource: ../../plugins/req  # ชี้ของจริง (path หรือ URL)
tags: [phase-1, requirements]
timestamp: 2026-08-13T10:22:00+07:00
# ── ส่วนขยายของโปรเจกต์ ────────────────
id: PLG-req                  # singleton type ไม่มีเลขลำดับ — ดู §5
lifecycle: built             # built | design-only | proposed | deprecated
owner: พี่ปู
spec_hash: sha256:…          # เฉพาะเอกสารชั้น A
---
```

> **⚠️ ห้ามใช้คีย์ `status:` สำหรับความหมายนี้** — `status` ถูกจองไว้แล้วโดย `spec.schema.json`
> ด้วยชุดค่าคนละชุด (`draft | validated | locked | superseded`) และหน้าชั้น A ถูก generate จากโหนดที่ถือค่านั้น
> ถ้าใช้คีย์เดียวกันสองความหมาย ตัวตรวจ D2/D3 จะ validate ได้แค่ชุดเดียว และอีกชุดจะแดงตลอด
> **`lifecycle` = สถานะของงานสร้าง · `status` = สถานะของโหนดใน spec** คนละเรื่อง คนละคีย์

### ใส่ที่ไหน ไม่ใส่ที่ไหน — ตัดสินด้วย "ใครอ่าน"

| ไฟล์ | frontmatter | เหตุผล |
|---|---|---|
| หน้า concept ใน `docs/wiki/**` | ✅ **บังคับครบ** | คน + เครื่องมือ + agent ภายนอกอ่าน · เป็นของที่ทำให้ bundle เป็น OKF |
| `index.md` · `log.md` | ✅ `type` + `title` พอ | เป็นสารบัญ ไม่ใช่ concept |
| `USER-GUIDE.md` · เอกสารออกแบบ | 🟡 ใส่ได้ ไม่บังคับ | คนอ่านเป็นหลัก |
| **`SKILL.md`** | ❌ **ห้ามเพิ่ม field ของ OKF** | frontmatter ของมันเป็น**สัญญากับ Claude Code** (`name`, `description`) การเติม field แปลกปลอมเข้าไปเสี่ยงกับ loader และไม่ได้ประโยชน์ — ไม่มีเครื่องมือ OKF ตัวไหนมาอ่าน `SKILL.md` |
| **`references/*.md`** | ❌ **ไม่ใส่** | Claude อ่านกลางงาน · frontmatter 8 บรรทัด × หลายไฟล์ × ทุก session = ต้นทุนที่ไม่ได้อะไรกลับมา ใช้หัวข้อ `#` บรรทัดเดียวแทน |

> **นี่คือจุดที่สามแหล่งขัดกันจริง ๆ และต้องเลือกข้าง** — OKF อยากได้ frontmatter ทุกไฟล์
> แต่กติกา token cost ของโปรเจกต์นี้มาก่อน · เส้นแบ่งคือ **"ไฟล์ที่ Claude อ่านระหว่างทำงาน ไม่ต้องมี"**

## 5. รายการ `type` — ปิดรายการ

OKF ปล่อยให้ผู้ผลิตตั้ง type เองได้ — ดีภายใน bundle เดียว แต่**พังทันทีที่ข้าม marketplace**
เพราะ `Plugin` กับ `plugin` กับ `Claude Plugin` จะกลายเป็นคนละชนิดในสายตาเครื่องมือ

**มีสองรายการปิด เพราะมีสอง bundle scope (§3.1)** — ปนกันไม่ได้ และ **D2 ตรวจตาม scope ของ bundle ที่หน้านั้นอยู่ ไม่ใช่ตรวจรวมกันทั้งกอง**

### 5.1 Authoring bundle — concept ของ *เครื่องมือ* (อยู่ใน repo ของ marketplace)

| `type` | ใช้กับ | id | รูปแบบ |
|---|---|---|---|
| `Marketplace` | ตัว repo | `MKT-aeon` | singleton |
| `Plugin` | หนึ่ง plugin | `PLG-req` | singleton |
| `Skill` | หนึ่ง skill | `SKL-requirement-and-rule-mapping` | singleton |
| `Schema` | ไฟล์ `*.schema.json` | `SCH-spec` | singleton |
| `Checkpoint` | CP1–CP6 | `CP1` … `CP6` | ใช้ชื่อเดิมที่ทั้งระบบเรียกอยู่แล้ว |
| `Command` | หนึ่งคำสั่ง | `CMD-req-001` | instance |
| `Script` | ตัวตรวจ / ตัวคำนวณ | `SCR-req-001` | instance |
| `Decision` | ADR — ตัดสินแล้วพร้อมเหตุผล | `ADR-req-003` | instance |
| `Field Note` | ผลใช้จริง 1 รอบ | `FN-req-001` | instance |
| `Standard` | มาตรฐาน เช่นไฟล์นี้ | `STD-doc-001` | instance |

### 5.2 Project bundle — concept ของ *งานลูกค้า* (อยู่ในโปรเจกต์ที่ใช้ plugin)

**รายการนี้ไม่ได้ตั้งขึ้นใหม่ — มันคือสไปน์ของ `spec.json` ที่มีอยู่แล้ว และ `spec.schema.json` เป็นเจ้าของ id pattern**

| `type` | มาจาก | id |
|---|---|---|
| `Requirement` | `requirements[]` | `REQ-<module>-<nnn>` |
| `Business Rule` | `rules[]` | `BR-<module>-<nnn>@vN` |
| `Example` | `examples[]` | `EX-<module>-<nnn>` |
| `Glossary Term` | `glossary[]` | `UL-<module>-<nnn>` |
| `Open Question` | `questions[]` | `Q-<module>-<nnn>` |
| `Deferred Question` | `deferred_questions[]` | `DQ-<module>-<nnn>` |
| `NFR` | `requirements[].nfr[]` | `NFR-<module>-<nnn>` |
| `Source` | `sources[]` | **`SRC-<nnn>`** ← ไม่มีส่วน module |
| `Calculation Contract` | `calculations[]` | `CALC-<module>-<nnn>@vN` |
| `Golden Dataset` | `golden_datasets[]` | `GD-<module>-<nnn>` |
| `Change Set` | `changes[]` | `CHG-<module>-<nnn>` |

> ✅ **สาม type ล่างพ้นสถานะ `lifecycle: proposed` แล้วเมื่อ 2026-08-13** — เงื่อนไขที่ประกาศไว้คือ
> *"จนกว่า `spec.schema.json` จะมีอาเรย์รองรับจริง"* และตอนนี้มีครบทั้งสาม (`calculations` ·
> `golden_datasets` · `changes` อยู่ใน `required` ของ schema) จึงตัด ⚠️ warn ที่ผูกกับเงื่อนไขนั้นออก
> **ไม่ใช่เพราะเลิกสนใจ แต่เพราะเงื่อนไขที่ตั้งไว้ถูกทำจนครบ** — warn ที่ปิดไม่ได้ต้องไม่มี (§9)
> พิสูจน์: `node plugins/req/scripts/doc-frontmatter.mjs --verify-against schemas/spec.schema.json` → exit 0
>
> รูปแบบ id ของทั้ง 11 type ในตารางนี้ **`spec.schema.json` เป็นเจ้าของ** และ `doc-frontmatter.mjs`
> ถือสำเนาไว้เพราะต้องรันในโปรเจกต์ลูกค้าที่หา schema ไม่เจอ — คำสั่งข้างบนคือตัวที่กันไม่ให้สำเนานั้นหนี

> **`index.md` · `log.md` · `BUNDLE.md` ของ bundle ไม่ใช่หน้า concept** และไม่ต้องมี `type`/`id`/hash
> — §6 แยกมันเป็น "กระดูกของ bundle" อยู่แล้ว · D1–D4 และ #12 (ก)–(ง) จึงข้ามไฟล์สามชื่อนี้
> แต่ **กติกาลิงก์ (D5 / #12 จ) ยังบังคับ** เพราะสารบัญที่ชี้ไปหน้าที่ถูกเปลี่ยนชื่อคือของเน่าที่ bundle นี้มีไว้กัน

> **`SRC-<nnn>` เป็นข้อยกเว้นของรูปแบบ instance และห้ามไปแก้** — `spec.schema.json` กำหนด `^SRC-[0-9]{3}$`
> ไว้แล้ว การเปลี่ยนรูปแบบ id เพื่อให้เข้ามาตรฐานเอกสารจะทำให้ทุก spec ที่มีอยู่ตกทันที
> **เมื่อ schema กับมาตรฐานนี้ขัดกันเรื่อง id — schema ชนะ** และมาตรฐานจดข้อยกเว้นไว้ตรงนี้
> (หลักเดียวกับที่ `marketplace.json` ยอมให้ schema ภายนอกชนะใน §3.1)

**กติกาการเพิ่ม type ใหม่** — ยืมมาจากกติกาของ question bank เพราะพิสูจน์แล้วว่ากันของบวมได้จริง:

> เพิ่มได้เฉพาะเมื่อ**งานเขียนเอกสารจริงเรียกร้องมันแล้ว** ห้ามเพิ่มจากทฤษฎีหรือจากการคาดว่าจะได้ใช้

**รูปแบบ id มีสองแบบ ไม่ใช่แบบเดียว:**

| แบบ | รูปแบบ | ใช้กับ | เหตุผล |
|---|---|---|---|
| **instance** | `<PREFIX>-<module>-<nnn>` เลข 3 หลัก | Command · Script · Decision · Field Note · Standard | มีได้หลายตัวต่อโมดูล ต้องมีเลขแยก — ตรงกับสไปน์เดิม (`REQ-job-001`) |
| **singleton** | `<PREFIX>-<slug>` **ไม่มีเลข** | Marketplace · Plugin · Skill · Schema | หนึ่ง repo มี `req` ได้ตัวเดียว · `PLG-req-001` คือเลขที่ไม่มีวันขึ้นเป็น `002` = noise |

(เวอร์ชันต่อท้ายด้วย `@vN` เฉพาะโหนดที่มีของข้างล่างชี้แบบล็อกเวอร์ชัน)

## 6. `index.md` และ `log.md` — กระดูกของ bundle

**`index.md` (ทุกไดเรกทอรี)** — LLMWIKI เรียกว่า *content-oriented catalog* · OKF เรียกว่า *progressive disclosure*
ของเดียวกัน: ให้คนอ่านรู้ว่ามีอะไรบ้างโดยไม่ต้องเปิดทุกไฟล์

- หนึ่งบรรทัดต่อหนึ่งหน้า: ลิงก์ + สรุปหนึ่งบรรทัด + สถานะ
- **ต้องมีคอลัมน์ที่ตอบคำถามหลักของไดเรกทอรีนั้น** — สารบัญที่มีแต่ชื่อไฟล์ไม่ได้ช่วยอะไรที่ `ls` ทำไม่ได้
  (เช่นสารบัญกฎต้องมีคอลัมน์ *"มีตัวอย่างพิสูจน์กี่ตัว"* เพราะนั่นคือคำถามที่คนเปิดมาถาม)
- อัปเดตทุกครั้งที่มีไฟล์เพิ่ม/ลบ — ถ้าเป็นชั้น A ให้ generate

**`log.md` (หนึ่งอันต่อ bundle)** — ชั้น C ต่อท้ายอย่างเดียว

```markdown
| เมื่อ | ใคร/คำสั่ง | เข้ามา | ผล |
|---|---|---|---|
| 2026-08-13T10:22+07:00 | `/req:capture loan` | SRC-006 | +GD-loan-003 · +Q-loan-004 🛑 |
```

**สิ่งที่ต้องจดแม้ไม่มีอะไรเปลี่ยน:** การตัดสินใจที่เลื่อนออกไป · คำถามที่ยังไม่ตอบ · การแจ้งเตือนที่ผู้ใช้ข้าม
บทความ harness ชี้ว่าความพังของ agent ที่ทำงานยาวคือ *undocumented intermediate states* — **สิ่งที่ยังไม่เสร็จสำคัญกว่าสิ่งที่เสร็จแล้ว** เพราะสิ่งที่เสร็จแล้วอ่านได้จาก git

## 7. เอกสารประตูเข้า — ข้อบังคับที่มาจากบทความ long-running agent ทั้งดุ้น

ทุก repo ต้องมี **ไฟล์เดียว** ที่ session ใหม่ (คนหรือ agent) อ่านแล้ว**ทำงานต่อได้โดยไม่ต้องเดา**
ใน marketplace `aeon` คือ `CLAUDE.md` · ต้องมีครบ 5 ส่วนนี้:

| # | ส่วน | ทำไม (failure mode ที่กัน) |
|---|---|---|
| 1 | **สร้างอะไรไปแล้ว vs ยังเป็นแค่แบบ** ระบุชัดรายตัว | *premature completion* — agent อ่านแบบออกแบบแล้วนึกว่าของมีอยู่จริง · CLAUDE.md ทำถูกแล้ว: *"do not assume any file outside `plugins/req/` exists until you have listed it"* |
| 2 | **ลำดับความน่าเชื่อของแหล่งอ้างอิง** อันไหนชนะเมื่อขัดกัน | สองแหล่งพูดไม่ตรงกันแล้วไม่มีใครรู้ว่าเชื่ออันไหน |
| 3 | **คำสั่งที่รันได้จริง** พร้อมผลที่ต้องได้ (เช่น *"expect 29 errors"*) | *skipping baseline verification* — ไม่มี smoke test ตอนเริ่ม บั๊กจะทับถมข้าม session |
| 4 | **งานถัดไปที่ยังไม่เสร็จ** เป็นรายการที่มีสถานะ ไม่ใช่ร้อยแก้ว | *one-shotting* — ไม่มีรายการงาน agent จะพยายามทำทีเดียวจบแล้วพังกลางทาง |
| 5 | **ประตูที่ยังปิดอยู่** — สิ่งที่ห้ามข้ามไปทำต่อ | ตัดสินใจซ้ำสิ่งที่ตัดสินไปแล้ว หรือข้ามสิ่งที่ยังไม่ตัดสิน |

### กติกาที่ตามมาจากบทความ 4 ข้อ

1. **เขียนให้คนที่ไม่มีความทรงจำเลยอ่านรู้เรื่อง** — ห้ามอ้าง "ตามที่คุยกันเมื่อวาน" · เอกสารคือความทรงจำเดียวที่เหลือ
2. **สถานะงานต้องเป็น JSON ที่มี pass/fail ต่อรายการ** ไม่ใช่ย่อหน้าเล่าความคืบหน้า
   > *"the model is less likely to inappropriately change or overwrite JSON files"*
   > และ *"It is unacceptable to remove or edit tests"* — **ห้ามลบรายการที่ยังไม่ผ่านเพื่อให้ดูเหมือนเสร็จ**
3. **ห้ามเขียนว่าเสร็จโดยไม่ระบุคำสั่งที่พิสูจน์** — `CLAUDE.md` บังคับไว้แล้วในรูปประโยคว่า
   *"`req`'s pass criterion is not 'runs without error'"* แต่คือ *"ใช้กับโมดูลจริงแล้วการ์ดแดงโผล่จริง"*
4. **หนึ่งไฟล์ = หนึ่งหน่วยงาน** เท่าที่ทำได้ · เอกสารก้อนใหญ่ทำให้ session หนึ่งต้องกลืนทั้งก้อนเพื่อแก้บรรทัดเดียว
   **ยกเว้นชั้น B ชนิด "ข้อเสนอออกแบบ"** ซึ่งคุณค่าอยู่ที่การเห็นทั้งระบบพร้อมกัน — ยกเว้นโดยประกาศ ไม่ใช่โดยเงียบ

## 8. กติกาการเขียน 10 ข้อ

1. **หนึ่งข้อเท็จจริงมีที่อยู่ที่เดียว** ที่เหลืออ้างด้วยลิงก์ · ก๊อปตัวเลขไปวางที่สอง = วันหนึ่งจะไม่ตรงกัน
2. **ทุกการอ้างอิงเป็นลิงก์ markdown ธรรมดา** — นี่คือกราฟความสัมพันธ์ทั้งหมด ไม่ต้องมีรูปแบบพิเศษ
3. **อ้างคำพูดต้นทางแบบคำต่อคำ** ห้ามถอดความ · คำที่ยกมาคือของที่เอาไปยันกับลูกค้าได้
4. **ทุกอย่างที่ยังไม่ตัดสินต้องมี id และมีสถานะ** — "ยังไม่แน่ใจ" ที่ไม่มี id จะกลายเป็นข้อเท็จจริงภายใน 3 วัน
5. **ตัวเลขต้องมาจากสคริปต์** ถ้ามันคำนวณได้ · ห้ามนับด้วยมือแล้วพิมพ์ลงไป
6. **ระบุว่าอะไรที่ยัง *ไม่* ได้ทำ** ให้ชัดเท่ากับที่ทำแล้ว — และคำสั่งที่ยังไม่มี ต้องบอกว่ายังไม่มี ห้ามเดาทำให้
7. **ภาษา — ตารางเต็มอยู่ที่ §3.4** สรุป: ไฟล์ที่ Claude อ่านทุกครั้ง = อังกฤษ · **คำตอบที่พูดกับผู้ใช้ = ไทยเสมอ** ·
   `help` / `USER-GUIDE.md` = ไทย · identifier / JSON key / โค้ด = อังกฤษ
   **ยกเว้นเอกสารประตูเข้า (`CLAUDE.md`)** ซึ่งถือกฎยืนของเจ้าของที่ทั้งระบบต้องเชื่อฟังคำต่อคำ —
   ของแบบนั้นเขียนเป็นไทยได้และควรเป็นไทย เพราะการแปลคือการตีความ และ CLAUDE.md เองก็สั่งไว้ว่า *"do not translate or paraphrase"*
8. **วันที่เป็น absolute เสมอ** ห้าม "อาทิตย์ที่แล้ว" — เอกสารอายุยาวกว่าความทรงจำของคนเขียน
   **รูปแบบมาตรฐาน: RFC 3339 มีวินาที และมี offset ชัดเจน** → `2026-08-13T10:22:00+07:00`
   วันที่ล้วนใช้ `2026-08-13` · **ห้ามใช้ `Z`** ให้ใช้ `+07:00` ให้ตรงกับข้อมูลที่มีอยู่ทั้งหมด
   ⚠️ **schema ไม่ได้บังคับเรื่องนี้ให้** — `$defs.timestamp` เป็นแค่ `{type: string, minLength: 10}`
   และข้อมูลจริงในระบบมีทั้ง `2026-08-01T12:10+07:00` (ไม่มีวินาที) → **ตัว render ต้อง normalize ก่อนเขียนลง frontmatter**
   จะ generate ค่า `timestamp` ตรง ๆ จาก spec ไม่ได้
9. **ตารางมาก่อนย่อหน้า** ถ้าเนื้อหาเป็นการเทียบหรือแจกแจง · ย่อหน้ายาวคือที่ซ่อนของข้อมูลที่ตรวจไม่ได้
10. **เขียนเหตุผลไว้ข้างการตัดสินใจเสมอ** — เอกสารที่บอกแค่ "ทำแบบนี้" จะถูกคนรุ่นถัดไปแก้กลับภายในเดือนเดียว

*"the meta-level twin of the runtime graph: does the design of the 8 plugins actually connect?"*
> ✅ **ทั้งคู่เกิดจริงแล้ว 2026-08-13** (งานข้อ 5 และ 6 ใน [`docs/progress.json`](../progress.json)) — ย่อหน้าข้างล่างจึงไม่ใช่ข้อเสนออีกต่อไป
> แต่เป็นคำอธิบายของสิ่งที่รันได้: `node scripts/verify-design.mjs --root .`

**การตรวจเอกสารคืองานเดียวกันกับตัวนั้น** — ทั้งคู่ถามว่า "ของที่เขียนไว้ ยังชี้ถึงกันจริงไหม"
มาตรฐานนี้จึงเสนอเป็น **ชุดตรวจที่เพิ่มเข้าไปใน `verify-design.mjs`** ไม่ใช่สคริปต์ตัวที่สาม
(ตัวที่สามแปลว่ามีสามที่ที่ต้องรันและสองที่ที่จะลืมรัน)

`document-template.md` คือหลักฐานว่าทิศทาง "ห้ามมีไทย" **บังคับเป็น error ไม่ได้**: มันกำหนดว่าเอกสารที่ผลิตออกมา
ต้องมีหัวข้อชื่อ *"การ์ดแดง"* *"ที่มาของ requirement"* — เขียนเป็นอังกฤษแล้วผลลัพธ์จะผิด
**สคริปต์แยกไม่ออกระหว่าง "ร้อยแก้วไทยที่ไม่ควรมี" กับ "สตริงไทยที่ต้องมี"** จึงได้แค่ชี้ให้คนดู

> **D9 · D11 · D12a เข้าเป็น `error` ตั้งแต่แรก ไม่ใช้บรรทัดฐาน warn-first** — บรรทัดฐานนั้นมีไว้สำหรับ
> check ที่ทีมคิดขึ้นเองแล้วยังไม่รู้ว่าคุ้มไหม · สามข้อนี้**เจ้าของสั่งเป็นข้อบังคับโดยตรง** จึงไม่ต้องหาหลักฐานว่าคุ้ม
> ส่วน **D12b เป็น warn ถาวร ไม่ต้องรอโปรโมต** — เพราะมันเดาเจตนาจากอักขระ และตารางข้างบนพิสูจน์แล้วว่าเดาผิดได้จริง

**D4 ต้องรับสองรูปแบบ ห้ามบังคับให้เหลือแบบเดียว:**

| รูปแบบ | ใช้ที่ไหน | ทำไมห้ามยุบ |
|---|---|---|
| `<!-- … spec-hash: sha256:… -->` (HTML comment, ขีดกลาง) | `docs/requirements/REQ-*.md` ที่มีอยู่แล้ว | `doc-hash.mjs` export `SPEC_HASH_RE = /spec-hash:\s*(sha256:[0-9a-f]{64})/` และ **check #10 พึ่งมันอยู่** — เปลี่ยนคีย์ = ทุกเอกสารที่มีอยู่กลายเป็น stale พร้อมกัน |
| `spec_hash: sha256:…` (YAML frontmatter, ขีดล่าง) | หน้า concept ใน `docs/wiki/**` (ของใหม่) | หน้า wiki มี frontmatter อยู่แล้ว ยัด HTML comment เพิ่มคือของซ้ำซ้อน |

**D5 ต้องข้ามลิงก์ในบล็อกโค้ด** (` ``` ` และ inline code) — เทมเพลตใน §12 มีลิงก์ตัวอย่างที่ยังไม่มีไฟล์จริง
ไม่ข้าม = false positive ถาวร ซึ่ง §9 บอกเองว่าห้ามมี

รูปแบบเดิมทั้งหมด: exit `0` เขียว · `1` เจอปัญหา (พิมพ์ออกมาทุกข้อ) · `2` ไฟล์พัง
**ไม่มีข้อไหนให้ AI ตัดสิน** และต้องมี fixture `clean/` + `dirty/` โดย `dirty/` ผิดครบทุกข้อ

**ส่วนที่ของใครของมัน — ห้ามยัดเข้าโมดูลร่วม**

> เขียนว่า "เสนอไว้แต่ยังไม่มี" เกิดขึ้นจริงแล้ว ด่านจึงเปิดตามเงื่อนไขที่ประกาศไว้เอง ไม่ใช่เพราะเปลี่ยนใจ
> **ไม่มีทะเบียน = ไม่รันแล้วพิมพ์ `LIMIT D7` ไม่ใช่รายงานศูนย์เงียบ ๆ** · หลักเดียวกับ D4 ที่เทียบ hash
> ด้วย closure ตัวเดียวกับตัวเรนเดอร์ (`scripts/registry.mjs`) — **ด่านที่คำนวณ hash เอง คือด่านที่ตรวจเลขคณิตของตัวเอง**

> **ของใหม่เข้าเป็น warn ก่อนเสมอ** ตามบรรทัดฐานของ check #11 (คำศัพท์) ที่ตั้งเป็น warn พร้อมเหตุผลว่า
> *"ยังไม่มีหลักฐานว่าคุ้ม ค่อยเลื่อนเป็นบล็อกหลังใช้จริง"* — และ **warn ที่ปิดไม่ได้ ห้ามมี**
> เพราะ warn ที่แดงตลอดจะสอนให้คนเลิกอ่าน warn ทั้งหมด

## 10. Anti-pattern — พร้อมราคาที่จ่ายไปแล้วจริง

| อย่าทำ | เกิดอะไร | ราคาที่จ่ายไปแล้ว |
|---|---|---|
| นับเลขสรุปด้วยมือแทนเรียกสคริปต์ | ต้องแบกไฟล์ทั้งก้อนเข้า context ทุกคำสั่ง | **~449k token** ใน field test รอบ 1 |
| ตั้ง orchestrator มาคุม agent ย่อย | context bootstrap ซ้ำซ้อน | **~330k token** กับหน้า CRUD หน้าเดียว |
| ใส่ marker block "แก้ตรงนี้ได้" ในเอกสาร generate | มีคนแก้นอก marker → regenerate กินทิ้งเงียบ | ความเชื่อมั่นใน regeneration หายทั้งทีม |
| เขียนสถานะเป็นร้อยแก้ว | โมเดลแก้ทับได้อย่างสบายใจ | บทความ harness ระบุตรง ๆ ว่าใช้ JSON แทน |
| ลบ/แก้รายการทดสอบให้ผ่าน | ฟีเจอร์หายเงียบ | *"unacceptable to remove or edit tests"* |
| สรุปว่าเสร็จโดยไม่รันของจริง | agent ประกาศจบทั้งที่ยังพัง | failure mode อันดับ 1 ของบทความ |
| เอกสารหนึ่งใบมีทั้ง generated และเขียนมือ | ไม่มีใครรู้ว่าแก้ตรงไหนได้ | ที่มาของกติกาห้าม marker |
| เพิ่ม `type` / คำถาม / check จากทฤษฎี | มาตรฐานบวมจนไม่มีใครทำครบ | บทเรียนจาก question bank |
